# 장애 시뮬레이터 시나리오 매트릭스 실행 보고서 (RPT-03 · M-014)

> **에이전트 지침**
> - **읽는 시점**: 장애 시뮬레이터 시나리오의 실제 동작·소요 시간이 필요할 때, 시나리오를 추가·변경할 때.
> - **이 문서가 정하는 것**: 아무것도 정하지 않습니다. 실측 기록입니다. 수치는 아래 환경·커밋에서만 유효합니다.
> - **강제 규칙**: 여기 수치를 다른 환경의 성능으로 옮겨 적지 않습니다. 재실행은 `load-tests/scenario-matrix.py`로 하고 원본 결과 경로를 함께 남깁니다.

## 1. 요약

운영 콘솔 장애 시뮬레이터([DOC-15 §5](../docs/15-ui-screen-plan.md), `apps/web-ops/src/lab/scenarios.ts`)의
시나리오 **아홉 개를 전부, 각 3회** 스크립트로 실행하고 사람이 눈으로 보던 것을 수치로 모았습니다.

- **27회 전부 기대한 종결 상태에 도달**했고, 성공한 건은 원장 전기 정확히 1회, 실패한 건은 0회였습니다(INV-004).
- 불변조건 게이지 네 개(`paritypay_invariant_*`)는 시작부터 끝까지 **전부 0**이었습니다.
- 미확정(`UNKNOWN`)에서 종결까지: 외부에 기록이 있으면 **31~35초**, 없으면 **43~44초**, 조회 장애가 60초 이어지면
  장애 해소 뒤 **6~26초**. 그동안 원장도 잔액도 움직이지 않았습니다.
- 웹훅 중복은 두 번째가 `DUPLICATE`로, 역순은 `STALE`로 버려졌고 상태·원장은 그대로였습니다.
- **발견 3건**: 로컬 스택이 기관에 웹훅 주소를 알려 주지 않아 웹훅 시나리오 세 개가 실제로는 아무 알림도
  받지 않고 있었음(고침); 시뮬레이터의 "웹훅 미전송"·"웹훅 역순" 정의가 버튼 한 번으로는 설명문의 상황을
  만들지 못함; 복구 시도 횟수는 확정 뒤에는 어디에도 남지 않음(§5).

## 3. 방법

시뮬레이터가 하는 것을 그대로 합니다 — 기관 모드를 바꾸고(`POST /admin/mock-bank/mode`, `/admin/mock-pg/mode`),
새 회원으로 충전(은행 시나리오) 또는 카드 결제(PG 시나리오)를 요청하고, 시뮬레이터 사용자가 다음
시나리오를 고르며 되돌리듯 모드를 즉시 `NORMAL`로 되돌린 뒤, **조회 API가 종결 상태를 보일 때까지**
1초마다 폴링합니다. 시간은 요청을 보낸 순간부터입니다 — 화면이 보는 것과 같습니다.

시나리오마다 다음을 기록합니다.

| 항목 | 출처 | 왜 |
|---|---|---|
| 첫 응답 HTTP·상태 | API | 201/200이면 즉시 확정, 202면 미확정 |
| 종결까지 초 | API 폴링 | FE-003 폴링 상한을 정하는 값 |
| 원장 POSTED 수 | DB 읽기 (`ledger_transaction.reference_id`) | INV-004 — 성공 1, 실패 0 |
| 잔액 변화 | API `GET /wallets/me` 전후 | 스냅샷이 원장과 같은 말을 하는지 |
| 웹훅 영수증·커서 | DB 읽기 (`webhook_receipt`, `webhook_cursor`) | 받아들인 알림 수와 순번 |
| 웹훅 처리 결과 | pay-api 로그 (`duplicate webhook`, `stale webhook`) | 버린 알림 수 |
| 불변조건 게이지 | `/actuator/prometheus` | 시나리오마다 0 확인 |

두 시나리오는 시뮬레이터 정의와 다르게 잡았고 이유를 §5에 적었습니다: `pg-timeout-after`·`pg-query-down`은
웹훅을 끄고(`NONE`) 쟀고, `webhook-out-of-order`는 승인 뒤 기관에 같은 승인을 다시 알리게 했습니다.

### 4.2 미확정 경로의 시간 구조

세 경로가 왜 그 시간인지를 로그로 확인했습니다.

| 경로 | 구성 | 근거 |
|---|---|---|
| 기록 있음 (4·5) | grace 30초 + 다음 틱(≤5초) + 조회 1회 → 31~35초 | 로그 `recovered top-up … as SUCCEEDED` 1줄 |
| 기록 없음 (3) | grace 30초 + "없음" 3회 연속 확인(백오프 2·4초) → 43~44초 | 로그 `settled … as FAILED after 3 consecutive not-found results` |
| 조회 장애 (6) | 장애 중 조회 실패 4~5회(+27~57초, 5초 간격 → 백오프 확대), 장애 해소 후 6~26초 안에 확정 | `log-derived.txt` |

6번에서 조회 장애가 이어지는 60초 동안 상태는 `UNKNOWN`, 원장 0, 잔액 변화 0이었습니다 — **아무것도
단정하지 않았습니다.** 해소 뒤 확정 시각이 6초와 26초로 갈린 것은 백오프가 장애 중에 커졌기 때문입니다
(2회차는 다섯 번째 실패 뒤 다음 확인이 25초 뒤였고, 그 확인이 성공했습니다).

M-011(reports/11)의 "기록 있음 35~45초·기록 없음 약 45초"와 같은 자리입니다. 이번에는 클라이언트가
요청을 보낸 순간부터 재어 몇 초 짧습니다.

## 5. 발견

### 발견 1 — 로컬 스택이 기관에 웹훅 주소를 알려 주지 않았습니다 (고침)

`docker-compose.yml`의 mock-pg에 `MOCK_PG_WEBHOOK_URL`이 없었습니다. 기관은 주소가 비어 있으면 알림을
보내지 않으므로(`WebhookSender`), `scripts/dev.sh`로 띄운 스택에서 시뮬레이터의 웹훅 시나리오 세 개를
적용해도 **알림이 하나도 오지 않았습니다.** 화면에는 "적용했습니다"가 뜨고 결제는 정상 승인되니 아무도
알 수 없었습니다. 통합 시험은 하니스가 주소를 등록하므로 거기서는 드러나지 않습니다.

이 실험은 하니스가 주소를 직접 등록해(`POST /mock-pg/admin/behavior`) 쟀습니다. 스택 쪽은
`MOCK_PG_WEBHOOK_URL=http://host.docker.internal:${PARITYPAY_PORT:-8080}/api/v1/webhooks/mock-pg`를
compose에 넣고, `dev.sh`가 우회한 API 포트를 `PARITYPAY_PORT`로 넘기게 고쳤습니다. 결함 B·J와 같은
모양입니다 — 시험 경로에만 있고 운영(여기서는 개발) 경로에 없던 배선.

### 발견 2 — 시뮬레이터의 웹훅 시나리오 둘은 버튼 한 번으로 설명문의 상황이 되지 않습니다

- **"웹훅을 아예 보내지 않음"** — 설명은 "알림 없이 조회만으로 확정되는지 봅니다"인데, 정의는 승인 모드
  NORMAL + 웹훅 NONE입니다. 승인이 정상이면 결제는 201로 즉시 `APPROVED`이고 조회로 확정할 것이 없습니다
  (9번 결과 0.1초). 설명문의 상황은 **승인 뒤 응답 끊김 + 웹훅 NONE**이고, 그것이 이 보고서의 5번입니다.
- **"웹훅 역순 도착"** — 기관은 같은 키의 **두 번째** 알림이 나갈 때만 뒤늦은 알림을 덧붙입니다
  (`WebhookSender`: `sequence > 1`). 결제 한 건은 알림이 하나라 아무 일도 일어나지 않습니다. 통합 시험도
  두 번째 알림을 손으로 보냅니다. 이 실험은 기관에 같은 승인을 다시 요청해 재현했습니다.

둘 다 시스템의 결함이 아니라 **시뮬레이터 정의와 설명문의 불일치**입니다. 조치는 다음 중 하나이고
결정은 열어 둡니다: (a) 미전송 시나리오의 승인 모드를 `TIMEOUT_AFTER_APPROVAL`로 바꾼다, (b) 역순
시나리오에 "이 시나리오는 같은 결제의 두 번째 알림이 있어야 재현됩니다"를 설명문에 적거나 뺀다.

### 발견 3 — 복구 시도 횟수는 확정 뒤에 남지 않습니다

`top_up_recovery`·`payment_recovery` 행은 확정과 함께 지워집니다. 운영 콘솔의 "조회 시도" 열은 미확정인
동안만 값이 있고, 확정 뒤에 "몇 번 만에 됐는가"는 로그에만 있습니다(`after 3 consecutive not-found
results`). 이 실험도 시도 횟수를 로그에서 셌습니다. 지표(`UNKNOWN` 체류 시간·복구 시도 분포)를 남기려면
확정 시점에 감사 로그나 카운터로 옮겨 적어야 합니다. 지금은 **미측정 항목**으로 둡니다.

### 그 밖에 적어 둘 것

- 은행이 명시적으로 거절하면 응답은 **200 FAILED**입니다(201도 4xx도 아님). 요청은 정상 처리됐고 결과가
  실패라는 뜻입니다(`TopUpController`). DOC-08에는 201과 202만 적혀 있어 200을 추가했습니다. 화면은
  "충전 실패"로 그립니다.
- 카드 결제 시나리오는 지갑 잔액을 움직이지 않습니다. 시뮬레이터 설명문 "고객 앱에서 충전이나 결제를
  실행하고 아래 카드를 보십시오"에서 카드 결제 뒤 잔액이 그대로인 것은 정상입니다.

## 6. 미측정

- 수동 검토 전환(8회 실패 뒤): 최대 백오프 10분이라 이 실행에서는 만들지 않았습니다. `pg-query-down`을
  10분 이상 유지해야 합니다.
- 복구 시도 횟수 분포(발견 3).
- 은행 쪽 "출금 뒤 응답 끊김"에 정산 지급 경로(`SettlementRecoveryService`)는 시뮬레이터에 없어 재지
  않았습니다. reports/11 F-009가 다룹니다.
- 여러 시나리오를 **동시에** 겹쳤을 때(예: 조회 장애 중 웹훅 중복)의 동작.
