# ParityPay 페이서비스 도메인 용어와 지식 (DOC-17)

> **에이전트 지침**
> - **읽는 시점**: 이 저장소를 처음 볼 때, 용어의 뜻이나 계정·상태 이름이 낯설 때, 사용자 문구를 쓸 때.
> - **이 문서가 정하는 것**: 용어의 뜻과 그것이 이 프로젝트에서 무엇에 대응하는지. **정책은 정하지 않습니다.** 금액·취소·오류 규칙은 DOC-04, 계정·분개는 DOC-07, 상태 전이는 DOC-06이 기준입니다. 이 문서와 기준 문서가 다르면 기준 문서가 맞고 이 문서를 고칩니다.
> - **강제 규칙**: 코드·API·화면·문서에서 같은 뜻에 다른 말을 쓰지 않습니다. 이 문서의 용어를 씁니다. 사용자에게 `UNKNOWN`을 실패로 번역하지 않습니다.

## 1. 페이서비스란 무엇인가

**페이서비스**(간편결제·페이머니 서비스)는 플랫폼이 사용자의 돈을 **미리 받아 두고**(충전), 그 잔액으로
플랫폼 안의 상점에서 결제하게 하며, 나중에 상점에 **모아서 지급**(정산)하는 서비스입니다. 카카오페이머니,
네이버페이 포인트, 토스머니처럼 "충전해서 쓰는 돈"이 그것입니다.

이 구조에서 플랫폼은 세 방향의 돈을 동시에 다룹니다.

```text
사용자 ──충전──▶ 플랫폼 ◀──결제──  사용자
                  │
                  └──정산 지급──▶ 판매자
```

돈이 플랫폼을 **거쳐 가기** 때문에, 플랫폼은 "누구의 돈이 얼마나, 왜, 언제 우리 손에 있는가"를 한
푼도 틀리지 않게 알아야 합니다. 그것을 기록하는 장부가 **원장**이고, 원장이 이 프로젝트의 중심입니다.

### 참여자

| 참여자 | 역할 | 이 프로젝트에서 |
|---|---|---|
| 사용자(고객) | 충전하고 결제하고 취소받습니다 | `member` + `CUSTOMER` 역할, 고객 앱 |
| 판매자(가맹점) | 상품을 팔고 정산을 받습니다 | `merchantId`, `MERCHANT` 역할, 고객 앱의 정산 화면 |
| 플랫폼(우리) | 페이머니를 발행하고 원장을 지키며 정산을 집행합니다 | `pay-api` |
| 은행 | 충전 출금과 정산 지급의 실제 자금이 오가는 곳 | `apps/mock-bank` (별도 프로세스) |
| PG(전자지급결제대행) | 카드 결제를 승인·환불해 주는 중개자 | `apps/mock-pg` (별도 프로세스) |
| 운영자 | 미확정 거래·대사 불일치·보정을 다룹니다 | `OPS_VIEWER`·`OPS_OPERATOR`·`OPS_APPROVER`, 운영 콘솔 |

### 왜 이 도메인이 어려운가

일반 웹 서비스와 다른 점은 **틀리면 돈이 사라지거나 생긴다**는 것입니다. 그리고 틀리는 경로가 정상
경로보다 많습니다.

- 같은 요청이 두 번 도착합니다 (재시도, 연타, 네트워크 재전송)
- 두 요청이 같은 잔액을 동시에 봅니다
- 은행이 출금은 했는데 응답만 잃어버립니다
- 이벤트가 두 번 전달되거나 순서가 바뀝니다
- 프로세스가 커밋 직후·발행 직전에 죽습니다

이 프로젝트의 목표는 정상 결제를 처리하는 것이 아니라 **위 상황에서도 원장이 맞는 것**입니다.
근거: [CLAUDE.md §1](../CLAUDE.md), [reports/12 §1](../reports/12-portfolio-technical-report.md)

### 규제 맥락 (일반 지식)

한국에서 충전형 페이머니는 통상 **선불전자지급수단**으로 분류되며, 발행자는 이용자가 충전한 돈을
자기 돈과 섞지 않고 별도로 관리할 의무를 집니다. 이 프로젝트는 규제를 구현하지 않지만, 원장의 계정
체계가 그 사고방식을 따릅니다 — 사용자가 충전한 돈은 우리 매출이 아니라 **사용자에게 돌려줄 부채**
(`2010 사용자 페이머니`)이고, 은행에 있는 돈은 그 부채를 뒷받침하는 **자산**(`1010 은행 예치금`)입니다.
"매출처럼 보이지만 부채"라는 구분이 이 도메인의 첫 번째 개념입니다.

## 2. 용어 사전

각 항목은 **뜻 → 이 프로젝트에서 → 근거** 순서입니다. 기준 문서가 있는 용어는 그 문서가 정의를
소유합니다.

### 2.1 돈과 지갑

**페이머니 (Pay Money)**
사용자가 플랫폼에 충전해 둔 선불 잔액. 사용자 입장에서는 "내 돈", 플랫폼 입장에서는 **부채**입니다.
→ 원장 계정 `2010 사용자 페이머니`(Liability). 화면의 "페이머니 잔액". → DOC-07 §3

**지갑 (Wallet)**
사용자·통화별로 하나인 페이머니 보관 단위. 상태(`ACTIVE`·`SUSPENDED`·`CLOSED`)와 소유권을 갖습니다.
→ `Wallet` Aggregate, `wallet` 테이블. 회원 가입 시 함께 만들어집니다. → DOC-06 §2, DOC-04 §2

**가용 잔액 (available balance)**
지금 새로 쓸 수 있는 금액. 화면의 큰 숫자가 이것입니다.
→ `wallet_balance.available_amount`. `INV-003`: 0 이상. → DOC-04 §2

**보류 잔액 (pending balance)**
처리 중이라 잠겨 있는 금액. "가용 + 보류 = 원장 잔액"입니다.
→ `wallet_balance.pending_amount`. 화면의 "처리 중 N원". → DOC-07 §6

**잔액 스냅샷 (balance snapshot)**
원장을 매번 더하지 않으려고 따로 유지하는 **파생값**. 진실이 아니며 원장에서 재구축할 수 있어야 합니다.
→ `wallet_balance` 테이블, `INV-010`, 운영자 API `balance-rebuild`. 화면에 "N시 기준"이 붙는 이유가
이것입니다(FE-005). → [ADR-008](adr/008-ledger-balance-snapshot.md), DOC-14 FE-005

**금액 (Money)**
KRW 원 단위 **양의 정수**. 방향은 부호가 아니라 `DEBIT`/`CREDIT`으로 표현합니다. `float`·`double` 금지.
→ `Money(amount, currency)` 값 객체, DB `BIGINT`. 수수료율도 만분율(basis point) 정수입니다. → DOC-04 BR-001

**한도 (limit)**
일·월 충전 한도 등 설정값. 초과는 `422 LIMIT_EXCEEDED`.
→ DOC-04 §3·§10

### 2.2 충전 · 결제 · 취소

**충전 (Top-up)**
사용자의 은행 계좌에서 돈을 출금해 페이머니로 바꾸는 것. 외부(은행)를 부르므로 결과를 모를 수 있습니다.
→ `TopUp` Aggregate, `POST /api/v1/top-ups`, 상태 `REQUESTED → PROCESSING → SUCCEEDED | FAILED | UNKNOWN`.
분개 JE-001. → DOC-06 §4, DOC-07 JE-001

**계좌 연결 (bank account link)**
충전에 쓸 은행 계좌를 등록하는 것. 금융 효과가 없어 멱등 키를 요구하지 않습니다. 계좌번호 원문은
화면에도 로그에도 남기지 않습니다. → `POST /api/v1/bank-accounts`

**결제 (Payment)**
주문 대금을 지불하는 것. 이 프로젝트에는 두 종류가 있고 **회계적으로 다릅니다.**

| | 페이머니 결제 (`PAY_MONEY`) | 외부 PG 결제 (`EXTERNAL_PG`) |
|---|---|---|
| 돈이 나가는 곳 | 사용자 페이머니(우리 부채) | 사용자의 카드(우리 밖) |
| 외부 호출 | 없음 — 한 DB 트랜잭션으로 끝 | PG 승인 호출 — 결과를 모를 수 있음 |
| 분개 | JE-003: 부채가 사용자→판매자로 **이전** | JE-013: PG 미수금 자산과 판매자 부채가 **함께 증가** |
| 미확정 | 생길 수 없음 | `UNKNOWN` 가능, 복구 작업 대상 |

→ `Payment` Aggregate, `POST /api/v1/payments`. → DOC-04 §4, DOC-07 JE-003·JE-013

**승인 (approval)**
결제가 금융적으로 확정된 것. `APPROVED`는 취소가 가능한 확정 상태입니다. "승인액"(`approvedAmount`)이
취소 가능액 계산의 기준입니다. → DOC-06 §4

**주문 (Order)**
결제의 맥락(무엇을 샀는가). **백엔드에 주문 엔티티가 없습니다.** `orderId`는 클라이언트가 만들어
결제에 실어 보내는 문자열이고, 주문 상태(배송 중·구매확정)는 고객 앱의 브라우저 저장소에 있습니다.
주문 상태와 결제 상태가 서로 다른 시스템에 있다는 것이 의도입니다. → DOC-15 §2, `apps/web-customer/src/shop/orders.ts`

**취소 (Cancellation)**
승인된 결제의 전부 또는 일부를 되돌리는 것. 원결제를 참조하는 **독립 Aggregate**이며 자기 멱등 키와
상태를 가집니다. 전액이면 결제는 `CANCELED`, 일부면 `PARTIALLY_CANCELED`.
→ `PaymentCancellation`, `POST /api/v1/payments/{id}/cancellations`, 분개 JE-004. → DOC-04 §6

**부분 취소 (partial cancellation)**
승인액보다 작은 금액의 취소. 여러 번 할 수 있으므로 **동시에 들어오면 합이 승인액을 넘을 수 있습니다.**
그래서 요청 시점에 금액을 **예약**합니다(아래 "취소 가능액"). → `INV-005`

**취소 가능액 (cancellable amount)**
`승인액 − 완료된 취소액 − 처리 중 취소액`. 요청 시 처리 중 금액을 먼저 올려 두고(예약), 완료되면 완료
금액으로 옮기고, 실패하면 예약을 풉니다. **결과를 모르면 풀지 않습니다** — 풀면 이미 나간 환불을 다시
보낼 수 있게 됩니다. 화면 값은 조회 시점의 것이라 제출 때는 다를 수 있고, 그래서
`CANCELLATION_AMOUNT_EXCEEDED`는 버그가 아니라 정상 결과입니다(FE-006).
→ `CancellationCapacity` 값 객체, `processingCancellationAmount`. → DOC-04 §6, DOC-14 FE-006

**환불 (refund)**
취소의 결과로 돈이 사용자에게 돌아가는 것. **결제한 곳으로 돌아갑니다** — 페이머니 결제는 페이머니로
(JE-004), 카드 결제는 카드로(JE-014). 카드 결제를 페이머니로 환불하면 사용자는 카드 청구를 진 채
페이머니를 받고 우리 부채는 두 번 생깁니다. 이 저장소에서 "취소"는 요청·상태를, "환불"은 그 결과로
돈이 돌아가는 방향을 말합니다. → DOC-04 §4·§6, DOC-07 JE-014

**구매확정 (order confirmation)**
사용자가 물건을 받았다고 확정하는 것. 이때부터 그 결제가 **정산 대상**(`ELIGIBLE`)이 됩니다. 결제 승인
즉시 판매자에게 지급하지 않는 이유가 여기 있습니다 — 반품·취소가 아직 가능하기 때문입니다.
→ `POST /api/v1/payments/{id}/confirmation`, 이벤트 `OrderConfirmed`. → DOC-04 §8

**송금·출금 (transfer · withdrawal)**
사용자 간 페이머니 이동(JE-005), 페이머니를 은행 계좌로 돌려보내기(JE-006). 정책과 분개는 정의되어
있으나 **MVP 구현 범위 밖**입니다. → DOC-03, DOC-04 §7

### 2.3 회계와 원장

이 절이 가장 낯설 수 있습니다. 코드에서 `DEBIT`/`CREDIT`을 볼 때마다 여기로 돌아오면 됩니다.

**이중부기 (double-entry bookkeeping)**
모든 거래를 **두 계정에 같은 금액으로** 기록하는 회계 방식. 한쪽은 차변, 다른 쪽은 대변이고 항상
차변 합계 = 대변 합계입니다. 돈이 "어디서 와서 어디로 갔는지"가 매 거래에 남기 때문에, 합이 안 맞으면
어딘가 틀렸다는 것을 **구조적으로** 알 수 있습니다. 단식부기(잔액만 더하고 빼기)로는 틀린 것을
나중에 알 수 없습니다. → [ADR-003](adr/003-double-entry-ledger.md), `INV-001`

**차변 · 대변 (Debit · Credit)**
거래의 두 방향. 뜻은 "빼기/더하기"가 아니라 **계정 종류에 따라 다릅니다.**

| 계정 분류 | 차변(DEBIT)이면 | 대변(CREDIT)이면 | 정상 잔액 |
|---|---|---|---|
| 자산 (Asset) | 증가 | 감소 | 차변 |
| 부채 (Liability) | 감소 | 증가 | 대변 |
| 수익 (Revenue) | 감소 | 증가 | 대변 |
| 비용 (Expense) | 증가 | 감소 | 차변 |

예: 충전 100,000원 → 은행 예치금(자산) 차변 100,000 = 자산 증가, 사용자 페이머니(부채) 대변 100,000 =
부채 증가. 이 문서와 원장의 차변·대변은 **플랫폼 법인의 관점**입니다. → DOC-07 §2

**계정 (Account)**
돈이 분류되는 서랍. 코드와 분류, 정상 잔액, 소유자 차원(어느 사용자·판매자·기관의 것인가)을 가집니다.
MVP 필수 계정은 셋입니다.

| 코드 | 계정 | 분류 | 무엇인가 |
|---|---|---|---|
| 1010 | 은행 예치금 | 자산 | 우리 법인 은행 계좌에 실제로 있는 돈 |
| 2010 | 사용자 페이머니 | 부채 | 사용자에게 돌려줄 의무 (사용자·지갑별) |
| 2030 | 판매자 지급예정금 | 부채 | 판매자에게 정산해 줄 의무 (판매자별) |

그 밖에 `1020 PG 미수금`(PG에게 받을 돈), `1030 판매자 미수금`(정산 후 환불로 판매자에게 되받을 돈),
`4010 플랫폼 수수료 수익`, `9010 정산 조정 계정` 등이 있습니다. → `LedgerAccount`, DOC-07 §3

**원장 (Ledger)**
계정·거래·항목의 전체. ParityPay에서 **돈의 진실은 원장 하나**이고 잔액·정산·화면은 전부 그 파생입니다
(system of record). → `modules/ledger`, [ADR-002](adr/002-postgresql-system-of-record.md)

**원장 거래 (Ledger Transaction) · 분개 (Journal Entry)**
한 업무 사건이 만드는 원장 기록 하나. 항목(entry) 여러 줄로 이뤄지고 차변 합 = 대변 합입니다. 카탈로그의
`JE-001`(충전)처럼 **어떤 업무가 어떤 계정을 어느 방향으로 움직이는지**를 미리 정해 둔 것이 분개
카탈로그이고, 카탈로그에 없는 분개는 코드에서 만들지 않습니다. → `LedgerTransaction`, `JournalFactory`, DOC-07 §5

**원장 항목 (Ledger Entry)**
원장 거래의 한 줄: 계정 + 방향 + 양의 금액. `INV-002`: 금액 > 0. 음수로 방향을 표현하지 않습니다.
→ `LedgerEntry`, `JournalLine`

**전기 (posting)**
분개를 원장에 확정 기록하는 것. `DRAFT → POSTED`. POSTED 뒤에는 UPDATE·DELETE가 없습니다(`INV-006`,
DB 트리거로도 막음). → DOC-07 §7

**참조 (reference)**
원장 거래가 가리키는 업무 사건: `referenceType`(TOP_UP·PAYMENT·CANCELLATION·SETTLEMENT…) +
`referenceId`. 원장 모듈은 다른 업무 모듈을 모르고 이 둘만 저장합니다. `referenceType + referenceId +
transactionType` 유니크 제약이 **같은 사건이 두 번 전기되는 것을 막는 마지막 방어선**입니다(`INV-004`).
→ DOC-05 §5, DOC-07 §4

**역분개 (reversal)**
확정된 거래를 되돌릴 때 원문을 고치지 않고 **반대 방향의 새 거래**를 추가하는 것. 원거래는
`REVERSED`로 표시되고 `reversal_of_transaction_id`로 연결됩니다. 취소가 역분개입니다.
→ [ADR-009](adr/009-reversal-adjustment.md), JE-002·JE-004

**보정 분개 (adjustment)**
대사에서 발견된 오류를 바로잡는 **새 분개**. 금액을 고치는 것이 아니라 차변·대변 계정을 지정한 거래를
추가합니다. 요청자와 승인자가 달라야 하고(이중 승인), 사유가 필수이며, 제출 직전에 비밀번호를 다시
묻습니다(재인증). → JE-012, 운영 콘솔 "보정 분개 요청", DOC-14 FE-010·FE-014

**조정 계정 (clearing account)**
차이를 잠시 담아 두는 계정(`9010`). **차이를 숨기는 곳이 아닙니다** — 해소 계획과 만료 경보가 있어야
합니다. 원장 불균형을 조정 계정으로 은폐하지 않습니다. → CLAUDE.md §3, DOC-07 JE-012

**원장 잔액 (ledger balance)**
계정의 항목을 다 더한 값. 부채 계정은 `대변 합 − 차변 합`. `INV-010`: 스냅샷과 같은 컷오프에서 같아야
합니다. → DOC-07 §6

**균형 (balanced)**
한 원장 거래의 차변 합 = 대변 합. 운영 콘솔 원장 상세의 "차변 = 대변" 배너가 이것이고, 값은 서버가
계산합니다(화면이 다시 더하지 않음). → `INV-001`

### 2.4 정산

**정산 (Settlement)**
일정 기간 동안 판매자에게 줄 돈을 **집계해 확정**하는 것. 승인 즉시 지급하지 않고 구매확정된 것만
모읍니다. → `Settlement` Aggregate, `modules/settlement`

**정산 항목 (settlement item)**
정산에 포함된 결제 하나하나의 근거: 매출(`SALE`, +), 취소(`CANCELLATION`, −), 수수료(`FEE`, −),
조정(`ADJUSTMENT`). **원장이 아니므로 부호가 있습니다.** `INV-008`: 항목 합 = 헤더 순액. 고객 앱의
정산 화면이 항목을 합계 옆에 두고 둘이 같은지 보여 주는 이유입니다. → DOC-06 §2, `Settlements.tsx`

**총액 · 순액 (gross · net)**
총액 = 승인액 합. 순액 = `승인액 − 취소액 − 플랫폼 수수료 − 조정액`. 판매자가 실제로 받는 돈은 순액.
→ DOC-04 §8

**플랫폼 수수료 (platform fee)**
플랫폼이 판매자에게서 떼는 몫. 판매자 지급예정금을 줄이고 수수료 수익을 인식합니다(JE-007). 비율은
만분율 정수(`fee-basis-points: 1000` = 10%). → DOC-07 JE-007

**지급 (payout)**
확정된 순액을 은행을 통해 판매자에게 보내는 것. 외부 호출이므로 `UNKNOWN`이 생길 수 있고, 응답이
유실되면 **재지급이 아니라 조회**로 확정합니다. `INV-009`: 지급 완료 정산은 외부 지급 참조를 가집니다.
→ 상태 `PAYING → PAID | FAILED | UNKNOWN`, JE-008

**보류 (HELD)**
분쟁·위험·계좌 오류로 지급을 멈춘 정산. 풀리면 `ELIGIBLE`로 돌아갑니다. → DOC-06 §4

**정산 후 환불**
이미 판매자에게 지급한 결제가 취소되면 지급예정금이 없으므로 **판매자 미수금**(자산)으로 기록하고
다음 정산에서 차감합니다(JE-009). 지급한 정산을 고치지 않습니다. → DOC-04 §8, JE-009

### 2.5 대사

**대사 (Reconciliation)**
우리 기록과 **외부 기록**(은행 출금 명세, PG 승인 명세, 지급 명세)을 맞춰 보는 것. 매일 새벽 4시에
돌며, 외부 명세를 **받지 못하면 그 회차를 멈춥니다** — 빈 명세로 진행하면 우리 기록 전부가 불일치로
올라갑니다. → `modules/reconciliation`, `ReconciliationJob`, DOC-04 §9, DOC-05 §10

**불일치 (mismatch)**
대사가 찾은 차이. 여섯 종류로 분류합니다.

| 유형 | 뜻 |
|---|---|
| `INTERNAL_ONLY` | 우리에겐 있는데 외부에는 없음 |
| `EXTERNAL_ONLY` | 외부에는 있는데 우리에겐 없음 — 자동 보정하지 않음 |
| `STATUS_MISMATCH` | 양쪽 다 있지만 상태가 다름 |
| `AMOUNT_MISMATCH` | 금액이 다름 — 자동 보정하지 않음 |
| `DUPLICATE` | 같은 참조가 여러 번 |
| `LEDGER_MISSING` | 업무 기록은 있는데 원장 전기가 없음 |

`MATCHED`는 불일치가 아니라 일치입니다. 단순 지연으로 설명되는 차이는 `delay-tolerance`(30분) 안에서
보류합니다. → `ReconciliationMatcherTest`, DOC-04 §9

**명세 (statement)**
외부기관이 내주는 기간별 거래 목록. 건별 조회 API와 **다른 시스템**입니다 — "건별 조회는 되는데 일별
명세가 안 나오는" 날이 대사에는 더 위험합니다. → DOC-05 §10

### 2.6 신뢰성 — 이 프로젝트가 진짜로 다루는 것

**멱등성 (idempotency)**
같은 요청을 몇 번 보내도 효과가 한 번인 성질. `INV-004`. 세 겹으로 지킵니다.

1. `Idempotency-Key` 헤더 — 범위는 `principalId + operation + key`. 같은 키·같은 본문이면 저장된 응답,
   같은 키·다른 본문이면 `409 IDEMPOTENCY_KEY_REUSED`
2. 업무 유니크 제약 — 같은 주문의 결제, 같은 외부 참조
3. 원장 유니크 제약 — `referenceType + referenceId + transactionType`

→ `idempotency_record`, DOC-04 §5, DOC-09 §3

**의도 (intent)** — 클라이언트 쪽 멱등성
"이 주문을 결제한다"처럼 사용자가 하려는 일 하나. 클라이언트는 **의도마다 키 하나**를 만들어 브라우저
저장소에 두고, 그 의도가 끝날 때까지 재시도에 같은 키를 씁니다. 재시도마다 새 키를 만들면 서버의
멱등성이 무의미해집니다 — 서버는 그것을 다른 요청으로 봅니다. 결제 버튼 연타가 승인 한 번인 것은
버튼을 잠가서가 아니라 키가 같아서입니다. → `useSettlingWrite`, `intentStore`, DOC-14 FE-001

**UNKNOWN (미확정)**
외부에 요청을 보냈는데 **결과를 모르는** 상태. 타임아웃·연결 끊김·5xx가 전부 여기로 모입니다. 실패가
아닙니다 — 은행이 출금을 했는지 안 했는지 모르는 것이고, 실패로 답하면 클라이언트가 재시도해 **이중
출금**이 됩니다. API는 `202 RESULT_PENDING`과 조회 위치를 돌려주고, 복구 작업이 **조회로만** 확정합니다.
화면 문구는 "결과 확인 중", 색은 보라(빨강 아님). → [ADR-007](adr/007-unknown-state.md), DOC-14 FE-002, ADR-012

**복구 (recovery)**
`UNKNOWN`을 최종 상태로 수렴시키는 백그라운드 작업. 외부에 **다시 요청하지 않고 상태를 조회**합니다.
"없음"이 연속 3회 확인되어야 `FAILED`로 봅니다(`not-found-confirm-threshold`). 운영자의 "외부 상태
다시 조회" 버튼도 조회를 앞당길 뿐 결과를 고르지 않습니다. → `TopUpRecoveryService`·`PaymentRecoveryService`·`CancellationRecoveryService`, DOC-09 §7·§8

**타임아웃 ≠ 실패**
이 저장소의 절대 규칙. 외부 호출 타임아웃은 `UNKNOWN`입니다. → CLAUDE.md §3

**Transactional Outbox**
DB에 업무 변경과 함께 **이벤트 발행 의도**를 같은 트랜잭션으로 저장하고, 별도 발행기가 브로커로
보내는 패턴. DB와 브로커에 따로 쓰면(이중 쓰기) 둘 사이에서 죽었을 때 한쪽만 남습니다.
→ `outbox_event`, `OutboxPublisher`, [ADR-005](adr/005-transactional-outbox.md)

**at-least-once · 멱등 소비자**
브로커는 메시지를 **최소 한 번** 전달합니다(두 번일 수 있음). 그래서 소비자는 `consumed_event`의
`eventId` 유니크 제약으로 두 번째를 버립니다. "정확히 한 번"은 전달이 아니라 **효과**의 성질입니다.
→ [ADR-006](adr/006-at-least-once-idempotent-consumer.md)

**파티션 키 · Aggregate 순서**
같은 결제의 승인과 취소는 순서대로 소비되어야 합니다. 토픽은 하나(`paritypay.events`)이고 파티션 키가
Aggregate ID입니다. 발행기가 여러 대면 브로커에 넣는 순서가 흔들리므로, 선점 쿼리가 **키마다 가장
앞선 미발행 이벤트 하나만** 집어갑니다. → DOC-05 §9, 결함 F

**프로젝션 (projection)**
이벤트를 소비해 만든 조회용 데이터. 거래내역 목록이 그것이고, 결제가 201로 끝난 직후에도 **아직 없을
수** 있습니다. 화면은 그 사이를 "반영 중"으로 표시합니다. → `wallet_transaction` 테이블(소비자가 채움), DOC-14 FE-004

**조건부 갱신 (conditional update)**
`UPDATE ... WHERE available_amount >= :amount AND version = :v`. 갱신 행이 0이면 잔액 부족 또는 경합.
잔액을 먼저 읽고 나중에 빼면 두 요청이 같은 잔액을 봅니다. → [ADR-004](adr/004-atomic-balance-update.md)

**웹훅 (webhook)**
기관이 결과를 **먼저** 알려 주는 경로. 인증 토큰 없이 열린 유일한 쓰기 경로라 서명·시각 허용 오차·
`webhook_receipt` 유니크로 중복을 막고, 오래된 이벤트는 상태 전이 규칙이 거부합니다. → DOC-09 F-008

**단일 비행 (single-flight)**
같은 일이 동시에 여러 번 일어나지 않게 하나로 합치는 것. 액세스 토큰 재발급이 그렇습니다 — 탭 여러
개가 동시에 만료를 만나면 재발급은 한 번만 나가야 합니다. 리프레시 토큰은 1회용이라 두 번 나가면
하나는 실패하고 세션이 끊깁니다. → DOC-14 FE-008

### 2.7 인증과 운영

**액세스 토큰 · 리프레시 토큰**
액세스 토큰은 짧은 수명의 JWT로 **메모리에만** 있고, 리프레시 토큰은 `HttpOnly`·`Secure`·`SameSite=Lax`
쿠키로 `/api/v1/auth` 경로에만 실립니다. 새로고침하면 앱이 쿠키로 다시 받습니다. 원문은 저장하지 않고
해시만 남깁니다. → [ADR-010](adr/010-refresh-token-cookie.md)

**역할 (role)**
`CUSTOMER`, `MERCHANT`, `OPS_VIEWER`, `OPS_OPERATOR`, `OPS_APPROVER`. 운영 콘솔은 `OPS_*`가 있어야
들어가고, 정산 화면은 `MERCHANT`에만 보입니다. → `SecurityConfig`

**이중 승인 (dual approval)**
원장을 움직이는 운영 작업(보정 분개)은 요청자와 승인자가 달라야 합니다. 서버가 막고 화면도 미리 막습니다.
→ DOC-14 FE-010

**재인증 (re-authentication)**
세션이 살아 있어도 위험한 작업 직전에 비밀번호를 다시 묻는 것. 5분짜리 증거(`X-Reauth-Token`)를 받아
요청 한 번에 쓰고 버립니다. → `POST /api/v1/auth/reauth`, DOC-14 FE-014

**타임라인 (timeline)**
한 거래에 관련된 모든 기록(결제·취소·원장·이벤트·기관 조회)을 시간순으로 늘어놓은 운영 조회. 기관을
못 부르면 그 부분만 `UNAVAILABLE`로 표시하고 나머지는 보여 줍니다. → 운영 콘솔 "거래 검색", DOC-15 §4.2

**감사 로그 (audit log)**
운영자가 무엇을 왜 했는지의 기록. 재조회·보정에는 사유가 필수입니다. → `audit_log`

**불변조건 (invariant)**
어떤 상황에서도 참이어야 하는 금융 조건 `INV-001`~`INV-010`. DB 제약·트리거·테스트·지표
(`paritypay.invariant.*`, 평소 0)로 지킵니다. 0이 아니면 임계치 없이 즉시 경보입니다. 운영 콘솔의
불변조건 카드는 **값이 없으면 "정상"이 아니라 "확인하지 못함"**입니다. → CLAUDE.md §2, DOC-04 §11

## 3. 돈의 흐름을 따라 읽기

용어를 한 줄에 꿰는 예시입니다. 사용자 A가 100,000원을 충전하고 판매자 M의 30,000원 상품을 산 뒤
10,000원을 부분 취소하고 구매확정하며, 수수료는 10%입니다. 표는 각 단계 **뒤**의 계정 잔액입니다.

| 단계 | 분개 | 은행 예치금 (자산) | A 페이머니 (부채) | M 지급예정금 (부채) | 수수료 수익 |
|---|---|---:|---:|---:|---:|
| 충전 100,000 | JE-001: 예치금 Dr / A페이머니 Cr | 100,000 | 100,000 | 0 | 0 |
| 결제 30,000 | JE-003: A페이머니 Dr / M지급예정 Cr | 100,000 | 70,000 | 30,000 | 0 |
| 부분 취소 10,000 | JE-004: M지급예정 Dr / A페이머니 Cr | 100,000 | 80,000 | 20,000 | 0 |
| 구매확정 | 분개 없음 — 정산 대상이 됨 | 100,000 | 80,000 | 20,000 | 0 |
| 수수료 2,000 (10%) | JE-007: M지급예정 Dr / 수수료수익 Cr | 100,000 | 80,000 | 18,000 | 2,000 |
| 정산 지급 18,000 | JE-008: M지급예정 Dr / 예치금 Cr | 82,000 | 80,000 | 0 | 2,000 |

마지막 줄을 보면 **자산 82,000 = 부채 80,000 + 수익 2,000**입니다. 매 단계에서 차변 합 = 대변 합이었기
때문에 끝에서도 맞습니다. 결제 단계에서 은행 예치금이 움직이지 않은 것에 주목하세요 — 페이머니
결제는 돈이 우리 밖으로 나가는 것이 아니라 **누구에게 줄 의무인지가 바뀌는 것**입니다.

같은 흐름을 화면에서 보면: 고객 앱 잔액 카드가 100,000 → 70,000 → 80,000으로 바뀌고(스냅샷, 기준
시각 표시), 거래내역에 "+100,000 / −30,000 / +10,000" 세 줄이 프로젝션으로 따라오며, 판매자의
정산 화면에는 매출 30,000 · 취소 −10,000 · 수수료 −2,000 · 순액 18,000이 항목으로 나옵니다.

| Payment | `READY` `PROCESSING` `APPROVED` `PARTIALLY_CANCELED` `CANCELED` `FAILED` `UNKNOWN` | 준비 / 처리 중 / 승인 / 일부 취소 / 전액 취소 / 실패 / 결과 모름 |
| Cancellation | `REQUESTED` `PROCESSING` `COMPLETED` `FAILED` `UNKNOWN` | 예약됨 / 환불 호출 중 / 완료 / 실패(예약 해제) / 결과 모름(예약 유지) |
| Settlement | `PENDING` `ELIGIBLE` `CALCULATED` `HELD` `PAYING` `PAID` `FAILED` `UNKNOWN` | 대기 / 지급 가능 / 집계 확정 / 보류 / 지급 중 / 지급 완료 / 실패 / 결과 모름 |
| LedgerTransaction | `DRAFT` `POSTED` `REVERSED` | 작성 중 / 확정(불변) / 역분개 연결됨 |
| Outbox event | `PENDING` `PUBLISHED` `FAILED` | 미발행 / 발행됨 / 포기(운영자 재처리) |
| Idempotency | `PROCESSING` `COMPLETED` `FAILED` `RECOVERY_REQUIRED` | 처리 중 / 응답 저장됨 / 확정 실패 / 복구 필요 |

허용되는 전이는 [DOC-06 §4·§5](06-domain-state-design.md)만이 기준입니다.

## 5. 자주 헷갈리는 쌍

| 이것 | 저것 | 차이 |
|---|---|---|
| 취소 | 환불 | 취소는 요청과 상태, 환불은 그 결과로 돈이 돌아가는 방향. 카드 결제 환불은 페이머니로 오지 않습니다 |
| `UNKNOWN` | `FAILED` | 모름 vs 확실히 안 됨. UNKNOWN에서 재시도하면 이중 출금, FAILED에서 재시도는 안전 |
| 승인 | 완료 | 결제는 승인(`APPROVED`)이 확정 상태. 충전·취소·정산은 완료(`SUCCEEDED`·`COMPLETED`·`PAID`) |
| 가용 잔액 | 원장 잔액 | 가용은 스냅샷이고 보류를 뺀 값. 원장 잔액은 항목의 합. `가용 + 보류 = 원장` |
| 정산 | 지급 | 정산은 얼마를 줄지 확정하는 것, 지급은 실제로 보내는 것. 지급만 외부 호출입니다 |
| 대사 | 원장 검증 | 대사는 외부 기록과 비교, 원장 검증(`GET /wallets/{id}/ledger-verification`)은 우리 원장과 우리 스냅샷을 비교 |
| 멱등 키 | 업무 유니크 | 키는 첫 방어선(클라이언트가 줌), 유니크는 마지막 방어선(DB가 지킴). 둘 다 있어야 합니다 |
| 역분개 | 보정 분개 | 역분개는 원거래를 정확히 되돌림(취소), 보정은 대사 오류를 바로잡는 임의 계정의 새 분개(운영자) |
| 이벤트 | 명령 | 이벤트는 일어난 사실(`PaymentApproved`), 명령은 해 달라는 요청(`ApprovePayment`). 토픽에는 사실만 흐릅니다 |
| 주문 상태 | 결제 상태 | 주문은 클라이언트(배송 중·구매확정), 결제는 서버(`APPROVED`…). 다른 시스템이 가지므로 같은 값일 수 없습니다 |
