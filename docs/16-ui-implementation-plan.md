# ParityPay UI 구현 계획서 (DOC-16)

> **에이전트 지침**
> - **읽는 시점**: UI를 실제로 만들기 시작할 때, 다음에 무엇을 할지 정할 때.
> - **이 문서가 정하는 것**: [DOC-15](15-ui-screen-plan.md)가 원하는 것과 백엔드가 지금 줄 수 있는 것의 격차, 그 격차를 메우는 순서, 마일스톤별 완료 기준.
> - **이 문서가 정하지 않는 것**: 화면 내용(DOC-15), 클라이언트 계약(DOC-14).
> - **강제 규칙**: 백엔드 API가 없는 화면을 "곧 생길 것"으로 가정하고 만들지 않습니다. 없으면 이 문서에 신규 API로 적고, 그 API를 만드는 것이 같은 마일스톤에 들어갑니다.

## 1. 세 문서의 역할

| 문서 | 답하는 질문 |
|---|---|
| DOC-15 UI 화면 계획 | **무엇을** 보여줄 것인가 |
| DOC-14 프론트엔드 설계서 | 클라이언트가 **무엇을 지켜야** 하는가, 앱을 **어떻게 나눌** 것인가 |
| **DOC-16 (이 문서)** | 그중 **무엇이 가능하고**, **어떤 순서로** 만들 것인가 |

DOC-15는 하고 싶은 것을 적은 문서입니다. 좋은 문서지만 **상당수가 아직 없는 API를 전제합니다.**
그 사실을 먼저 확인하지 않고 화면부터 만들면, 절반쯤 만들고 나서 막힙니다.

## 2. 격차 분석 — DOC-15가 요구하는 것 vs 백엔드 현황

2026-09-10에 코드를 직접 확인한 결과입니다.

### 2.1 지금 바로 만들 수 있는 것 (백엔드 변경 없음)

| DOC-15 화면 | 쓰는 API |
|---|---|
| 1.1 홈·지갑 (가용/처리중 잔액) | `GET /wallets/me` |
| 1.2 페이머니 충전 + 3분기 결과 | `POST /top-ups`, `GET /top-ups/{id}` |
| 1.3 거래내역 (커서) | `GET /wallets/{id}/transactions` |
| 1.4 거래 상세 | `GET /payments/{id}` |
| 1.5 결제창 | `POST /payments` |
| 1.6 취소·환불 (부분 취소 계산) | `POST /payments/{id}/cancellations`, `cancellableAmount` |
| 2. 테스트 커머스 (상품·주문·주문내역) | 상품은 **프론트 고정 데이터**, 주문 ID는 클라이언트가 생성 |
| 4.2 통합 거래 검색 (일부 식별자) | `GET /admin/transactions/{referenceId}/timeline` |

### 2.2 백엔드 API가 필요한 것

| DOC-15 요구 | 현황 | 필요한 것 |
|---|---|---|
| 4.4 **원장 탐색기** (차변/대변 표) | `ledger` 모듈에 **REST 컨트롤러가 없습니다.** 타임라인이 원장 "요약 줄"만 보여 줍니다 | `GET /admin/ledger/transactions/{id}` — 항목별 차변·대변·계정·균형 |
| 5.4 **불변조건 모니터** | `paritypay.invariant.*`가 **Prometheus 지표로만** 나갑니다 | `GET /admin/invariants` — 지표 캐시를 JSON으로 |
| 4.2 통합 검색 (10종 식별자) | 5종만 됩니다: `topUpId`·`paymentId`·`orderId`·`cancellationId`·원장 `reference_id` | `eventId`·`walletId`·`memberId`·외부 거래번호 추가 |
| 4.6 소비자별 처리 상태 | `consumed_event` 테이블은 있지만 **조회 API가 없습니다** | 이벤트 상세에 소비자별 소비 여부 |
| 3.3 정산 상세 (주문 단위 근거) | `SettlementResponse`는 **합계 금액만** 줍니다 | `settlement_item` 목록 노출 |
| 5.1 웹훅 중복·역순 시나리오 | `mock-pg`에 `WebhookMode`(DUPLICATE·OUT_OF_ORDER·NONE)가 **있지만** pay-api의 모드 API가 이 값을 전달하지 않습니다 | `MockPgModeRequest`에 `webhookMode` 추가 |

### 2.3 만들지 않는 것 (백엔드에 개념이 없음)

**없는 것을 화면으로 만들면 거짓말이 됩니다.** 아래는 범위에서 뺍니다.

| DOC-15 요구 | 왜 빼는가 |
|---|---|
| 결제 PIN | 인증은 서명된 토큰으로 합니다(Phase 7). PIN이라는 개념이 없고, 만들면 **보안 장치인 척하는 장식**이 됩니다 |
| 송금·출금 버튼 | DOC-03이 MVP 제외로 정한 기능이고 구현도 없습니다. 눌리지 않는 버튼을 두지 않습니다 |
| 일일·월간 한도 안내 | `LIMIT_EXCEEDED`는 **로그인 실패 잠금**에만 쓰입니다. 금액 한도 정책·API가 없습니다 |
| 이번 달 충전·결제 합계 | 집계 API가 없습니다. 클라이언트가 커서를 끝까지 넘겨 더하는 것은 틀린 방법입니다 |
| 거래 후 잔액 | `wallet_transaction`에 그 컬럼이 없습니다. 클라이언트가 역산하면 동시 거래에서 틀립니다 |
| 5.1 응답 N초 지연 주입 | 기관에 지연 주입 기능이 없습니다. 타임아웃 시나리오로 이미 같은 경로를 덮습니다 |
| 5.1 발행기·소비자 중단 | 프로세스를 죽이는 실험은 `load-tests/`가 하고 있습니다. 웹 버튼으로 끄는 스위치는 **운영 콘솔에 두면 위험한 기능**입니다 |
| 4.5 담당자 지정·자동 복구 일시 중지·메모 | 상태 모델과 감사 경로를 새로 만들어야 합니다. 지금 필요성이 증명되지 않았습니다 |
| 4.8 보정 분개 `DRAFT→REQUESTED→APPROVED` 상태 기계 | 현재는 **요청과 승인이 한 번의 호출**입니다(요청자≠승인자 강제). 상태 기계를 넣는 것은 워크플로 재설계이며 별도 결정입니다 |
| 4.2 멱등성 키 해시·Trace ID 검색 | 멱등 키는 **개인정보에 준해 다루는 값**입니다. Trace ID 검색은 트레이스 백엔드(Jaeger)의 일이며 이미 있습니다 |

## 3. 앱 구성

DOC-14는 앱을 **고객 앱**과 **운영 콘솔** 둘로 나눴습니다. DOC-15가 Shop과 Lab을 더했습니다.
넷을 각각 배포하지 않고 **둘로 유지합니다.**

| 앱 | 담는 영역 | 이유 |
|---|---|---|
| `apps/web-customer` | **Shop** + **My Pay** + Merchant | 같은 사람이 쓰고, 같은 토큰을 쓰고, Shop은 결제창의 맥락을 만드는 껍데기입니다 |
| `apps/web-ops` | **Operations** + **Lab** | Lab은 기관 장애를 주입합니다. 고객 브라우저로 그 코드가 내려가면 안 됩니다 |

**Lab을 운영 콘솔에 두는 것은 타협이 아니라 판단입니다.** 장애 주입은 `OPS_OPERATOR` 권한이
필요하고, 관찰 대상(타임라인·원장·Outbox·불변조건)이 전부 운영 콘솔에 있습니다. 따로 떼면 같은
화면을 두 번 만들게 됩니다.

## 4. 마일스톤

각 마일스톤은 **백엔드 변경 + 프론트엔드 화면 + 시험**을 함께 담습니다. 화면만 만들고 API를
다음으로 미루지 않습니다.

### FE-M2 · 충전과 결제 (백엔드 변경 없음)

DOC-14의 FE-001~003 상태 기계가 처음으로 실제로 쓰입니다.

- SCR-05 충전, SCR-06 결제창, 결과 3분기(완료·실패·**확인 중**)
- 멱등 키 재사용, 202 폴링(2초 간격·90초 한계, M-011 측정값)
- 장애 주입으로 202 경로를 **E2E로** 확인
- **완료 기준**: 결제 버튼을 연속으로 눌러도 승인이 1건. 응답을 유실시켜도 화면이 "실패"라고
  말하지 않고, 복구가 확정한 결과를 보여 줍니다

### FE-M3 · Shop과 거래내역

- 상품 목록·주문서·주문 완료·주문내역 (상품은 프론트 고정 데이터)
- **주문 상태와 결제 상태를 분리해 표시** — DOC-15가 짚은 핵심입니다
- SCR-07 취소(부분 취소 계산), SCR-08 거래내역(커서·"반영 중" 표시)
- **완료 기준**: 한 주문이 결제 → 부분 취소 → 구매확정까지 흐르고, 거래내역 지연이 화면에서 거짓말을 하지 않습니다

### FE-M4 · 운영 콘솔 기본 + 검색 식별자 확장

- **백엔드**: 타임라인 검색에 `walletId`·`memberId`·`eventId` 추가
- OPS-01 통합 거래 검색·타임라인, OPS-02 미확정 목록, OPS-03 재조회
- **완료 기준**: 고객이 어떤 식별자를 들고 와도 하나의 입력으로 사고 하나를 끝까지 추적

### FE-M5 · 원장 탐색기 (백엔드 신규 API)

- **백엔드**: `GET /admin/ledger/transactions/{id}` — 항목별 차변·대변, 계정, 균형 여부, 역분개 연결
- 원장 거래 상세 화면. **수정 버튼은 없습니다**(API도 없습니다)
- 결제 상세에서 `ledgerTransactionId`를 눌러 이동
- **완료 기준**: 결제 한 건에서 원장까지 클릭으로 도달하고, 차변 합계 = 대변 합계가 화면에 보입니다

### FE-M6 · Lab 장애 시뮬레이터 + 불변조건 모니터

- **백엔드**: `GET /admin/invariants`(JSON), `MockPgModeRequest`에 `webhookMode` 추가
- 시나리오 선택 → 실행 → 상태 변화 관찰 → 불변조건 카드
- **완료 기준**: 장애를 주입해 `UNKNOWN`을 만들고 복구되는 동안 **불변조건 카드가 계속 정상**

### FE-M7 · 정산·대사 (백엔드 신규 API)

- **백엔드**: 정산 상세에 `settlement_item` 목록 노출
- 판매자 대시보드·정산 상세(주문 단위 근거), OPS-05 대사 워크벤치, OPS-06 보정 분개
- **완료 기준**: 정산액이 어떤 주문에서 왔는지 화면에서 추적. 자기 요청을 자기가 승인할 수 없습니다

## 5. 진행 규칙

- 마일스톤 하나가 커밋 하나 이상이며, **백엔드 변경은 시험과 함께** 들어갑니다.
- 새 API는 `docs/api/openapi.json` 스냅샷을 갱신하고, 프론트엔드 타입을 다시 생성합니다.
  둘이 어긋나면 CI가 막습니다.
- DOC-15에서 범위를 뺀 항목(§2.3)을 나중에 되살리려면 **이 문서를 먼저 고칩니다.**
- 완료는 DOC-13 체크리스트에 표시하고, **시험이 통과한 것만** 체크합니다.
