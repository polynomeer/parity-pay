# ParityPay 실험 결과 해석 안내서 (DOC-20)

> **에이전트 지침**
> - **읽는 시점**: 실험 스크립트가 남긴 출력(콘솔 요약, `raw.json`, `summary.json`, `report.txt`, k6 JSON)이나 장애 시뮬레이터 화면을 **읽어 판단**할 때. 실행 절차는 [DOC-19](19-experiment-runbook.md)입니다.
> - **이 문서가 정하는 것**: 각 출력의 필드가 무엇을 뜻하는지, 무엇이 "정상"이고 무엇이 결함 신호인지, 그리고 **결함이라고 말하기 전에 측정 자체를 의심하는 순서**. 정책·불변조건은 CLAUDE.md §2와 DOC-04·09가 정하고, 이 문서는 그것을 출력에 대응시킬 뿐입니다.
> - **강제 규칙**: 이 문서의 예시 수치는 전부 reports/11·13에 기록된 실측을 옮긴 것이며, 다른 환경의 기대값으로 쓰지 않습니다. 새 출력 필드를 추가하면 여기 표에 같이 적습니다.

## 1. 읽기 전에 — 이 프로젝트에서 수치가 뜻하는 것

1. **판정의 순서가 정해져 있습니다.** ① 불변조건(INV)이 0인가 → ② 금융 효과가 정확히 1회인가(INV-004) → ③ 시간·처리량.
   ①·②가 틀리면 ③은 볼 필요가 없고, ③이 나빠도 ①·②가 맞으면 **시스템은 옳고 느린 것**입니다. 이 프로젝트의 목표는
   "정상 결제가 되는 것"이 아니라 장애 중에도 ①·②가 유지되는 것입니다(CLAUDE.md §1).
2. **절대 수치는 이 기계의 것입니다.** 부하 도구·앱·DB가 한 노트북의 CPU를 나눠 씁니다(reports/11 §2). M-013이 잰 날은
   load1이 49~97이었습니다. 그래서 결론은 언제나 **모양**(어디서 꺾이는가, 무엇이 기다리는가, 전후 비율)이지 "이 시스템은
   초당 N건"이 아닙니다. 어떤 수치가 운영 용량으로 인용되어 있다면 그것이 오류입니다.
3. **시간 값 중 상당수는 분포가 아니라 설정이 정한 상수입니다.** 미확정 거래의 확정 시간은 `grace 30s + 틱 5s + 백오프`의
   산술이고(§4.2), 그 값이 흔들리면 설정을 먼저 봅니다.
4. **"증명하지 못함"은 통과가 아닙니다.** 중복·유실·역전·정지를 재현하려는 실험에서 그 현상이 0건이면 시스템이 잘한 것이
   아니라 **실험이 조건을 만들지 못한 것**입니다. 스크립트는 이것을 `proved: false`나 "이 실행은 멱등성을 증명하지
   못합니다"로 표시합니다(§3).
5. **실패한 요청을 빼고 지연을 계산하지 않습니다.** k6 요약의 p95는 실패 응답을 포함한 값이어야 하고, `dropped_iterations`가
   있으면 그만큼은 **응답조차 없었다**는 뜻이라 p95보다 나쁩니다(§4.5).
6. **결함이라고 쓰기 전에 §5의 순서로 측정을 의심합니다.** 지금까지 결함으로 오인할 뻔한 측정 실패가 넷 있었습니다
   (순차 비교의 4.8배, 목록 밖으로 밀린 문장의 처리량 0, 웹훅 주소가 없던 로컬 스택, `ps %cpu`의 수명 평균).

## 2. 판정의 세 층 — 무엇을 어디서 보나

### 2.1 불변조건: 0이어야 하는 값

| 값 | INV | 어디서 보나 | 0이 아니면 |
|---|---|---|---|
| `paritypay_invariant_unbalanced_ledger_transactions` | INV-001 차변=대변 | `/actuator/prometheus`, 시뮬레이터 카드, `scenario-matrix`의 `gaugesBefore/After`, Grafana | **원장 트리거가 뚫린 것.** 있을 수 없는 일이므로 마이그레이션·트리거부터 의심 |
| `paritypay_invariant_negative_wallet_balances` | INV-003 가용 잔액 ≥ 0 | 위와 같음 | 조건부 UPDATE 우회. 분산락 실험(M-024)에서 일부러 만들었을 때만 본 값 |
| `paritypay_invariant_over_cancelled_payments` | INV-005 취소 ≤ 승인 | 위와 같음 | 취소 예약(`processingCancellationAmount`)이 풀린 채 재취소 |
| `paritypay_invariant_balance_snapshot_drift` | INV-010 스냅샷=원장 | 위와 같음, `crash-recovery`의 "잔액 스냅샷 = 원장", `lock-lease`의 `totalDrift` | 스냅샷과 원장이 다른 트랜잭션에서 갱신됨. **어느 쪽이 맞는지는 원장** |
| `paritypay_invariant_refresh_age_seconds` | (지표 자체의 신선도) | 시뮬레이터 "신선도", 경보 `InvariantMetricsStale` | **180초를 넘으면 위 네 값의 0은 아무 뜻이 없습니다.** 갱신이 멈춘 채 마지막 0이 보이는 것 |

네 게이지는 30초마다 계산해 캐시합니다(결함 G 이후). 그래서 시나리오 직후의 0은 **직전 계산의 0**일 수 있습니다.
시나리오가 끝나고 30초 뒤의 값, 또는 `refresh_age`가 작은 값을 봐야 합니다. `scenario-matrix`는 시나리오마다 `gaugesAfter`를
남기는데 그 값도 같은 성질입니다 — 9개 시나리오 뒤 전부 0.0이었다는 것은 13분 동안 한 번도 0이 아닌 적이 없었다는 뜻입니다.

### 2.2 정확히 1회: 참조당 1

"돈이 맞는가"는 게이지가 아니라 **행 수**로 봅니다. 게이지는 원장 안의 균형만 보고, 원장이 두 번 전기된 것은 균형이 맞으므로
게이지에 잡히지 않습니다.

| 세는 것 | 기대 | 어느 출력 |
|---|---|---|
| 같은 업무 참조(`reference_id`)의 POSTED 원장 거래 수 | 성공 1 · 실패 0 | `scenario-matrix` `ledgerPosted`, `crash-recovery` "업무 참조당 원장 거래" |
| 같은 멱등 키의 업무 행 수 | 1 | `crash-recovery` "멱등 키당 충전 행" |
| 외부 기관의 출금·승인·환불 기록 수 | 내부 성공 건수와 같음 | `crash-recovery` "성공한 충전 = 외부 출금 수", "내부 기록 없는 외부 출금" |
| 거래내역·정산 항목 등 **프로젝션** 행 수 | 이벤트 수와 같고, 고유 참조 수와 같음 | `rebalance`·`kafka duplicate`의 `rows`/`distinctRows` |
| 잔액 변화 | 충전 성공 +금액 · 실패·미확정 0 · **카드 결제 0**(지갑을 건드리지 않음, JE-013) | `scenario-matrix` `balanceDelta` |

### 2.3 시간·처리량: 상수인가 분포인가

| 종류 | 예 | 읽는 법 |
|---|---|---|
| 설정이 정하는 상수 | 미확정 → 확정 (31~35초 / 43~44초) | 산술과 맞으면 정상. 다르면 설정·틱·배치 크기부터 (§4.2·§4.4) |
| 부하가 정하는 분포 | 결제 p50/p95, 처리량 | 같은 조건의 다른 변형과 **비율**로 비교. 절대값 인용 금지 |
| 붕괴 시각 | 무관한 API가 무너진 초 | 산술(초당 10건 × 30초 = 200 스레드 → 20초대)과 맞으면 "예측 가능한 붕괴". `None`이면 무너지지 않음 |
| 정지·회복 구간 | 차단기 OPEN 구간, poison 뒤 파티션 정지 | 시작·끝 시각을 이벤트 목록에서 읽고, 그 안의 요청 운명을 봄 |

## 3. 모든 출력에 공통인 필드

| 필드 | 뜻 | 주의 |
|---|---|---|
| `commit` / `commitSha` | 실행 시점 `git rev-parse --short HEAD` | 작업 트리가 더러웠는지는 적히지 않습니다. 보고서에는 "미커밋 작업 트리"라고 씁니다 |
| `run` / `index` | 몇 번째 실행인지 (`run`은 1부터, `scenario-matrix`의 `index`는 0부터) | 1회차는 JIT·캐시가 차갑습니다. 3회 중 1회차만 다르면 그것이 이유일 수 있습니다 |
| `variant` | 같은 실험 안의 대조 변형 (`platform-threads` vs `virtual-threads`, `acks=all/1/0`, `LOCK_PLAIN` vs `CONTROL`) | 변형 사이 비교가 실험의 목적입니다. 한 변형만 보고 결론 내지 않습니다 |
| `env` | 그 변형에 넣은 `EXPERIMENT_*` 환경변수 | 여기 없는 설정은 기본값입니다. 기본값이 무엇인지는 `application.yml` |
| `proved` | 재현하려던 현상이 실제로 일어났는가 | `false`면 그 실행의 다른 값은 **결론에 쓰지 않습니다** |
| `since` | 측정 시작 시각. DB 읽기의 `created_at >` 기준 | 이전 실행의 행을 세지 않으려는 것 |
| `load` | 부하 조건 (rps, VU, 스레드, 지속 시간) | 두 실행의 `load`가 다르면 비교할 수 없습니다 |
| `samples` | 1~2초 간격의 지표 표본 (`tomcat_threads_busy_threads`, `hikaricp_connections_pending`, `paritypay_pg_*` …) | **빈 구간이 정보입니다** — 스크레이프 자체가 실패한 시간(M-019에서 붕괴 뒤 84초) |
| `probes` | 250 ms 간격의 "무관한 API" 호출 `[t, ms, status]` | 200이 아니거나 1,000 ms를 넘는 첫 표본이 붕괴 시각 |

## 4. 출력 유형별 해석

### 4.1 장애 시뮬레이터 화면 (운영 콘솔)

화면에는 시나리오 선택, "적용했습니다", 불변조건 카드 넷, 신선도가 있습니다. 고객 앱에서 충전·결제를 누른 뒤 보는 것:

| 시나리오 | 고객 앱이 보는 것 | 카드 | 시간 (reports/13 실측) |
|---|---|---|---|
| 정상 처리 | 201 → 즉시 `SUCCEEDED` | 전부 정상 | 0초 |
| 은행 명시적 실패 | **200** `FAILED` (201도 4xx도 아님 — 요청은 정상 처리됐고 결과가 실패) | 정상 | 0초 |
| 은행 출금 전 응답 끊김 | 202 `UNKNOWN` → `FAILED` | 정상 | **43~44초** |
| 은행 출금 뒤 응답 끊김 | 202 `UNKNOWN` → `SUCCEEDED`, 잔액 +금액 | 정상 | **31~35초** |
| PG 승인 뒤 응답 끊김 | 202 `UNKNOWN` → `APPROVED`, 잔액 그대로 | 정상 | 31~35초 (웹훅이 오면 더 빠름) |
| PG 상태 조회 장애 | 202 `UNKNOWN`이 **장애가 이어지는 동안 그대로** | 정상 | 장애 해소 뒤 6~26초 |
| 웹훅 중복·역순·미전송 | 201 `APPROVED` 즉시 | 정상 | 0초 |

- **`UNKNOWN`이 오래 머무는 것은 정상입니다.** 조회 장애 중에는 아무것도 단정하지 않는 것이 요구사항입니다(ADR-007). 화면이
  `UNKNOWN`을 실패(빨강)로 그리면 그것이 결함입니다 — 보라색이어야 합니다(ADR-012).
- **카드가 "정상"인데 신선도가 오래됐다면 카드를 믿지 않습니다**(§2.1).
- 카드 결제 시나리오에서 **잔액이 그대로인 것은 정상**입니다. 카드 결제는 지갑을 건드리지 않습니다.
- 웹훅 시나리오 셋은 버튼 한 번으로 설명문의 상황이 되지 않습니다(reports/13 발견 2). "웹훅 미전송"은 승인이 정상이라
  조회할 것이 없고, "역순"은 같은 결제의 두 번째 알림이 있어야 재현됩니다. 이것은 시스템 결함이 아니라 시뮬레이터 정의의
  한계이며, 수치가 필요하면 §4.2를 씁니다.

### 4.2 `scenario-matrix` — `summary.json` · `results.json` · 콘솔

`results.json`의 한 행(시나리오 한 회):

| 필드 | 뜻 | 기대 | 어긋나면 |
|---|---|---|---|
| `httpStatus` | 첫 응답 HTTP | 201(즉시 성공) · 200(즉시 실패) · **202(미확정)** | 시나리오 정의와 다른 코드 → 기관 모드가 적용되지 않은 것(이전 실험이 남긴 모드, 웹훅 주소 미등록) |
| `firstStatus` | 첫 응답의 업무 상태 | `SUCCEEDED`/`FAILED`/`UNKNOWN`/`APPROVED` | 202인데 `UNKNOWN`이 아니면 API 계약 위반 |
| `terminal` | 폴링이 끝났을 때의 상태 | 시나리오의 `expect`와 같음 | 다르면 **복구가 틀린 결론을 냈거나** (`TIMEOUT_AFTER`인데 `FAILED`) 시간 안에 못 끝남(`deadline`) |
| `seconds` | 요청을 보낸 순간부터 종결까지 | 아래 산술 | 90초를 넘으면 FE-003 폴링 상한을 넘은 것 — 화면은 "아직 확인 중"으로 남습니다 |
| `attempts` / `notFound` / `manualReview` | 복구 시도 수·"없음" 확인 수·수동 검토 전환 | 미확정 동안만 값이 있음 | 확정 뒤에는 `null` — 복구 행이 지워지므로(reports/13 발견 3). 시도 횟수가 필요하면 로그 |
| `ledgerPosted` | 그 참조의 POSTED 원장 거래 수 | 성공 1 · 실패 0 | **2면 INV-004 위반, 성공인데 0이면 원장 없이 상태만 바뀐 것.** 둘 다 즉시 결함 |
| `balanceDelta` | 지갑 가용 잔액의 전후 차이 | 충전 성공 +금액, 그 외 0, 카드 결제 항상 0 | `ledgerPosted`와 어긋나면 INV-010 방향의 문제 |
| `kind` | `top-up` / `payment` | — | — |
| `webhookReceipts` / `webhookLog` / `renotifyHttp` | 받아들인 웹훅 영수증 수 / 로그의 `duplicate`·`stale` 수 / 재알림 요청의 HTTP (PG 시나리오만) | 중복: 영수증 1·버림 1, 역순: 영수증 3·버림 1, 미전송: 0 | 웹훅 시나리오인데 전부 0이면 **기관에 웹훅 주소가 등록되지 않은 것**(reports/13 발견 1) |

**`seconds`의 산술.** 복구 설정이 주기 5초 · grace 30초 · 백오프 2초→10분 · "없음" 3회 확인일 때:

| 경로 | 구성 | 기대 |
|---|---|---|
| 외부에 기록 있음 (출금 뒤·승인 뒤 끊김) | grace 30 + 다음 틱 ≤5 + 조회 1회 | **31~35초** |
| 외부에 기록 없음 (출금 전 끊김) | grace 30 + "없음" 3회 연속 확인 (백오프 2·4초) + 틱 | **43~44초** |
| 조회 장애 N초 | 장애 중 실패마다 백오프가 커짐 → 해소 뒤 다음 확인까지 최대 백오프만큼 | 해소 뒤 **6~26초** (백오프가 어디까지 커졌는지에 따라) |

실측이 이 값보다 **짧으면** grace가 적용되지 않은 것(설정·프로필 확인), **길면** 틱을 놓쳤거나(스케줄러 스레드 부족 — 결함 H)
배치가 밀린 것(§4.4). 조회 장애 뒤 확정이 6초와 26초로 갈리는 것은 정상입니다 — 다섯 번째 실패 뒤의 백오프가 25초 근처입니다.

`summary.json`은 시나리오별 3회 요약과 `gaugesBefore/After`입니다. 콘솔의 마지막 표가 reports/13 §4.1 표의 원본입니다.

### 4.3 `crash-recovery-experiment` — 콘솔 `[PASS]/[FAIL]`

트래픽 중 `SIGKILL` → 재시작 → 응답 못 받은 요청을 **같은 멱등 키로 재전송** → 검증 14개. 종료 코드 0이 전부 PASS입니다.

| 검증 | 세는 것 | FAIL이면 |
|---|---|---|
| 멱등 키당 충전 행 (INV-004) | `top_up`에서 같은 `(wallet_id, idempotency_key)`가 2행 이상 | 멱등 레코드와 업무 유니크 제약 **둘 다** 뚫림 |
| 외부 출금 중복 | 은행에 같은 `external_key`가 2행 이상 | 재시작 뒤 같은 요청을 다시 보냄 — 상태 조회 대신 재전송한 것 |
| 업무 참조당 원장 거래 (INV-004) | 같은 `reference_id`의 원장 거래 2건 이상 | 복구가 이미 전기된 건을 다시 전기 |
| 성공한 충전 = 원장 거래 수 / = 외부 출금 수 | 세 수가 같은가 | 어느 하나가 크면 그 계층에 고아가 있음 |
| 잔액 스냅샷 = 원장 (INV-010) / 잔액 = 성공 건수 × 금액 | 스냅샷·원장·산술 셋이 같은가 | 스냅샷이 원장과 다른 트랜잭션에서 갱신됨 |
| 불균형 원장 거래 (INV-001) | 차변≠대변인 거래 | 트리거 우회 |
| 내부 기록 없는 외부 출금 | 은행에는 있는데 `top_up`에 없는 건 | **F-001인데 외부 호출이 먼저 나간 것** — 트랜잭션 안 외부 호출 |
| 재전송이 모두 결과를 돌려줌 | 재전송 응답이 전부 2xx | 멱등 재전송이 409/5xx면 클라이언트가 결과를 알 방법이 없음 |
| 미확정으로 남은 충전 / 미발행 이벤트 / 발행 포기 이벤트 | 0 | 복구·발행기가 재시작 뒤 이어받지 못함 (F-003) |
| 거래내역 프로젝션 = 성공한 충전 | 소비자까지 도달 | 발행은 됐는데 소비가 안 됨 |

마지막 줄의 `F-001 n / F-002 m`은 응답을 못 받은 요청이 **커밋 전에 죽었는지(행 없음) 후에 죽었는지(행 있음)**를 DB로 가른
것입니다. 두 수의 합이 재전송 건수입니다. 어느 쪽이든 최종 효과는 1회여야 하고, 그것이 위 검증들입니다.
"복구 대기 N초"는 재시작부터 미확정이 0이 될 때까지이며 §4.2의 산술을 따릅니다.

### 4.4 `recovery-latency` (M-011) · `recovery-backlog` (M-012) — `report.txt`

**M-011** (한 건씩, 한가한 시스템): `결과: SUCCEEDED 12건`, `확정까지 (초) n=12 최소 · 중앙값 · p95 · 최대`, `각 실행: …`.
편차가 5초 안이면 정상입니다 — 요청이 틱 어디에 떨어졌는지의 차이입니다. 그보다 크면 틱을 놓친 것입니다.
`확정 못함`이 있으면 `deadline`(기본 900초) 안에 끝나지 않은 것이고, 그 건은 수동 검토로 갔는지(`manualReview`) 봅니다.

**M-012** (N건을 한꺼번에):

| 줄 | 뜻 | 읽는 법 |
|---|---|---|
| `주입 폭: N초` | 첫 요청부터 마지막 응답까지 | 주입은 동시가 아닙니다. 기관이 응답을 붙잡는 동안(read-timeout) 워커 하나가 막히므로 `N / 워커 × 타임아웃` 근처. 이 폭이 크면 "적체"가 아니라 "주입 병목"을 잰 것 (결함이 아니라 하니스 설정 — 읽기 타임아웃 500 ms·워커 50으로 잡은 이유) |
| `확정까지 … 최대` | 가장 늦게 확정된 건 | 산술 `30 + 5·⌈N/50⌉`(마지막 줄에 같이 찍힘)과 비교 |
| `클라이언트 한계 90초 초과: n건` | FE-003 폴링 상한을 넘긴 건 | 이 수가 곧 **화면이 "아직 확인 중"으로 남긴 건수** |
| `5초 구간별 확정: 30s 48건, 35s 50건, …` | 틱마다 몇 건 확정됐나 | **구간당 50건이 상한으로 보이면 결함 K** — 틱당 한 배치만 처리해 초당 10건이 상한이던 것. 고친 뒤에는 한 틱에 여러 배치가 비워져 구간당 건수가 50을 넘습니다 |

결함 K의 신호는 "느리다"가 아니라 **기울기**였습니다 — 확정 건수가 5초마다 정확히 50씩 늘면 배치 하나가 틱 하나에 묶인
것입니다. 고친 뒤 재측정 표가 reports/11 M-012 절에 전후로 있습니다.

### 4.6 `lock-wait` (M-007·M-009) · `db-saturation` (M-013) — 콘솔 표 · `report.txt`

같은 하니스입니다. 부하를 걸면서 DB 안쪽을 세 가지로 봅니다.

**(1) `pg_stat_statements` 상위** — `calls / total_ms / mean_ms / max_ms / statement`. 보는 것은 **잔액 UPDATE의 `mean_ms`**가
경합에서 얼마나 늘어나는가입니다. 문장 자체가 느려진 것이 아니라 잠금을 기다린 시간이 `mean_ms`에 들어갑니다.
`상위 문장 실행 시간 합계 = 벽시계 초당 N 초분`은 DB가 초당 몇 초어치 일했는가(코어 수 단위)입니다.

**(2) 대기 이벤트 (10 ms 표본)** — 이것이 병목의 위치를 가릅니다.

| 대기 | 뜻 | 이것이 크면 |
|---|---|---|
| `Lock:transactionid` / `Lock:tuple` | 다른 트랜잭션이 쥔 **행 잠금**을 기다림 | 직렬화 지점이 DB 행. 동일 지갑이면 **요구사항의 성질**(한 지갑의 잔액은 순서대로 바뀌어야 함)이지 결함이 아님. 줄이려면 잠금 **보유 시간**을 줄임(결함 I: 차감을 트랜잭션 뒤로) |
| `Client:ClientRead` | DB가 **앱이 다음 문장을 보내길** 기다림 | **DB가 놀고 있음.** 병목은 DB 밖 — 앱 CPU, 커넥션 풀, 부하 도구 |
| `LWLock:WALWrite`, `IO:WalSync` | 커밋(fsync) | 커밋 비용. 처리량이 늘어도 DB CPU가 그대로면 그룹 커밋 |
| (표본에 대기 없음) | 실제로 실행 중 | CPU를 쓰는 중 |

**(3) 커넥션 풀** — `pool: active 평균 / pending 평균·최대`. `pending`이 0이 아니면 **DB 앞이 아니라 풀 앞에 줄이 선 것**이고
그것은 앱 설정입니다.

**판정 순서:**

```text
pending > 0 ?            → 풀이 첫 한계. 풀을 키우고 다시 (M-013: 풀 20 → 40에서 정점이 423 → 688로 이동)
Lock 비율 높음 ?         → 행 잠금. 같은 지갑이면 요구사항, 다른 지갑인데 높으면 결함(결함 E: 원장 계정 최초 생성 경합)
ClientRead 75%+ ?        → DB는 한가함. 앱 CPU·기계를 봄 (M-013: 8점 모두 75~84%)
DB CPU가 코어를 채움 ?   → 그때가 DB 한계. 이 기계에서는 닿지 못함
```

**M-013 곡선 읽기:** 표의 각 행이 (풀, VU) 한 점입니다. 처리량이 **VU = 풀 크기에서 정점이고 그 위에서 떨어지면** 풀이 한계입니다
(pending이 같이 늘고 DB CPU는 그대로). 풀을 키웠을 때 정점이 옮겨가면 결론이 "풀 설정"이고, 같은 자리에서 꺾이면 그때 DB·CPU를 봅니다.
**같은 VU에서 풀 40 계열이 풀 20 계열보다 느린 점이 있다면 그것은 기계 상태(load1)이지 풀 때문이 아닙니다** — 두 계열은 시간을 두고
따로 돌았습니다. 그래서 절대값이 아니라 꺾이는 위치만 결론에 씁니다.

**`transaction-timeline`** (M-007·M-010)은 한 건의 문장 순서와 "잔액 차감 이후 COMMIT까지"의 시간입니다. CPU 경합은 순서를 바꾸지
않으므로 시끄러운 기계에서도 판정할 수 있습니다 — M-010은 처리량으로 판정하지 못하다가 이것으로 확정했습니다(flush 없음: 차감 뒤
문장 4개 · 26 ms, flush 있음: COMMIT뿐 · 1 ms).

### 4.7 Outbox·발행기 — `outbox-drain` (P-005) · `multi-instance` (M-001·M-003) · `rebalance` (M-005)

**`multi-instance` 콘솔 표:** `발행기 | run | 발행 | 실패 | 소요 | 처리량 | 브로커 도착 | 유실 | 중복 | 순서역전`

| 열 | 기대 | 어긋나면 |
|---|---|---|
| 유실 (`missing`) | **0** | 토픽에 없는 이벤트. PUBLISHED로 표시됐는데 브로커에 없으면 acks 설정(M-016) |
| 중복 (`duplicates`) | 0 이상 (설계상 허용) | 양이 문제. 두 발행기가 같은 이벤트를 보낸 수. `SKIP LOCKED`가 작동하면 거의 0 |
| 순서역전 (`inversions`) | **0** | 같은 파티션 키 안에서 sequence가 뒤로 감. 정산 소비자가 순서에 의존하므로 **금액이 틀립니다**(결함 F) |
| 처리량 | 대수에 따라 늘어야 함 | 1→2→4대에 늘지 않으면 한 키의 직렬화(M-003 head-of-line)나 DB가 한계 |

**`rebalance` 콘솔:** `거래내역 행 = 이벤트 수`, `거래내역 행 = 고유 참조`, `중복 전달(로그) > 0`. 세 줄이 전부 맞아야 "문제 없음"이고
종료 코드 0입니다. **`중복 전달 0`이면 실패로 처리합니다** — 재분배가 중복을 만들지 않았다면 멱등성을 증명한 것이 아닙니다.
`파티션 재할당`이 0이면 kill 시점이 소비 시작 전이었던 것입니다(`--kill-after` 조정).

### 4.8 `kafka-failure-experiment` (M-015~M-018) — `<실험>-<UTC>.json`

**`duplicate`** (소비자가 처리 뒤 커밋 전에 죽음; BATCH 커밋 vs 자동 커밋):

| 필드 | 뜻 | 읽기 |
|---|---|---|
| `rowsBeforeKill` | 죽이기 전까지 프로젝션에 들어간 행 | 0이면 kill이 너무 빨랐음 |

| `rows` / `distinctRows` | 프로젝션 행 / 고유 참조 | 둘이 같아야 함. 다르면 중복이 **행으로 남은 것** — 결함 |
| `lost` | `events − rows` | **0이어야 함.** 자동 커밋에서 0이 아니면 "처리 전에 커밋"이 유실을 만든 것 |
| `rebalances` | `partitions assigned` 로그 수 | 재분배가 실제로 일어났는지 |

**`loss`** (발행 중 브로커 `SIGKILL`; acks=all / 1 / 0):

| 필드 | 뜻 | 읽기 |
|---|---|---|
| `publishedAtKill` | 브로커를 죽인 순간의 PUBLISHED 수 | `--kill-at` 근처여야 함 |
| `publishedButMissing` | 우리는 PUBLISHED로 표시했는데 브로커에 **없는** 이벤트 | **이것이 유실입니다.** acks=all에서는 0이어야 하고(`proved` 조건), 1·0에서는 >0이 곧 실험의 증명 |
| `inBrokerNotPublished` | 브로커에는 있는데 우리는 PUBLISHED로 표시 못 한 것 | 유실이 아닙니다. 재발행되면 **중복**이 되고 소비자 멱등성이 막습니다 |
| `brokerDuplicates` | 토픽에 같은 eventId가 두 번 이상 | 재발행의 흔적. 허용되지만 양을 적음 |
| `unparsable` | 읽을 수 없는 레코드 | 0이 아니면 하니스나 봉투 형식 문제 |
| `logFailures` | 발행 실패 로그 수 | 브로커가 죽은 동안의 실패. 0이면 그 동안 발행 시도가 없었던 것 |

acks=all의 `proved`는 "유실도 중복도 없음"이고, acks=1·0의 `proved`는 "유실이나 중복이 **있음**"입니다 — 대조군과 실험군의
증명 조건이 반대입니다.

**`order`** (같은 결제의 확정·취소가 다른 파티션으로; 키 = Aggregate vs 랜덤):

| 필드 | 뜻 | 읽기 |

| `arrivalInversions` | 취소가 확정보다 **먼저** 소비된 결제 수 | 랜덤 키에서 >0이어야 증명. Aggregate 키에서는 0 |

| `paymentsCorrect5400` / `paymentsOverpaid9000` | 정산 순액이 맞는 결제 / 취소가 빠져 **과지급**된 결제 | 하니스가 만든 결제는 10,000 − 1,000 − 4,000 + 400 = 5,400이 맞고, 취소가 버려지면 9,000 |
| `overpaidTotalWon` | 과지급 합계 (원) | 순서가 깨졌을 때 **돈으로 얼마인가** |

**`poison`** (파싱할 수 없는 봉투 하나):

| 필드 | 뜻 | 읽기 |
|---|---|---|

### 4.9 `external-isolation-experiment` (M-019~M-023) — `<실험>-<UTC>.json`

기관이 응답을 붙잡을 때(`HANG_*`) 결제 서버가 어떻게 되고, **기관과 무관한 API(잔액 조회)가 언제 무너지는가**를 봅니다.

| 필드 | 뜻 | 읽기 |

| `probeCollapseAtSec` | 250 ms 프로브가 처음으로 실패하거나 1초를 넘긴 시각 | **`None`이면 무관한 API가 살아남은 것.** 값이 있으면 그 시각부터 서버가 기관에 묶임. M-019 플랫폼 스레드: 23.7~24.0초 = 초당 10건 × 30초 지연이 Tomcat 200을 채우는 산술 |

| `samples`의 빈 구간 | 스크레이프 실패 | 서버가 지표조차 못 줌. 경보가 "지표 없음"을 이상으로 보지 않으면 붕괴가 조용함 |
| `jstack.socketRead` | 소켓 읽기에서 기다리는 프레임 수 | 플랫폼 스레드 202개 전부(400 = 200×2). 가상 스레드에서는 jstack에 안 보이므로 지표로 봐야 함 |
| `k6.paymentOutcomes` | 결과별 건수 (`201_APPROVED`, `202_UNKNOWN`, `201_FAILED_CIRCUIT_OPEN`, `201_FAILED_MOCK_PG_LATE_RESPONSE` …) | 장애 동안 결제가 **어떤 운명**이었는가. `UNKNOWN`은 복구가 맡고, `FAILED_CIRCUIT_OPEN`은 기관에 가지도 않은 것 |

| `circuitTransitions` | `[시각, 이전 상태, 다음 상태]` — CLOSED→OPEN→HALF_OPEN→CLOSED | OPEN 시각이 기관 지연 시작 + 실패율 창, CLOSED 복귀가 `restoredAtSec` 뒤 반개방 성공 뒤 |

### 4.10 `lock-lease-experiment` (M-024~M-028) — `<실험>-<UTC>.json`

이 실험은 **채택하지 않은 경로**(분산락)를 일부러 만들어 기본 경로(조건부 원자 UPDATE)와 대조합니다. 결과 JSON의 `results[]`
한 행이 한 실행입니다.

| 필드 | 뜻 | 읽기 |
|---|---|---|
| `holds.overlappingPairs` | 같은 지갑에서 `[acquired_at, released_at]`이 겹치는 락 보유 쌍 | **>0이면 두 소유자가 동시에 있었던 것** — lease가 트랜잭션보다 먼저 만료됨. `CONTROL`에는 락이 없어 0 |
| `holds.maxSimultaneousOwners` | 한 순간의 최대 소유자 수 | 2 이상이면 이중 소유 |
| `holds.lostUpdatePairs` | 겹친 둘이 **둘 다 썼고** 뒤의 쓰기가 앞의 읽기 위에 덮인 쌍 | 이것이 실제 잃어버린 갱신 수 |
| `holds.releaseResults` | 해제 결과 분포 (`RELEASED`, `EXPIRED`, `STOLEN`, `REDIS_DOWN`) | `STOLEN` = 해제하려는데 이미 남의 락. `EXPIRED` = 해제 전에 만료 |
| `holds.renewals` | Watchdog가 락을 연장한 횟수 (놓친 연장은 지표 `paritypay.experiment.lock.renewals_lost`) | `stop-the-world` 변형에서는 `SIGSTOP` 동안 연장 스레드도 멈추므로 연장이 있어도 겹침이 다시 생김 |
| `totalDrift` / `walletsWithDrift` | 스냅샷(가용+처리중) − 원장 계산값의 합 / 지갑 수 (INV-010) | **0이어야 합니다.** `CONTROL`에서 0이 아니면 기본 경로의 결함 — 즉시 보고 |
| `excessApprovals` / `walletsLedgerNegative` | 원장 잔액이 음수가 된 만큼 / 지갑 수 (INV-003) | 잔액보다 많이 승인한 것. 락 경로에서 >0이 곧 "락이 있으니 안전하다"의 반증 |
| `fenceRejected` | fencing 토큰 불일치로 거부된 쓰기 | `fence-at-write`에서 거부가 있어도 drift가 남으면 "쓰기 시점 비교"는 부족한 것; `fence-at-read`가 0 drift여야 함 |
| `events` | `redis killed`·`redis restarted` 시각 | `redisdown`에서 그 사이의 `client.outcomes`(fail-closed면 전부 거절, fail-open이면 락 없이 진행)와 drift를 봄 |
| `client.throughputPerSec` / `p95Ms` | 클라이언트가 본 처리량·지연 | 같은 sleep 아래 `CONTROL`과 비교. 락이 정합성을 못 지키면서 느리기까지 하면 이유가 둘 |

**판정:** `CONTROL`(분산락 없음)이 `overlappingPairs`·`totalDrift`·`excessApprovals` 전부 0이어야 이 실험이 ADR-004를 확정합니다. 락
변형에서 0이 아닌 값은 결함이 아니라 **실험이 보여 주려던 것**입니다.

### 4.11 `ledger-aggregation-benchmark` (M-006) · `transaction-history-benchmark` (M-008) — 콘솔

둘 다 표를 비우고 합성 데이터로 채운 뒤 `EXPLAIN ANALYZE`의 Execution Time을 5회 재어 중앙값을 찍습니다. 클라이언트 시간이
아닙니다(docker exec 왕복이 수십 ms).

- **선형인가**를 봅니다. 전 지갑 불일치 탐지는 전체 항목 수에 선형(약 0.43 µs/항목)이었고, 그래서 스크레이프마다 돌리면 안 된다는
  결함 G가 나왔습니다. 값이 선형보다 나쁘게 자라면 인덱스가 안 쓰인 것입니다.
- **계획을 같이 봅니다.** 대상 계정이 전체의 절반이면 인덱스 대신 병렬 순차 스캔을 고릅니다. 현실적 분포(5,000 지갑 중 한 계정
  200건)에서는 인덱스 스캔 1.2 ms였습니다. **분포를 밝히지 않은 수치는 옮기지 않습니다.**
- M-008은 커서 조회와 OFFSET을 깊이별로 비교합니다. 커서가 깊이에 무관하게 평평하고 OFFSET이 깊이에 비례하면 설계대로입니다.

### 4.12 통합 테스트 · E2E

이 둘의 결과는 이진입니다 — 통과 아니면 실패. 해석할 것은 **왜 실패했는가**뿐이고, 규칙은 하나입니다: **`@Disabled`·재시도로 덮지
않습니다.** 간헐 실패(flaky)는 대개 실제 경합이거나 하니스의 타임아웃이며(예: 기관 관리자 호출 400 ms → 별도 10초 클라이언트),
원인을 고칩니다. `FROM-CACHE`는 실행이 아닙니다.

E2E 7건 중 "두 탭 동시 재발급"은 **두 탭의 재발급 응답을 700 ms 붙잡아** 실제 경쟁을 만듭니다. 이 시험이 잠금을 빼도 통과한다면
경쟁이 안 만들어진 것이지 잠금이 불필요한 것이 아닙니다(§1의 4).

### 4.13 관측 스택 (Prometheus 규칙 · Grafana)

`deploy/observability/rules/invariants.yml`의 경보는 두 종류입니다.

| 경보 | 뜻 | 실험 중 울리면 |
|---|---|---|
| `LedgerUnbalanced`, `NegativeWalletBalance`, `OverCancelledPayment`, `BalanceSnapshotDrift` | INV 위반 **1건이라도** (임계치 없음) | 실험을 멈추고 §5로. 실험이 일부러 만든 것(M-024)이 아니면 결함 |

## 5. "결함이다"라고 쓰기 전에 — 측정을 의심하는 순서

이상한 값이 나오면 아래를 **위에서부터** 지웁니다. 전부 지워진 뒤에 남는 것이 결함입니다.

1. **`proved`·"증명하지 못함"·종료 코드.** 실험이 조건을 만들지 못했으면 다른 값은 무의미합니다.
2. **스택이 맞았는가.** `dev.sh`의 pay-api가 같이 떠 있었는가(소비자 둘), DB 포트가 맞았는가, 기관 모드가 이전 실험의 것이었는가,
   기관에 웹훅 주소가 있었는가(reports/13 발견 1), 기관 jar가 있어 컨테이너가 살아 있었는가.
3. **하니스가 세는 방법이 맞았는가.** 처리량을 상위 목록에서 찾았는가(M-009의 0), CPU를 수명 평균으로 읽었는가(M-013), 안정
   판정 대기가 너무 짧았는가(kafka `duplicate`의 30초 → 90초), 폴링 해상도가 잰 값보다 굵은가.
4. **기계가 시끄러웠는가.** `load1`, 다른 프로젝트의 컨테이너. 절대값이 흔들리면 모양만 취하고, 모양도 흔들리면 다시 잽니다.
5. **비교가 공정했는가.** 두 빌드를 번갈아 돌렸는가, `load`가 같은가, 1회차의 차가운 JIT을 빼고 봤는가, 데이터가 쌓인 뒤의 실행이
   불리하지 않았는가(reports/11 §2 데이터셋).
6. **산술과 맞는가.** 시간이 설정의 산술(§4.2)과 맞으면 그것은 결함이 아니라 설정입니다. 설정을 바꿀지는 별개의 결정입니다.

남았다면 결함입니다. 기록 양식은 reports/11의 "M-0xx가 찾아낸 결함 X" 절과 같습니다 — **무엇이 잘못됐나 · 왜 그랬나(코드 위치) ·
어떻게 고쳤나(커밋) · 고친 뒤 같은 실험의 재측정.** 전 수치를 지우지 않습니다. 결함 K(틱당 한 배치), L(미확정 취소가 201),
M(poison을 조용히 버림), N(외부 호출에 상한·차단기 없음)이 이 양식으로 적혀 있습니다.

## 6. 읽기 연습 — 기록된 결과 셋

**M-013 (DB 포화 곡선).** 8점 전부 `Lock` 0%, `ClientRead` 75~84%, 풀 20에서 VU 40·80에 `pending` 22→63이고 처리량은 정점 뒤 하락,

**reports/13 6번 (PG 조회 장애 60초).** `httpStatus` 202, 60초 동안 `terminal` 없음, `ledgerPosted` 0, `balanceDelta` 0, 해소 뒤

정상. 카드 결제라 잔액 0도 정상.
