# ParityPay 제품 기획서 (DOC-01)

> **에이전트 지침**
> - **읽는 시점**: 새 기능이 이 제품의 범위에 속하는지 판단할 때, 우선순위를 정할 때.
> - **이 문서가 정하는 것**: 제품 목표, 사용자, 전체 범위, 성공 지표, 로드맵.
> - **강제 규칙**: "제외 범위"에 있는 것은 사용자가 명시적으로 요청하기 전까지 구현하지 않습니다. 성능 목표를 임의의 TPS로 선언하지 않습니다.

## 1. 제품 개요

ParityPay는 가상의 커머스 플랫폼에 내장되는 페이머니 기반 결제 서비스입니다. 사용자는 Mock Bank 계좌에서 충전한 잔액으로 주문을 결제하고 취소·환불할 수 있습니다. 구매확정 이후에는 판매자 정산이 수행되고, 운영자는 내부 원장과 외부기관 기록의 불일치를 탐지하고 복구합니다.

제품의 핵심 메시지는 다음과 같습니다.

> 외부기관의 타임아웃, 중복 요청, 이벤트 재전달과 프로세스 재시작이 발생해도 금액이 중복 이동하지 않고 모든 거래가 추적 가능한 최종 상태로 수렴합니다.

## 2. 문제 정의

사용자에게 결제는 하나의 버튼이지만 시스템 내부에서는 주문, 결제, 외부 승인, 원장, 잔액, 이벤트, 취소와 정산이 서로 다른 생명주기를 갖습니다. `주문 성공 = 결제 성공 = 원장 기록 성공 = 정산 성공`으로 간주하면 다음 문제가 발생합니다.

- 클라이언트 재시도로 동일 결제가 여러 번 승인됩니다.
- 잔액 조회와 차감 사이의 경쟁 조건으로 잔액이 음수가 됩니다.
- 외부 승인 후 응답이 유실되면 성공한 거래를 실패로 오판합니다.
- DB 커밋 후 이벤트 발행이 실패해 후속 처리가 누락됩니다.
- 취소할 때 기존 원장을 수정하면 감사 가능성이 사라집니다.
- 내부와 외부 기록 차이를 늦게 발견해 운영 비용이 증가합니다.

## 3. 비전과 제품 원칙

### 비전

모든 돈의 이동에 근거가 남고, 모든 불확실한 거래가 추적 가능하며, 모든 실패가 중복 없이 복구 가능한 결제 인프라를 구현합니다.

### 원칙

설계·구현 판단이 갈릴 때 아래 순서로 결정합니다.

1. 돈의 기록과 감사 가능성을 편의 기능보다 우선합니다.
2. 결과를 모르는 거래를 실패로 덮지 않고 명시적 상태로 표현합니다.
3. 중복 요청과 중복 이벤트를 예외가 아닌 정상 운영 조건으로 취급합니다.
4. 확정 원장은 수정·삭제하지 않고 역분개와 보정 분개를 사용합니다.
5. 관리자 조회, 재처리, 알림과 감사 로그도 제품 기능으로 취급합니다.
6. 분산 기술은 해결할 문제가 명확할 때 단계적으로 도입합니다.

## 4. 목표 사용자

| 사용자 | 목표 | ParityPay의 가치 |
|---|---|---|
| 구매자 | 빠르고 정확한 결제와 환불 | 중복 차감 방지, 명확한 처리 상태와 거래내역 |
| 판매자 | 근거가 명확한 정산 | 주문·취소·수수료별 정산 상세 |
| 운영자 | 문제 거래의 신속한 판단과 복구 | 통합 타임라인, 대사 차이, 안전한 재처리 |
| 개발자·SRE | 장애 진단과 안전한 변경 | 구조화 로그, 메트릭, 트레이스와 불변조건 알림 |
| 면접관·리뷰어 | 설계·구현 역량 검증 | 재현 가능한 실험, ADR과 결과 보고서 |

## 5. 제품 가치

| 가치 | 약속 | 대표 수단 |
|---|---|---|
| 정확성 | 같은 요청이 반복되어도 돈은 한 번만 움직입니다. | 멱등성, DB 제약, 조건부 갱신 |
| 추적성 | 업무·원장·외부·이벤트 기록을 연결합니다. | 상관관계 ID, 거래 타임라인 |
| 복구성 | 응답 유실과 중단 후에도 거래가 수렴합니다. | `UNKNOWN`, 재조회, Outbox, 대사 |
| 운영성 | 문제를 탐지하고 근거를 남기며 조치합니다. | 관리자 워크벤치, 알림, 감사 로그 |
| 설명 가능성 | 선택과 트레이드오프를 실험으로 설명합니다. | ADR, 성능·장애 테스트 보고서 |

## 6. 제품 범위

### MVP

- 회원 인증과 사용자별 KRW 지갑
- Mock Bank 계좌 연결과 페이머니 충전
- 가용 잔액 조회와 거래내역
- 페이머니 결제 승인과 전액 취소
- 이중부기 원장과 잔액 스냅샷
- 멱등성 처리와 동시성 제어
- Transactional Outbox와 멱등한 이벤트 소비
- 기본 운영자 거래·원장·이벤트 조회
- 불변조건, 동시성, 재시작과 중복 전달 테스트

### 포트폴리오 목표 범위

- 부분 취소, 출금과 사용자 간 송금
- 외부 승인 후 타임아웃과 `UNKNOWN` 자동 복구
- 구매확정, 판매자 수수료와 정산
- 내부·Mock PG·Mock Bank 기록 대사
- 규칙 기반 이상거래 탐지
- Prometheus·Grafana·OpenTelemetry 기반 관측성
- 부하·장애 실험 및 결과 보고서

### 제외 범위

- 실제 은행·카드사 연결과 실제 자금 이동
- 전자금융업 인허가와 실서비스 규제 준수의 완전 구현
- 다중 통화, 환율, 할부와 해외결제
- ML 기반 FDS와 신용평가
- 처음부터 모든 모듈을 독립 마이크로서비스로 분리

## 7. 핵심 사용자 여정

1. 사용자가 가입하면 KRW 지갑과 사용자 원장 계정이 생성됩니다.
2. Mock Bank 계좌를 연결하고 100,000원을 충전합니다.
3. 30,000원 주문을 페이머니로 결제합니다.
4. 10,000원 상품을 부분 취소하고 잔액과 원장 반영을 확인합니다.
5. 남은 주문을 구매확정하면 판매자 정산 대상이 됩니다.
6. 운영자는 주문번호로 결제, 원장, 외부 응답과 이벤트 타임라인을 확인합니다.
7. 대사 작업은 내부와 외부 기록의 상태·금액·누락 차이를 탐지합니다.

이 여정은 데모 시나리오이자 E2E 테스트의 기준 흐름입니다.

## 8. 성공 지표

| 지표 | 목표 |
|---|---|
| 중복 금액 변동 | 0건 |
| 원장 불균형 | 0건 |
| 음수 가용 잔액 | 0건 |
| 동일 멱등 요청 100회 결과 | 업무 효과 1회 |
| 장애 시나리오 복구 | 정의한 모든 자동화 시나리오가 최종 상태로 수렴 |
| 추적 완전성 | 테스트 거래 100%가 핵심 ID로 연결 |
| 재현성 | 깨끗한 환경에서 실행·테스트·데모 재현 가능 |

성능 목표는 구현 환경과 부하 모델 없이 임의의 TPS로 선언하지 않습니다. 기준선을 측정하고 변경 전후 결과를 비교합니다.

## 9. 단계별 로드맵

| 단계 | 결과 |
|---|---|
| 1. 원장 기반 | 충전과 원장 불변조건 완성 |

| 3. 이벤트 기반 | Outbox와 멱등 소비자 완성 |

| 5. 운영 기반 | 정산·대사·관리자 기능 완성 |
| 6. 증명 기반 | 관측성·부하·장애 보고서와 기술 발표 완성 |

작업 단위 체크리스트는 [13-implementation-checklist.md](13-implementation-checklist.md)에 있습니다.

## 10. 완료 정의

정상 결제가 동작하는 것만으로 완료하지 않습니다. 중복, 동시 요청, 외부 응답 유실, 이벤트 중복, 프로세스 재시작 상황에서도 원장 균형과 잔액 불변조건이 유지되고 거래가 최종 상태로 수렴해야 합니다. 그 과정을 자동화 테스트, 로그, 메트릭, 트레이스와 문서로 재현할 수 있을 때 완료입니다.
