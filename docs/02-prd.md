# ParityPay PRD (DOC-02)

> **에이전트 지침**
> - **읽는 시점**: 기능을 구현하기 전, 테스트의 수용 조건을 정할 때.
> - **이 문서가 정하는 것**: 기능 요구사항(`FR-`), 비기능 요구사항(`NFR-`), 수용 조건(`AC-`), 권한 모델.
> - **강제 규칙**: 구현하는 유스케이스는 반드시 `FR-` ID를 갖습니다. 새 기능을 만들면 이 표에 요구사항을 추가하고, 테스트 이름 또는 메타데이터에 ID를 연결합니다. 세부 업무 규칙은 [04-payment-policy.md](04-payment-policy.md), MVP 포함 여부는 [03-mvp-scope.md](03-mvp-scope.md)를 따릅니다.

## 1. 문서 목적

이 문서는 제품 기획을 구현 가능한 사용자 스토리, 기능 요구사항, 비기능 요구사항과 수용 조건으로 변환합니다.

## 2. 사용자 스토리

### 구매자

- 사용자는 페이머니를 보유하기 위해 지갑을 생성할 수 있습니다.
- 사용자는 연결한 Mock Bank 계좌에서 원하는 금액을 충전할 수 있습니다.
- 사용자는 현재 사용 가능 잔액과 보류 잔액을 구분해 볼 수 있습니다.
- 사용자는 같은 결제 요청을 다시 보내도 이중 결제되지 않아야 합니다.
- 사용자는 결제 결과를 즉시 알 수 없을 때 처리 중임을 확인할 수 있습니다.
- 사용자는 승인된 결제를 전액 또는 허용 범위에서 부분 취소할 수 있습니다.
- 사용자는 모든 거래내역과 거래별 상태를 조회할 수 있습니다.

### 판매자

- 판매자는 구매확정된 결제의 지급 예정액을 조회할 수 있습니다.
- 판매자는 결제, 취소, 수수료와 조정액으로 정산 근거를 확인할 수 있습니다.
- 판매자는 정산 실패 또는 보류 상태와 사유를 확인할 수 있습니다.

### 운영자

- 운영자는 주문·결제·원장·외부거래 식별자로 거래를 검색할 수 있습니다.
- 운영자는 `UNKNOWN`, 이벤트 실패와 대사 불일치를 한곳에서 확인할 수 있습니다.
- 운영자는 권한과 사유를 남기고 허용된 재조회·재처리 작업을 실행할 수 있습니다.
- 운영자는 확정 원장을 직접 수정하거나 삭제할 수 없습니다.

## 3. 기능 요구사항

| ID | 요구사항 | 수용 조건 | 우선순위 |
|---|---|---|---|
| FR-001 | 사용자 가입 시 KRW 지갑을 생성합니다. | 사용자·통화별 활성 지갑이 하나이고 원장 계정이 함께 생성됩니다. | Must |
| FR-002 | Mock Bank 계좌를 연결합니다. | 계좌 원문 비밀번호를 저장하지 않고 소유 확인 토큰만 저장합니다. | Must |
| FR-003 | 연결 계좌에서 페이머니를 충전합니다. | 성공 시 은행예치금 자산과 사용자 페이머니 부채 분개가 균형을 이룹니다. | Must |
| FR-004 | 지갑 잔액을 조회합니다. | 가용·보류 잔액과 기준 시각을 반환합니다. | Must |
| FR-005 | 페이머니로 주문을 결제합니다. | 잔액 충분·한도 통과 시 한 번만 승인되고 원장과 Outbox가 원자적으로 기록됩니다. | Must |
| FR-006 | 결제를 조회합니다. | `paymentId` 또는 `orderId`로 금액·상태·취소 누적액을 확인합니다. | Must |
| FR-007 | 승인 결제를 전액 취소합니다. | 새 역분개를 만들고 원결제와 연결하며 중복 환불하지 않습니다. | Must |
| FR-008 | 지갑 거래내역을 조회합니다. | 커서 기반 페이지네이션과 안정적인 정렬을 제공합니다. | Must |
| FR-009 | 쓰기 요청을 멱등하게 처리합니다. | 동일 키·동일 본문은 기존 결과, 동일 키·다른 본문은 409입니다. | Must |
| FR-010 | Outbox 이벤트를 발행합니다. | 업무 커밋된 이벤트는 재시작 후에도 발행 대상에 남습니다. | Must |
| FR-011 | 소비 이벤트를 멱등하게 처리합니다. | 동일 `eventId` 재전달이 결과를 추가 생성하지 않습니다. | Must |
| FR-012 | 운영자가 거래 타임라인을 조회합니다. | 업무·원장·외부·이벤트 기록을 하나의 상관관계로 확인합니다. | Must |
| FR-013 | 승인 결제를 부분 취소합니다. | 누적 완료·처리중 취소액이 승인액을 초과하지 않습니다. | Should |
| FR-014 | 외부 결과 불명확 거래를 복구합니다. | `UNKNOWN`이 조회·웹훅·대사로 최종 상태에 수렴합니다. | Should |
| FR-015 | 사용자 간 송금을 처리합니다. | 출금·입금 분개가 하나의 원장 거래로 균형을 이룹니다. | Should |
| FR-016 | 판매자 정산을 계산·지급합니다. | 동일 결제가 중복 정산되지 않고 취소·수수료·조정을 반영합니다. | Should |
| FR-017 | 내부·외부 기록을 대사합니다. | 누락·상태·금액·중복·원장 차이를 분류합니다. | Should |
| FR-018 | 위험 규칙을 평가합니다. | `ALLOW`, `CHALLENGE`, `BLOCK`과 근거 규칙을 저장합니다. | Could |

## 4. 비기능 요구사항

| ID | 요구사항 | 검증 기준 |
|---|---|---|
| NFR-001 | 원장 정합성 | 모든 POSTED 거래에서 차변=대변입니다. |
| NFR-002 | 잔액 안전성 | 모든 완료 거래 후 가용 잔액이 0 이상입니다. |
| NFR-003 | 멱등성 | 동일 쓰기 요청 100회에 업무 효과가 1회입니다. |
| NFR-004 | 복구 가능성 | DB 커밋·발행·소비 경계에서 종료해도 최종 상태가 수렴합니다. |
| NFR-005 | 추적성 | `traceId`, 업무 ID, 원장 ID, 이벤트 ID를 연결할 수 있습니다. |
| NFR-006 | 감사성 | 운영자 중요 작업의 주체·사유·전후·결과가 남습니다. |
| NFR-007 | 보안 | 민감정보 비저장·마스킹, 최소 권한과 속도 제한을 적용합니다. |
| NFR-008 | 재현성 | 컨테이너 기반으로 테스트와 장애 시나리오를 반복 실행할 수 있습니다. |
| NFR-009 | 관측성 | 성공률, 오류 사유, UNKNOWN 체류, Outbox 지연, 불일치를 측정합니다. |
| NFR-010 | 성능 투명성 | 모든 성능 수치는 환경·데이터·부하 모델과 함께 기록합니다. |

## 5. 대표 수용 시나리오

아래 시나리오는 통합 테스트로 그대로 구현합니다.

### AC-001 정상 충전

**Given** 활성 지갑과 잔액이 충분한 Mock Bank 계좌가 있습니다.
**When** 사용자가 100,000원을 충전합니다.
**Then** 충전은 성공하고 지갑 잔액이 100,000원 증가하며 균형 잡힌 원장 거래와 Outbox 이벤트가 생성됩니다.

### AC-002 중복 결제

**Given** 50,000원 잔액과 동일한 `Idempotency-Key`가 있습니다.
**When** 30,000원 결제를 동시에 100회 요청합니다.
**Then** 결제와 원장 거래는 각각 한 건만 생성되고 모든 성공 응답은 동일한 `paymentId`를 반환합니다.

### AC-003 잔액 경합

**Given** 지갑 잔액이 50,000원입니다.
**When** 서로 다른 키로 40,000원 결제 두 건을 동시에 요청합니다.
**Then** 한 건만 승인되고 다른 건은 잔액 부족으로 실패하며 잔액은 10,000원입니다.

### AC-004 승인 후 응답 유실

**Given** Mock PG가 승인 후 응답을 유실하도록 설정되었습니다.
**When** 결제를 요청합니다.
**Then** ParityPay는 즉시 실패로 확정하지 않고 `UNKNOWN`으로 보존한 뒤 외부 조회 결과에 따라 멱등하게 확정합니다.

### AC-005 취소

**Given** 30,000원 승인 결제가 있습니다.
**When** 10,000원을 부분 취소합니다.
**Then** 원결제는 `PARTIALLY_CANCELED`, 취소는 `COMPLETED`가 되고 상쇄 분개가 새로 생성됩니다.

## 6. 권한 모델

| 역할 | 권한 |
|---|---|
| CUSTOMER | 본인 지갑, 충전, 결제, 취소와 거래내역 |
| MERCHANT | 본인 주문·지급예정·정산 내역 조회 |
| OPS_VIEWER | 거래·원장·대사·이벤트 읽기 |
| OPS_OPERATOR | 허용된 재조회·재처리·보류 작업 |
| OPS_APPROVER | 금액 보정과 고위험 운영 작업 승인 |
| SYSTEM | 배치, 이벤트 소비, 복구 작업 |

모든 조회·변경 API는 역할과 **리소스 소유권**을 함께 검사합니다. 소유권 검사 없는 조회 API를 만들지 않습니다.

## 7. 분석·운영 이벤트

- 충전·결제·취소 성공률과 실패 사유
- `UNKNOWN` 진입·해소와 체류시간
- 멱등성 중복 차단 건수
- 잔액 부족·한도·위험 차단 건수
- Outbox 발행 지연과 소비 중복 차단 건수
- 대사 불일치 유형과 미해결 금액
- 정산 실패·보류·재시도 건수

## 8. 릴리스 게이트

MVP는 Must 요구사항, `INV-001`부터 `INV-007`까지의 불변조건, 필수 통합·동시성·장애 테스트가 모두 통과해야 완료됩니다. 미측정 성능 수치는 릴리스 차단 사유가 아니지만 측정 방법과 기준선은 반드시 남깁니다.
