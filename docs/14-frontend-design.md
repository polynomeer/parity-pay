# ParityPay 프론트엔드 설계서 (DOC-14)

> **에이전트 지침**
> - **읽는 시점**: 프론트엔드를 구현하거나, 클라이언트가 지켜야 하는 계약을 확인할 때.
> - **이 문서가 정하는 것**: 무엇을 만드는가(앱 구분·화면 목록), 이 백엔드가 클라이언트에 강제하는 계약, 기술 선택과 근거, 마일스톤.
> - **이 문서가 정하지 않는 것**: 제품 범위(DOC-01·03), 업무 규칙(DOC-04), API 계약(DOC-08). 여기서는 참조만 하고 다시 정의하지 않습니다.
> - **강제 규칙**: §4의 클라이언트 계약은 서버의 불변조건과 짝을 이룹니다. 어기면 서버가 지키는 INV-004가 무의미해집니다. 화면을 추가할 때 §4를 먼저 읽습니다.

## 1. 현재 상태와 이 문서를 쓰는 이유

**프론트엔드는 없습니다.** 저장소에 `package.json`, HTML, JS/TS 파일이 하나도 없습니다. 지금까지
클라이언트는 `curl`, k6 스크립트, Swagger UI였습니다.

DOC-03은 MVP 제외 범위에 "복잡한 사용자용 프론트엔드"를 넣어 두었고, 그 판단은 MVP 기간 동안
옳았습니다. 백엔드가 증명하려던 것(장애 상황의 금융 정합성)은 화면 없이도 증명할 수 있었고,
실제로 실험 24종으로 증명했습니다. MVP는 끝났으므로 이 문서는 그 제외 항목을 **MVP 이후 확장**으로
다시 엽니다.

**그런데 화면을 붙이는 것은 장식이 아닙니다.** 이 백엔드는 결과를 모르는 상태(`UNKNOWN`), 지연되는
읽기 모델(프로젝션), 경합하는 취소 가능액을 그대로 드러냅니다. 이것들을 모르는 클라이언트는
**서버가 지키는 보장을 깨뜨립니다.** 재시도할 때마다 새 멱등 키를 만드는 클라이언트 앞에서는
INV-004("동일 업무 참조의 금융 효과는 정확히 1회")가 아무것도 막지 못합니다. 서버는 두 요청을
서로 다른 의도로 볼 수밖에 없기 때문입니다.

그러므로 이 문서의 절반(§4)은 화면이 아니라 **클라이언트가 지켜야 하는 계약**입니다.

## 2. 무엇을 만드는가

`docs/api/openapi.json`은 이미 `customer`와 `operations` 두 그룹으로 나뉘어 생성됩니다. 역할
모델도 갈라져 있습니다(`CUSTOMER`·`MERCHANT` / `OPS_VIEWER`·`OPS_OPERATOR`·`OPS_APPROVER`).
**앱을 둘로 나눕니다.**

| 앱 | 사용자 | API 그룹 | 성격 |
|---|---|---|---|
| **고객 앱** (`apps/web-customer`) | `CUSTOMER`, `MERCHANT` | `customer` | 쓰기 중심. 멱등성·불확실 상태를 정면으로 다룸 |
| **운영 콘솔** (`apps/web-ops`) | `OPS_*` | `operations` | 읽기 중심 + 고위험 쓰기. 근거·승인·감사 |

나누는 이유는 취향이 아닙니다.

- **노출면이 다릅니다.** 운영 콘솔은 전체 거래 타임라인, 원장 대조, 지급 실행을 다룹니다. 고객
  앱과 같은 번들에 넣으면 고객 브라우저로 그 코드가 내려갑니다.
- **배포 주기가 다릅니다.** 고객 앱은 사고 없이 자주, 운영 콘솔은 사고 중에 급하게 바뀝니다.
- **인증 정책이 다릅니다.** 운영 콘솔은 짧은 세션과 재인증이 맞고, 고객 앱은 그렇지 않습니다.

### 우선순위

**고객 앱을 먼저 만듭니다(FE-M1).** 운영 콘솔이 포트폴리오로는 더 눈에 띄지만, 클라이언트가
지켜야 하는 계약(§4)이 전부 고객 앱 쪽에 있습니다. 그 계약을 구현하고 시험해 보지 않으면
백엔드의 정합성 주장은 "서버만 지키면 되는 것"으로 남습니다. 운영 콘솔은 대부분 읽기라 계약
위험이 낮고, 뒤로 미뤄도 잃는 것이 적습니다.

## 3. 이 백엔드가 클라이언트에 강제하는 것

여기가 이 문서의 핵심입니다. 각 항목은 **어기면 무엇이 깨지는지**와 함께 적습니다.

### FE-001 멱등 키는 클라이언트가 소유하고, 의도가 끝날 때까지 재사용합니다

서버는 `principalId + operation + Idempotency-Key`로 요청을 식별합니다(DOC-09). 키를 만드는 쪽은
클라이언트이므로, **키의 수명을 관리하는 책임도 클라이언트에 있습니다.**

- 키는 **사용자의 의도 하나**에 하나입니다. "결제하기를 눌렀다"가 의도이고, 그 뒤의 모든 재시도는
  같은 의도입니다.
- 키는 요청을 보내기 **전에** 만들어 저장합니다(`localStorage`). 응답을 받고 만들면, 응답을 못
  받은 경우에 키가 없습니다.
- 키는 **종결 상태를 확인한 뒤에만** 버립니다. 종결은 `APPROVED`·`FAILED`·`CANCELED`이며,
  `UNKNOWN`과 네트워크 오류는 종결이 아닙니다.

**어기면**: 네트워크 오류 후 새 키로 재시도하면 서버는 별개의 결제로 처리합니다. 이중 청구입니다.
INV-004는 같은 키에 대해서만 성립합니다.

**이 규칙이 특히 중요한 이유가 하나 더 있습니다.** 고객 API에는 `orderId`로 결제를 찾는 경로가
없습니다(`GET /api/v1/payments/{paymentId}`만 있고, `orderId` 조회는 운영자 타임라인에만
있습니다). 즉 **응답을 못 받아 `paymentId`를 모르면, 같은 멱등 키로 다시 POST하는 것이 결과를
알아낼 유일한 방법입니다.** 키를 잃어버린 클라이언트는 자기 결제를 영원히 찾지 못합니다.

### FE-002 202와 `UNKNOWN`은 실패가 아닙니다

`POST /api/v1/payments`는 결과를 모를 때 **202 Accepted**와 `Location: /api/v1/payments/{id}`를
줍니다. 충전(`POST /api/v1/top-ups`)도 `REQUESTED`·`PROCESSING`·`UNKNOWN`에서 202입니다.

| 응답 | 의미 | 화면 |
|---|---|---|
| 201 | 확정 성공 | 성공 |
| 200 (충전 `FAILED`) | 확정 실패 | 실패 사유 |
| **202** | **아직 모름** | **"확인 중" — 실패로 표시하지 않습니다** |
| 409 | 업무 규칙 거절(잔액 부족 등) | 사유와 함께 거절 |
| 5xx·네트워크 오류 | 모름 | **"확인 중" — FE-001의 키로 재확인** |

**어기면**: 202를 오류로 처리해 "결제 실패"를 띄우면, 사용자는 다시 결제합니다. 서버는 이미
승인했을 수 있습니다. ADR-007이 서버에서 막은 이중 청구를 클라이언트가 되살립니다.

**"다시 시도" 버튼을 202 화면에 두지 않습니다.** 대신 `Location`을 폴링합니다.

### FE-003 결제 제출 상태 기계

FE-001·FE-002를 하나의 상태 기계로 고정합니다. 화면 구현은 이 표를 따릅니다.

```text
                   ┌──────────┐
                   │   idle   │
                   └────┬─────┘
            제출(키 생성·저장)
                   ┌────▼─────┐
        ┌──────────│submitting│──────────┐
        │          └────┬─────┘          │
     201│               │202          409│
        │               │  5xx/네트워크   │
   ┌────▼────┐     ┌────▼─────┐    ┌─────▼─────┐
   │approved │     │confirming│    │ rejected  │
   │ (키 폐기)│     │ (키 유지) │    │ (키 폐기) │
   └─────────┘     └────┬─────┘    └───────────┘
                        │ GET 폴링 (지수 백오프)
                        │
          ┌─────────────┼─────────────┐
     APPROVED        UNKNOWN        FAILED
          │         (계속 폴링)          │
     ┌────▼────┐                  ┌────▼────┐
     │approved │                  │ failed  │
     └─────────┘                  └─────────┘
```

**폴링 정책은 측정으로 정했습니다(M-011).** 확정까지 걸리는 시간은 부하가 아니라 서버 설정이
정하며, 편차가 1초 미만입니다.

| 경로 | 확정까지 (중앙값 / p95) |
|---|---:|
| 응답만 유실 → 성공 확정 | 34.9초 / 35.2초 |
| 요청 전 단절 → 실패 확정 | 45.0초 / 45.4초 |

여기서 나오는 규칙입니다.

- **첫 30초 동안은 결과가 바뀔 수 없습니다.** 복구 작업의 `grace`가 30초라 그 전에는 대상이
  되지도 않습니다. 그러니 250 ms 간격으로 두드릴 이유가 없습니다 — **2초 간격**이면 충분하고,
  서버에 헛일을 덜 시킵니다.
- **한계는 90초입니다.** 관측된 최악(45.4초)의 두 배쯤이고, 부하가 있을 때 늘어날 여지를 둡니다.
  ~~30초~~는 처음에 예시로 적었던 값인데 **틀렸습니다.** `grace`가 30초이므로 30초에서 포기하면
  **매번 답이 오기 직전에 포기합니다.**
- 한계를 넘어도 **실패로 바꾸지 않고** "처리 중"을 유지한 채 화면을 떠날 수 있게 합니다. 서버의
  복구 작업이 확정하고, 사용자는 나중에 결과를 봅니다.
- `confirming` 중 앱을 껐다 켜도 저장된 키로 복구합니다. 이것이 키를 `localStorage`에 두는 이유입니다.
- `rejected`(409)만 키를 즉시 버립니다. 업무 규칙 거절은 종결이기 때문입니다.

### FE-004 거래내역은 지연됩니다

`GET /api/v1/wallets/{walletId}/transactions`는 **Kafka 소비자가 만드는 프로젝션**을 읽습니다
(ADR-006). 결제가 201로 성공한 직후에도 목록에 없을 수 있습니다.

- 목록에 없다는 것이 "일어나지 않았다"가 아닙니다.
- 쓰기 응답으로 받은 결과를 **낙관적으로 먼저 보여 주고**, 프로젝션이 따라오면 대체합니다.
- 낙관적 항목은 "반영 중" 표시를 답니다. 조용히 섞으면 사용자는 목록을 진실로 믿습니다.

**어기면**: 결제 직후 목록이 비어 보여 사용자가 다시 결제합니다.

### FE-005 잔액은 스냅샷입니다

`GET /api/v1/wallets/{walletId}`는 `available`, `pending`, `currency`, **`asOf`**를 돌려줍니다.
원장이 진실이고 이 값은 조회용 스냅샷입니다(ADR-008).

- `asOf`를 화면에 표시합니다. 언제 기준인지 밝히지 않은 잔액은 오해를 만듭니다.
- 클라이언트에서 잔액을 계산하지 않습니다. 결제 후 `available - amount`를 그려 놓지 않고 다시
  조회합니다. 동시 거래가 있으면 그 뺄셈은 틀립니다.
- `GET .../ledger-verification`은 **운영자 전용**입니다(`OPS_*` 권한). 고객 앱에서 호출하지 않습니다.

### FE-006 취소 가능액은 경합합니다

`PaymentResponse.cancellableAmount`는 조회 시점의 값입니다. 부분 취소는 예약→확정 2단계이므로
(DOC-09), 화면을 그린 뒤 제출하기 전에 다른 요청이 그 액수를 가져갈 수 있습니다.

- `409 CANCELLATION_AMOUNT_EXCEEDED`는 **버그가 아니라 정상 결과**입니다. 오류 화면 대신 최신
  가능액을 다시 조회해 보여 줍니다.
- 취소 금액 입력의 상한은 화면 그린 시점의 값이지만, 서버가 최종 판정자입니다.

### FE-007 금액은 정수입니다

KRW는 원 단위 정수입니다(`long`/`BIGINT`).

- 화면·계산 어디에서도 부동소수점 연산을 하지 않습니다. 표시할 때만 `Intl.NumberFormat`으로
  포맷합니다.
- JSON의 `long`은 JS `number`로 들어옵니다. `Number.MAX_SAFE_INTEGER`는 약 9.0×10^15원이라 현실
  금액에서는 안전하지만, **경계가 존재한다는 사실을 알고 있습니다.** 합계를 클라이언트에서
  누적하지 않는 이유이기도 합니다. 합계가 필요하면 서버 값을 씁니다.

### FE-008 토큰 회전은 단일 비행(single-flight)을 요구합니다

액세스 토큰 15분, 리프레시 토큰은 **교환할 때마다 회전**합니다(Phase 7).

- 리프레시 토큰은 `HttpOnly` 쿠키에 있고 브라우저가 자동으로 붙입니다(ADR-010). 클라이언트가
  값을 만지지 않는다고 해서 이 문제가 사라지지는 않습니다 — 쿠키는 하나뿐이라 동시에 두 번
  교환하면 늦은 쪽이 이미 회전된 값을 보냅니다.
- 회전은 이전 리프레시 토큰을 무효로 만듭니다. 두 요청이 동시에 401을 만나 각자 refresh하면
  **뒤늦은 쪽이 이미 무효가 된 토큰으로 시도해 로그아웃됩니다.**
- 그러므로 refresh는 **앱 전체에서 하나만** 진행합니다. 진행 중인 refresh가 있으면 다른 요청은
  그 결과를 기다립니다. 여러 탭을 쓰면 탭 간에도 조율이 필요합니다(`BroadcastChannel` 또는
  저장소 잠금).
- 비밀번호를 바꾸면 **세션이 전부 철회**됩니다. 어느 화면에서든 갑작스러운 401을 견뎌야 합니다.
- 로그인 실패가 누적되면 계정이 잠깁니다. 잠금은 "비밀번호 틀림"과 다른 문구여야 합니다.

### FE-009 오류 코드 표시 규칙

서버는 `ErrorCode` 13종과 `traceId`를 함께 줍니다. 원문 메시지를 그대로 노출하지 않습니다.

| 코드 | 사용자에게 | 비고 |
|---|---|---|
| `INSUFFICIENT_BALANCE` | 잔액 부족 | 잔액을 응답에 담지 않습니다(정책). 화면에서 잔액을 다시 조회해 보여 줍니다 |
| `LIMIT_EXCEEDED` | 한도 초과 | |
| `CANCELLATION_AMOUNT_EXCEEDED` | 취소 가능액 초과 | FE-006 |
| `IDEMPOTENCY_KEY_REUSED` | 요청이 이전과 다릅니다 | **클라이언트 버그 신호**입니다. 같은 키에 다른 본문을 보냈다는 뜻이므로 개발 중에는 크게 드러냅니다 |
| `WALLET_NOT_ACTIVE`, `INVALID_STATE_TRANSITION` | 지금은 할 수 없는 작업 | |
| `RISK_BLOCKED` | 승인되지 않음 | 사유를 자세히 알리지 않습니다 |
| `RESULT_PENDING` | **오류로 표시하지 않습니다** | FE-002의 "확인 중" |
| `EXTERNAL_TEMPORARY_ERROR` | 일시적 문제, 잠시 후 재확인 | 재시도는 같은 키로만 |
| `INVALID_AMOUNT`, `INVALID_REQUEST` | 입력값 문제 | 필드 단위로 표시 |
| `RESOURCE_NOT_FOUND` | 찾을 수 없음 | |
| `INTERNAL_ERROR` | 일반 안내 + `traceId` | 내부 메시지는 절대 노출하지 않습니다 |

`traceId`는 모든 오류 화면에 작게 노출합니다. 문의가 들어왔을 때 운영자가 타임라인을 여는 열쇠입니다.

| SCR-05 | 충전 | `POST /top-ups`, `GET /top-ups/{id}` | FR-003, FE-001~003 |
| SCR-06 | 결제 | `POST /payments`, `GET /payments/{id}` | FR-005, FE-001~003 |
| SCR-07 | 결제 상세·취소 | `POST /payments/{id}/cancellations` | FR-006·007, FE-006 |
| SCR-08 | 거래내역 | `GET /wallets/{id}/transactions` | FR-008, FE-004 |
| SCR-09 | 구매확정 | `POST /payments/{id}/confirmation` | 정산 트리거 |
| SCR-10 | 비밀번호 변경 | `POST /auth/password` | FE-008 |
| SCR-11 | 판매자 정산 | `GET /merchant/settlements` | `MERCHANT` 전용 |

**SCR-08 거래내역**은 커서 페이지네이션입니다. `nextCursor`는 **불투명 문자열**이므로 파싱하거나
직접 만들지 않습니다. M-008에서 110만 건에서도 깊이와 무관하게 0.06~0.09 ms인 것을 확인했으므로,
무한 스크롤이 성능 문제를 만들지 않습니다.

**OPS-01 타임라인이 이 콘솔의 중심 화면입니다.** 고객이 어떤 식별자를 들고 오든(주문 ID·결제 ID)
하나의 입력으로 시작합니다. 다른 화면은 대부분 타임라인으로 들어가는 입구입니다.

### 운영 콘솔의 추가 규칙

- **FE-010 이중 승인은 화면에서도 강제합니다.** 보정 분개(OPS-06)는 요청자와 승인자가 달라야
  하고 서버가 거부합니다. 화면은 로그인한 운영자가 자기 요청을 승인하려 할 때 **버튼을 누르기
  전에** 막습니다. 서버가 막으니 괜찮다고 두면, 운영자는 실패한 뒤에야 알게 됩니다.
- **FE-011 사유는 선택 입력이 아닙니다.** 보정·해결·보류는 사유가 필수이고 감사 로그에 남습니다.
  기본값이나 자동 채움을 넣지 않습니다.
- **FE-012 금액을 직접 고치는 화면은 없습니다.** 서버에 그런 API가 없습니다. 화면도 만들지
  않습니다. 보정은 새 분개로만 합니다.
- **FE-013 재처리는 순서를 뒤집을 수 있습니다.** Outbox 재처리(OPS-08)는 뒤 형제가 이미 발행된
  경우 순서가 역전됩니다. 서버 응답이 그 사실을 알려 주므로 확인 대화상자에 그대로 보여 줍니다.

## 6. 기술 선택

| 항목 | 선택 | 근거 |
|---|---|---|
| 언어 | TypeScript (strict) | 금액·상태 열거형을 타입으로 고정합니다 |
| 프레임워크 | React 19 + Vite | SSR·SEO가 필요 없습니다. 토큰을 다루는 SPA이고, 빌드 산출물은 정적 파일입니다 |
| 라우팅 | React Router | 역할별 경로 보호가 단순합니다 |
| 서버 상태 | TanStack Query | **재시도 정책을 명시적으로 통제할 수 있는 것이 선택 이유입니다**(§7) |
| 폼 | React Hook Form + Zod | 금액 입력 검증을 서버 규칙과 같은 자리에 둡니다 |
| API 타입 | `openapi-typescript`로 `docs/api/openapi.json`에서 생성 | §8 |
| 스타일 | Tailwind CSS | 두 앱이 공유하는 토큰만 정의합니다 |
| 테스트 | Vitest + Testing Library + MSW + Playwright | §9 |

**Next.js를 쓰지 않는 이유**: 서버 렌더링이 필요 없고, 서버 컴포넌트를 도입하면 토큰을 어디에
두는가가 복잡해집니다. 이 앱의 어려움은 렌더링이 아니라 **불확실한 쓰기**입니다.

### 배치

```text
apps/web-customer/     고객 앱
apps/web-ops/          운영 콘솔
packages/api-client/   생성된 타입 + fetch 래퍼 + 멱등 키 관리 (두 앱이 공유)
packages/ui/           공용 표시 규칙 (금액·시각·상태 배지)
```

Gradle 멀티모듈 옆에 pnpm 워크스페이스를 둡니다. 백엔드 빌드와 섞지 않습니다 — `./gradlew build`가
프론트엔드 때문에 느려지면 안 됩니다. CI는 변경 경로에 따라 나눠 돌립니다.

## 7. 재시도 정책 — 라이브러리 기본값이 위험한 지점

TanStack Query의 기본 동작은 **쿼리를 3회 재시도**하는 것입니다. 뮤테이션은 기본적으로 재시도하지
않지만, 편의를 위해 `retry: 3`을 켜는 것이 흔합니다.

**금융 쓰기에 그것을 켜면 안 됩니다.** 정확히는, 켜더라도 **같은 멱등 키로만** 재시도해야 합니다.
`packages/api-client`가 이 규칙을 코드로 강제합니다.

- 쓰기 함수는 멱등 키 없이 호출할 수 없는 시그니처를 갖습니다. 키를 인자로 요구합니다.
- 재시도는 래퍼 안에서만 일어나고, 래퍼는 **처음 만든 키를 그대로** 다시 씁니다.
- 화면 코드가 `fetch`를 직접 부르지 못하게 ESLint 규칙으로 막습니다.

읽기(GET)는 자유롭게 재시도해도 안전합니다.

## 8. API 계약 고정

저장소에는 이미 `docs/api/openapi.json` 스냅샷과 이를 비교하는 테스트가 있습니다(Phase 8).
**프론트엔드 타입을 이 스냅샷에서 생성합니다.**

```bash
pnpm --filter @paritypay/api-client generate   # openapi.json → TypeScript
```

이렇게 하면 백엔드가 응답 필드를 바꿨을 때 **프론트엔드 빌드가 깨집니다.** 지금은 스냅샷 테스트가
"바뀌었다"를 알려 주지만, 누가 영향을 받는지는 알려 주지 않습니다. 생성된 타입이 그 연결을 만듭니다.

생성물은 커밋합니다. 빌드 시점에 생성하면 백엔드 없이 프론트엔드를 빌드할 수 없게 됩니다.

## 9. 테스트 전략

DOC-10의 원칙(금융 분기 전수 검증 우선)을 클라이언트에도 적용합니다. **§3의 계약마다 시험이
하나씩 있습니다.**

| 시험 | 확인하는 것 | 대응 |
|---|---|---|
| 네트워크 실패 후 재시도가 **같은 키**를 보낸다 | 요청 두 건의 `Idempotency-Key` 헤더가 동일 | FE-001 |
| 202 응답이 오류 화면을 만들지 않는다 | "실패" 문구가 없고 폴링이 시작됨 | FE-002 |
| 폴링 중 새로고침해도 복구된다 | 저장된 키로 상태를 다시 확인 | FE-001·003 |
| 409는 키를 폐기한다 | 다음 제출이 새 키를 만듦 | FE-003 |
| 결제 직후 목록에 없어도 낙관적 항목이 보인다 | "반영 중" 표시 | FE-004 |
| 동시 401 두 건이 refresh를 한 번만 호출한다 | 요청 수 검증 | FE-008 |
| 자기 요청을 자기가 승인할 수 없다 | 버튼 비활성 + 사유 표시 | FE-010 |

- API는 **MSW**로 대역을 세웁니다. 202·409·네트워크 단절을 시나리오로 만들 수 있어야 합니다.
- E2E(Playwright)는 실제 백엔드와 Mock Bank·Mock PG를 띄우고 돌립니다. 장애 주입 API로 **응답
  유실을 실제로 만들어** FE-002·003을 종단 확인합니다. 이 프로젝트가 백엔드에서 한 것과 같은
  방식입니다.
- 시험이 유효한지 확인합니다. 키 재사용 로직을 일부러 깨뜨렸을 때 해당 시험이 실패하는 것을
  보고 나서 통과를 신뢰합니다.

## 10. 보안

- **토큰 저장**: 리프레시 토큰은 `HttpOnly` 쿠키에 있습니다(2026-09-10, [ADR-010](adr/010-refresh-token-cookie.md)).
  자바스크립트가 읽을 수 없고 클라이언트 코드에 값이 나타나지 않습니다. `localStorage`에 남는 것은
  **액세스 토큰뿐**이며 15분짜리입니다.
  - 대가가 하나 붙었지만 배포 형태로 해결했습니다: `SameSite=Lax` 쿠키는 교차 사이트 요청에
    실리지 않으므로 API와 화면이 같은 사이트여야 하는데, [ADR-011](adr/011-deployment-shape.md)이
    **각 앱이 자기 오리진에서 `/api`를 프록시**하게 해서 교차 오리진 요청 자체를 없앴습니다.
    §2의 "두 앱을 다른 오리진에"는 그대로입니다.
  - **다만 포트만 다른 것으로는 부족합니다.** 쿠키는 포트를 구분하지 않아 `localhost:8181`의
    리프레시 쿠키가 `localhost:8182`로도 갑니다. 그래서 개발·E2E·배포 모두 `app.localhost`·
    `ops.localhost`처럼 호스트이름을 가릅니다(ADR-011). E2E가 쿠키가 건너가지 않는 것을 확인합니다.
  - 액세스 토큰을 메모리로 옮기는 것은 아직 하지 않았습니다. 새로고침마다 로그인하게 되므로
    조용한 재발급이 먼저 필요합니다.
- 로그·오류 화면에 토큰·비밀번호·전체 계좌번호를 남기지 않습니다. 서버 규칙과 같습니다.
- 운영 콘솔은 별도 오리진에 배포하고 짧은 세션을 씁니다.
- CSP를 적용하고 인라인 스크립트를 쓰지 않습니다.

## 11. 만들지 않는 것

- **비밀번호 재설정 완료 화면**: 서버에 재설정 토큰은 있지만 **전달 어댑터(이메일·SMS)가
  없습니다.** 사용자가 토큰을 받을 방법이 없으므로 화면을 만들어도 끝까지 동작하지 않습니다.
  전달 어댑터가 생긴 뒤에 만듭니다.
- **웹훅 수신 화면**: 기관이 서버로 보내는 경로입니다. 클라이언트와 무관합니다.
- **실시간 알림(WebSocket/SSE)**: 서버에 그런 채널이 없습니다. 폴링으로 충분한지 먼저 확인하고,
  부족하다는 근거가 생기면 그때 서버와 함께 설계합니다.
- **금액 수정·잔액 직접 조정 화면**: 그런 API가 없고, 있어서도 안 됩니다.

## 13. 열린 질문

측정하거나 결정하지 않은 것을 추측으로 채우지 않습니다.

1. ~~**리프레시 토큰을 `httpOnly` 쿠키로 옮길 것인가.**~~ 2026-09-10에 옮겼습니다
   ([ADR-010](adr/010-refresh-token-cookie.md)). CSRF는 `SameSite=Lax`가 막고 별도 CSRF 토큰을
   두지 않았습니다. **남은 부분**: 액세스 토큰은 여전히 `localStorage`에 있습니다(15분).
2. **`orderId`로 결제를 조회하는 고객 API를 열 것인가.** 지금은 멱등 키가 유일한 복구 경로입니다
   (FE-001). 키를 잃은 사용자를 위한 경로가 필요한지 판단하지 않았습니다.
3. ~~**폴링 간격과 한계.**~~ 2026-09-09에 쟀습니다(M-011). 2초 간격·90초 한계로 정했고 근거는
   §3 FE-003에 있습니다. **남은 부분**: 미확정이 수백 건 쌓였을 때의 분포는 재지 않았습니다
   (복구 배치가 `batch-size: 50`이라 뒤쪽 건은 더 기다릴 수 있습니다).
4. **운영 콘솔의 재인증 주기.** 고위험 작업 앞에서 비밀번호를 다시 물을 것인지 정하지 않았습니다.
5. ~~**지갑 경로의 `me` 전환.**~~ 닫혔습니다(2026-09-10, FE-M1). 검토할 것도 없었습니다 —
   `walletId`가 가입 응답에만 있고 토큰에도 없어서, **다른 기기에서 로그인하면 자기 지갑을 조회할
   수단이 아예 없었습니다.** `GET /api/v1/wallets/me`를 열었고 클라이언트는 지갑 ID를 보관하지
   않습니다. "노출이 필요한가"가 아니라 "없으면 동작하지 않는" 문제였습니다.
