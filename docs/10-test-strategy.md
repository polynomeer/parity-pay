# ParityPay 테스트 전략서 (DOC-10)

> **에이전트 지침**
> - **읽는 시점**: 테스트를 작성하거나 PR을 준비할 때.
> - **이 문서가 정하는 것**: 테스트 레벨별 대상, 필수 시나리오(`T-`, `F-`), 성능 측정·보고 원칙, CI 품질 게이트.
> - **강제 규칙**: 금융 로직 변경에는 불변조건 테스트가 함께 있어야 합니다. 통합 테스트는 Testcontainers로 실제 PostgreSQL·Kafka를 사용하며 인메모리 대체를 하지 않습니다. 실패한 테스트를 비활성화해 통과시키지 않습니다. 성능 수치는 측정 없이 기록하지 않습니다.

## 1. 목표

ParityPay 테스트는 코드 라인보다 금융 불변조건, 상태 전이, 중복·동시성·장애 복구와 운영 추적성을 검증합니다. 테스트 결과는 요구사항 ID와 연결하고 재현 가능한 환경을 제공합니다.

## 3. 단위 테스트

- `Money`의 통화 일치, 범위와 산술 오버플로
- Payment와 Cancellation의 허용·금지 상태 전이
- 취소 가능액과 동시 취소 예약 계산
- 충전·결제·취소·송금·정산 분개 생성
- 차변·대변 합계 검증
- 정산 수수료·조정·순액 계산
- 위험 규칙의 경계값
- 오류 코드 매핑과 민감정보 마스킹

## 4. 속성 기반 테스트

임의의 충전, 결제, 취소, 송금과 역분개 시퀀스를 생성합니다.

### 속성

- `INV-001`: 각 POSTED 원장 거래는 균형을 이룹니다.
- `INV-003`: 가용 잔액은 음수가 되지 않습니다.
- `INV-004`: 동일 업무 참조는 한 번만 금융 효과를 냅니다.
- `INV-005`: 취소 완료·처리중 합계는 승인액 이하입니다.
- `INV-006`: 확정 원장은 이전 스냅샷과 비교해 변경되지 않습니다.
- `INV-010`: 원장 재생 잔액과 스냅샷이 일치합니다.

실패한 임의 시퀀스는 seed와 최소 반례를 저장해 회귀 테스트로 승격합니다.

## 7. 성능 테스트

### 워크로드

- 서로 다른 지갑 결제: 병렬 확장 기준선
- 동일 지갑 결제: 잠금·조건부 갱신 경합
- 읽기 80%·쓰기 20% 혼합 거래내역
- Outbox 대량 적체 후 복구
- 정산 배치와 API 동시 실행
- 대사 대량 파일 또는 레코드 비교

### 측정값

- 처리량, p50·p95·p99, 오류율
- 잔액 갱신 충돌·재시도율
- DB CPU·I/O·락 대기·slow query·커넥션 풀
- Outbox 최고·평균 지연과 backlog
- 브로커 consumer lag
- GC pause, heap, thread pool과 외부 호출 latency

### 보고 원칙

- 장비·컨테이너 제한·JVM 옵션·데이터 규모를 기록합니다.
- warm-up과 측정 구간을 분리합니다.
- 최소 3회 실행하고 중앙값과 편차를 제공합니다.
- 기준선과 변경 후를 같은 조건에서 비교합니다.
- 실패 요청을 제외하고 지연을 계산하지 않습니다.

## 8. 계약 테스트

- OpenAPI 요청·응답 예시와 구현을 검증합니다.
- 이벤트는 타입·버전마다 JSON Schema를 두고
  (`modules/shared-kernel/src/main/resources/events/schema/`) 기록 시점에 봉투 전체를 검사합니다.
  검사는 테스트·로컬 프로필에서만 켜므로, 계약을 어긴 이벤트를 만드는 흐름은 그 흐름의 테스트가
  실패합니다. 스키마를 일부러 깨고 돌려 보면 15개 테스트 클래스가 실패합니다(빈 게이트가 아님).
- payload에 선언하지 않은 필드는 거부합니다. 필드가 조용히 늘어나면 소비자 계약이 바뀐 것을
  아무도 보지 못한 채 배포됩니다.
- 코드의 이벤트 타입 상수, 스키마 파일, 명세서 카탈로그 표가 일치하는지 `EventCatalogTest`가
  검사합니다.
- Mock Bank·PG의 성공, 명시 실패, 타임아웃, 조회 응답 계약을 고정합니다.
- 이벤트 필드 삭제·타입 변경은 CI에서 차단합니다.

## 10. 테스트 데이터

- 고정 fixture보다 빌더와 명시적 시나리오를 우선합니다.
- 사용자, 지갑, 판매자와 외부 계좌 ID를 테스트마다 격리합니다.
- 시간 의존 로직은 `Clock`을 주입합니다.
- 랜덤 테스트는 seed를 출력합니다.

| 게이트 | 이유 |

### 정적 분석

포맷은 Spotless + palantir-java-format입니다. google-java-format 대신 palantir를 쓰는 이유는
Javadoc입니다. 이 저장소의 주석은 한국어 산문인데 google-java-format은 Javadoc 문단을 한 줄로
이어 붙이고, 한글 폭을 1로 세므로 140자짜리 줄이 됩니다. palantir는 Javadoc을 건드리지 않습니다.

린터는 Error Prone이며 다음 검사를 **오류**로 올렸습니다. 경고로 두면 로그에만 쌓입니다.

| 검사 | 막는 것 |
|---|---|
| `UnusedVariable`, `UnusedMethod` | 지우다 만 필드·메서드·매개변수 |
| `StringSplitter` | 뒤쪽 빈 칸을 조용히 버리는 `String.split(String)` |
| `StringCaseLocaleUsage` | 기본 로케일에 따라 결과가 달라지는 대소문자 변환 |
| `IntLongMath` | int로 계산해 long에 담는 코드 (금액에서 조용히 넘칩니다) |
| `MissingOverride` | `@Override` 없는 재정의 |
| `ReturnValueIgnored` | 버리면 안 되는 반환값 |
| `MissingSummary` | 공개 API Javadoc에 요약문이 없는 경우 |

JPA 엔티티에는 `@SuppressWarnings("UnusedVariable")`이 붙어 있습니다. 감사 시각과 `@Version`
필드는 Hibernate가 리플렉션으로만 읽으므로 "쓰지 않는 필드"로 보입니다.

### 벤치마크

`BalanceStrategyBenchmarkTest`는 `@Tag("benchmark")`로 기본 실행에서 제외합니다. 여러 라운드를
돌아 몇 분이 걸리고 결과가 실행 환경에 민감해 PR 게이트로 적합하지 않습니다. 주 1회
[benchmark 워크플로](../.github/workflows/benchmark.yml)가 실행하고 원본 결과를 아티팩트로
남깁니다. 로컬에서는 `./gradlew test -PincludeBenchmarks`로 켭니다.

커버리지 100%를 목표로 삼기보다 핵심 금융 분기와 상태 전이를 100% 검증 대상으로 삼습니다. 전체 커버리지 수치는 보조 지표로 공개합니다.

## 12. 테스트 결과 기록

각 결과에는 커밋 SHA, 환경, 실행 명령, 시작·종료 시각, 데이터 seed, 성공·실패와 증거 경로를 기록합니다. 수동으로 수정한 그래프만 남기지 않고 원본 결과 파일을 함께 보존합니다.
