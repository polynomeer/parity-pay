# ADR-014 외부기관 호출을 타임아웃·벌크헤드·차단기로 격리함

- Status: Accepted
- Decided: 2026-09-16
- Date: 2026-09-16

> **에이전트 영향**: 외부 PG 호출은 전부 `PgCallGuard`를 지납니다. 어댑터에서 `MockPgClient`를 직접 부르지
> 않습니다. 장치가 거절하면 `PgCallRejectedException`이 나가고 그것은 **요청이 나가지 않았다**는 뜻입니다 —
> 호출자는 그것을 `UNKNOWN`이 아니라 알려진 실패(`FAILED`, 사유 `CIRCUIT_OPEN`·`BULKHEAD_FULL`·
> `RATE_LIMITED`)로 확정합니다. 타임아웃은 여전히 `UNKNOWN`입니다(ADR-007). **승인 재시도를 켜지
> 않습니다.** `paritypay.mock-pg.resilience.retry`는 실험 전용이고 기본값 `false`를 바꾸지 않습니다.

## Context

외부기관 호출에는 읽기 타임아웃(3초, `MockPgProperties`)과 미확정 복구(ADR-007)가 있었지만, **기관이 느려졌을
때 우리 프로세스가 어떻게 되는가**는 재 본 적이 없었습니다. 알려진 위험은 셋입니다.

1. 느린 기관이 요청 스레드를 붙잡으면 기관과 무관한 API(잔액 조회)까지 함께 멈춥니다.
2. 기관이 죽어 있는 동안 들어오는 결제마다 타임아웃까지 기다렸다가 미확정으로 쌓이고, 복구 작업이
   존재하지 않는 기록을 세 번씩 묻습니다.
3. 타임아웃 뒤 재시도를 붙이면 기관에 가는 요청이 배수로 늘고, 승인이면 이중 청구입니다.

이 프로젝트는 가상 스레드를 쓰고(`spring.threads.virtual.enabled`) 외부 호출을 DB 트랜잭션 밖에서 하므로
1번은 "이론상" 덜 위험하지만, 이론이었습니다. reports/11 M-019~M-023이 다섯 조건을 실측했고 이 ADR은 그
결과로 결정한 것입니다.

## Decision

외부 PG 호출 앞에 격리 장치를 두고 **기본값으로 켭니다.** 순서는 바깥에서 안으로 리미터 → 벌크헤드 →
차단기 → 호출입니다.

| 장치 | 기본값 | 막는 것 | 근거 |
|---|---|---|---|
| 읽기 타임아웃 | 3초 (기존) | 느린 기관이 호출을 무한정 붙잡는 것 | M-019 |
| 벌크헤드 (세마포어) | 켬, 동시 50, 대기 0 | 느린 기관이 프로세스 전체를 잠식하는 것 | M-019·M-023 |
| 차단기 | 켬, COUNT 윈도 20, 최소 10건, 실패율 50%, OPEN 10초, HALF_OPEN 3건 | 죽은 기관 앞에서 요청마다 타임아웃까지 기다리는 것 | M-021 |
| 리미터 | **끔** (켜면 TOKEN_BUCKET, 50/s) | 기관 TPS 상한 초과 | M-022 |
| 재시도 | **끔 — 실험 전용** | (켜면) 없음. 요청 증폭과 이중 청구를 만듭니다 | M-020, ADR-007 |

### 거절은 미확정이 아닙니다

장치가 거절한 호출은 기관에 도달하지 않았습니다. 그래서 새 예외 `PgCallRejectedException`으로 구분하고,
`PaymentService`·`PaymentCancellationService`는 그것을 `DECLINED`(사유 = 거절 이유)로 확정합니다. 결제는
`FAILED`, 응답은 201에 `failureReason`이 실립니다. 미확정으로 두면 차단기가 열린 동안의 결제 전부가
복구 작업의 조회 대상이 되어, 존재하지 않는 기록을 "없음" 3회 확인할 때까지 45초씩 기다립니다(M-011).

타임아웃(`PgUnknownResultException`)은 그대로 `UNKNOWN`입니다. 차단기는 타임아웃을 **실패로 셉니다** —
결과를 모르는 호출이 절반이면 기관은 사실상 죽은 것이고, 그때 새 요청을 보내 봐야 미확정만 늘립니다.

### 차단기가 열린 동안 들어온 결제의 운명

즉시 `FAILED(CIRCUIT_OPEN)`, HTTP 201, 기관 도달 0건, 미확정 0건. 클라이언트는 새 시도(새 멱등 키)로
다시 결제할 수 있고, 같은 키로 재요청하면 저장된 `FAILED` 응답을 받습니다. 돈은 어디에도 움직이지
않았습니다 — M-021이 거절된 결제 전부를 기관 기록과 대조해 확인했습니다.

### 재시도를 붙이지 않는 이유

M-020: 타임아웃 뒤 3회 재시도는 기관이 받는 요청을 클라이언트 요청의 3배로 만들었고, 기관이 외부 키로
멱등하지 않았다면 그것이 곧 세 번의 청구입니다. 지터는 요청을 시간 축으로 펼 뿐 총량을 줄이지 않습니다.
설계는 재시도 대신 미확정 보존과 조회입니다(ADR-007). 재시도 설정이 코드에 있는 것은 그 수치를 같은
코드로 재기 위해서이며 `EXPERIMENT_RETRY` 없이는 켜지지 않습니다.

## Alternatives

| 대안 | 뺀 이유 |
|---|---|
| 가상 스레드만 믿고 격리 없음 | M-019에서 무관한 API는 살았지만 진행 중 호출이 무한정 쌓였고(30초 지연 × 10 rps = 300건), 기관이 돌아와도 그것을 전부 기다렸습니다. 상한이 없는 것은 격리가 아닙니다 |
| Resilience4j Spring Boot 통합 | Boot 4·Spring 7 조합에서의 지원이 확인되지 않았고, 필요한 것은 데코레이터 넷뿐입니다. 라이브러리만 씁니다 |
| Spring Framework 7 `@Retryable`·`@ConcurrencyLimit` | 벌크헤드는 되지만 차단기·리미터가 없고, 재시도는 애초에 붙이지 않습니다 |
| 차단기 OPEN 시 `UNKNOWN` 보존 | 요청이 나가지 않았는데 나간 것처럼 다룹니다. 복구 작업이 헛일을 하고 사용자는 45초를 기다립니다 |
| 리미터를 기본 켬 | 기관이 상한을 알려 준 적이 없습니다. 모르는 상한을 지키는 것은 우리가 우리를 막는 것입니다 |
| Toxiproxy로 장애 주입 | Mock PG가 소켓을 연 채 응답을 붙잡는 것(`HANG_*`)이 곧 TCP 수준의 응답 없음이었습니다. 컨테이너 하나를 더 두지 않았습니다 |

## Consequences

- 결제 응답에 `failureReason`이 생겼습니다(API 변경, OpenAPI 스냅샷 갱신).
- 지표가 늘었습니다: `paritypay.pg.circuit_state`(0/1/2), `paritypay.pg.circuit_failure_rate`,
  `paritypay.pg.in_flight`, `paritypay.pg.rejected{reason}`, `paritypay.pg.retries`(실험).
- 차단기가 열리면 그 10초 동안 **정상이었을 결제도** 거절됩니다. 그것이 차단기의 비용이고, 대안(전부
  타임아웃까지 기다림)보다 쌉니다. HALF_OPEN 3건이 회복을 확인합니다.
- 벌크헤드 50은 이 노트북의 수치가 아니라 "상한이 있어야 한다"의 자리표시자입니다. 운영에서는 기관의
  동시 처리 능력과 우리 인스턴스 수로 정합니다.
- 조회(`getStatus`)도 같은 장치를 지납니다. 차단기가 열려 있으면 조회도 거절되어 `UNAVAILABLE`이 되고,
  복구 작업은 백오프합니다 — 죽은 기관에 조회를 퍼붓지 않습니다.
- `experiment-resilience` 프로필과 `EXPERIMENT_*` 환경변수가 생겼습니다. 설계가 아닙니다.

## Validation

- 기관 30초 지연·타임아웃 없음에서 플랫폼 스레드는 무관한 API가 무너지고, 가상 스레드는 무너지지 않되
  진행 중 호출이 쌓이며, 벌크헤드가 그것을 상한에서 자른다 (M-019·M-023)
- 재시도 3회는 기관 요청을 3배로 만든다 (M-020)
- 차단기가 CLOSED→OPEN→HALF_OPEN→CLOSED로 전이하고, OPEN 동안의 결제는 기관에 도달하지 않은 채
  `FAILED(CIRCUIT_OPEN)`이며 미확정이 0이다 (M-021)
- 고정 윈도는 경계에서 상한의 2배를 통과시키고 슬라이딩 윈도는 넘기지 않는다 (M-022)
- 단위 시험 `PgCallGuardTest`, 통합 시험 `PgIsolationIntegrationTest`

## Outcome — 2026-09-16

다섯 실험을 각 3회 돌렸습니다(reports/11 M-019~M-023, 원본 `reports/data/11-M019~M023-*.json`).

| 확인한 것 | 결과 |
|---|---|
| 타임아웃 없음 + 30초 지연, 플랫폼 스레드 | 3회 모두 **23.7~24.0초**에 Tomcat 200 스레드가 전부 기관을 기다리며 무관한 잔액 조회 p95 30초(타임아웃)·실패 184~195건. jstack: exec 202개 전부 소켓 읽기 대기. DB 풀은 마르지 않음(외부 호출이 트랜잭션 밖). 지표 엔드포인트도 함께 죽음 |
| 같은 조건, 가상 스레드(설계) | 조회 p95 7~8 ms, 실패 0 — 붕괴 없음. 그러나 진행 중 결제 300건이 상한 없이 대기 |
| 같은 조건 + 벌크헤드 50 (M-023) | 플랫폼 스레드에서도 조회 p95 **9.5~10.2 ms**, 실패 0, busy 53에서 멈춤. 결제 601건은 즉시 `FAILED(BULKHEAD_FULL)`, 기관 도달 0 |
| 재시도 3회 (M-020) | 기관 요청 **3.00×**(903/301), 초당 최대 11 → 33. 지터는 총량·봉우리 모두 안 줄임(38~41). 이중 청구 0은 Mock PG가 외부 키로 멱등해서 |
| 차단기 (M-021) | CLOSED→OPEN **+7.5~8.0 s**, HALF_OPEN 프로브 3건씩, 기관 회복 뒤 **3.8~3.9 s**에 CLOSED(1회는 경계 겹침으로 12.6 s). OPEN 동안 결제 329~360건 = 201 `FAILED(CIRCUIT_OPEN)`, **기관 도달 0, 미확정 0**. 대조군(차단기 없음)은 370건이 3초씩 기다린 뒤 미확정 |
| 리미터 50/s, 부하 80/s (M-022) | 임의 1초 최대: 고정 윈도 77~82(예비 100), 토큰 버킷 86, **슬라이딩 윈도 52**. 거절은 즉시(p95 18~20 ms), 기관 도달 0 |

결정을 이 결과로 확정했습니다: 벌크헤드·차단기 **기본 켬**, 리미터 끔(켜면 토큰 버킷), 재시도 없음. 이 실험
이전에는 셋 중 아무것도 없었고 그것이 결함 N입니다. 회귀 시험 `PgCallGuardTest` 5건·`PgIsolationIntegrationTest`
1건.

**미측정.** 벌크헤드·차단기 수치(50, 윈도 20, 10초)의 최적값 — 이 노트북의 부하로 정한 것이 아니라 "있어야
한다"의 자리표시자입니다. 연결 거부(`docker stop`)와 은행 쪽(`MockBankClient`)은 재지 않았습니다 — 은행 호출은
아직 격리 장치를 지나지 않습니다.
