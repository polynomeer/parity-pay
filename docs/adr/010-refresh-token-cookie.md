# ADR-010 리프레시 토큰을 httpOnly 쿠키로 옮김

- Status: Accepted
- Decided: 2026-09-10
- Date: 2026-09-10

> **에이전트 영향**: 리프레시 토큰은 응답 본문에 넣지 않습니다. 서버가 `HttpOnly` 쿠키로 심고 브라우저가 자동으로 돌려줍니다. 클라이언트 코드가 리프레시 토큰 값을 만질 수 없어야 하며, 만질 수 있게 만드는 변경은 이 결정을 되돌리는 것입니다.

## Context

Phase 7에서 인증을 넣을 때 토큰 두 개를 모두 응답 본문으로 돌려줬습니다. 프론트엔드는 그것을
`localStorage`에 넣었고, [DOC-14 §10](../14-frontend-design.md)에 **알려진 한계**로 적어 두었습니다.

> 리프레시 토큰이 `localStorage`에 있으면 XSS에 노출됩니다. 이상적인 형태는 `httpOnly` 쿠키지만
> 지금 서버는 토큰을 응답 **본문**으로 주므로 서버 변경이 필요합니다.

두 토큰의 성격이 다른데 같은 곳에 두고 있었습니다.

| | 수명 | 훔치면 |
|---|---|---|
| 액세스 토큰 | 15분 | 15분 동안 그 사용자로 행세 |
| 리프레시 토큰 | 길다 | **계속 갱신해 무기한 행세** |

스크립트 하나가 `localStorage`를 읽을 수 있으면 후자를 가져갑니다. 회전(rotation)은 이 경우에
도움이 되지 않습니다 — 공격자가 먼저 쓰면 회전되는 쪽은 피해자입니다.

## Decision

**리프레시 토큰을 `HttpOnly` 쿠키로 옮깁니다.** 응답 본문에서 뺍니다.

| 항목 | 값 | 이유 |
|---|---|---|
| 이름 | `paritypay_refresh` | |
| `HttpOnly` | 예 | 자바스크립트가 읽을 수 없습니다. 이 결정의 전부입니다 |
| `Secure` | 설정값(운영 참) | 로컬 http 개발을 막지 않으려고 설정으로 둡니다 |
| `SameSite` | `Lax` | **CSRF 방어를 여기서 합니다**(아래) |
| `Path` | `/api/v1/auth` | 인증 경로 밖으로는 아예 나가지 않습니다 |
| `Max-Age` | 리프레시 토큰 수명 | |

액세스 토큰은 **그대로 응답 본문**입니다. 15분짜리이고, 클라이언트가 `Authorization` 헤더에
붙여야 하므로 읽을 수 있어야 합니다.

### CSRF는 SameSite=Lax가 막습니다

쿠키가 되는 순간 브라우저가 **자동으로** 붙입니다. `evil.com`이 `POST /api/v1/auth/tokens/refresh`를
일으키면 쿠키가 함께 갈 수 있고, 그것이 CSRF입니다.

`SameSite=Lax`는 **교차 사이트 POST에 쿠키를 붙이지 않습니다**(최상위 GET 이동만 허용). 그래서 이
엔드포인트에 별도 CSRF 토큰을 두지 않습니다. 토큰을 하나 더 만들면 그것을 어디에 보관할지가 다시
문제가 되고, 결국 같은 자리로 돌아옵니다.

공격자가 응답을 **읽을** 수는 없습니다(CORS). 최악은 피해자의 리프레시 토큰이 회전되어 세션이
끊기는 것인데, `Lax`가 그 요청 자체를 막습니다.

## Alternatives

- **본문에 그대로 두고 XSS를 막는다**: XSS를 완전히 막는 것은 보장할 수 없습니다. 의존성 하나만
  뚫려도 됩니다. 보관 위치를 바꾸면 스크립트가 뚫려도 리프레시 토큰은 나가지 않습니다.
- **본문과 쿠키 둘 다 준다**: 호환은 되지만 노출이 그대로 남습니다. 결정을 한 셈이 아닙니다.
- **CSRF 토큰을 추가한다**: `SameSite=Lax`로 충분한 자리에 보관 문제를 하나 더 만듭니다. 필요한
  근거가 생기면 그때 별도 결정으로 합니다.

## Consequences

**배포 형태가 제약됩니다.** `SameSite=Lax` 쿠키는 교차 사이트 요청에 실리지 않습니다. 따라서 API와
화면은 **같은 사이트**여야 합니다.

- 개발: Vite가 `/api`를 프록시하므로 브라우저에서는 같은 오리진입니다. 그대로 동작합니다.
- 운영: `app.example.com`·`ops.example.com`·`api.example.com`처럼 같은 등록 도메인 아래 두거나,
  화면이 API를 자기 오리진으로 프록시해야 합니다. **완전히 다른 사이트에 API를 두면 이 결정이
  동작하지 않습니다.**

이것은 대가입니다. DOC-14 §2가 정한 "두 앱을 다른 오리진에" 는 유지되지만, 그 오리진들이 API와
같은 사이트여야 한다는 조건이 붙습니다.

**브라우저가 아닌 클라이언트는 리프레시할 수 없습니다.** 응답 본문에 값이 없기 때문입니다. 부하·실험
스크립트는 액세스 토큰만 쓰므로 영향이 없고, 회전·철회를 검증하는 시험은 쿠키를 읽도록 바꿨습니다.

**로그아웃과 비밀번호 변경이 쿠키를 지웁니다.** 서버에서 철회하는 것만으로는 브라우저에 죽은
쿠키가 남습니다.

## Validation

구현 후 다음을 시험으로 확인합니다.

- 로그인·재발급 응답 본문에 `refreshToken`이 **없다**
- 쿠키에 `HttpOnly`·`SameSite=Lax`·`Path=/api/v1/auth`가 붙는다
- 본문 없이 쿠키만으로 재발급된다
- 쿠키 없이 재발급하면 거부된다. **본문으로 우회할 수도 없다** — 값을 알아도 본문에 실으면
  받아주지 않아야 합니다. 받아주면 이 결정은 없는 것과 같습니다
- 회전이 유지된다 — 이전 쿠키로 다시 재발급하면 거부된다
- 로그아웃·비밀번호 변경이 쿠키를 지운다

## Outcome

구현하고 위 항목을 전부 시험으로 확인했습니다. 결과는
[reports/11](../../reports/11-performance-failure-report-template.md)이 아니라 시험 자체가 증거입니다 —
성능이 아니라 계약 변경이기 때문입니다.

- 백엔드: `AuthenticationApiTest`(본문에 없음, 쿠키 속성, 쿠키 없이·본문으로는 실패, 회전, 로그아웃
  삭제), `PasswordManagementTest`(비밀번호 변경·재설정이 쿠키를 지우고 세션을 끊음)
- 프론트: `packages/api-client`의 계약 시험 — 재발급 호출에 본문이 없고 `credentials: "include"`로
  나가는지, 저장된 토큰에 리프레시 값이 없는지

**거부는 401이 아니라 400 `INVALID_REQUEST`입니다.** 처음에는 401로 적었지만, 이미 회전·만료·철회가
전부 400 `INVALID_REQUEST`로 나가고 있었습니다. 쿠키가 없을 때만 401로 하면 "쿠키가 아예 없었는가"와
"있었지만 죽었는가"가 상태 코드로 갈립니다. 같은 코드로 두는 편이 낫습니다.
