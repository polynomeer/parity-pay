# ADR-005 Transactional Outbox 사용

- Status: Accepted
- Decided: 2026-09-06
- Date: 2026-09-03

> **에이전트 영향**: 애플리케이션 코드에서 커밋 후 브로커로 직접 발행하지 않습니다. 이벤트는 업무 트랜잭션 안에서 `outbox_event`에 저장하고, 별도 발행기가 전달합니다.

## Context

DB 변경 후 브로커 발행이 실패하면 업무는 완료됐지만 후속 이벤트가 유실됩니다. 반대로 먼저 발행하면 롤백된 업무의 이벤트가 전달될 수 있습니다.

## Decision

업무 데이터와 Outbox 행을 같은 DB 트랜잭션에 저장하고 별도 발행기가 브로커로 전달합니다.

## Alternatives

- 애플리케이션에서 커밋 후 직접 발행: 발행 유실 창이 존재합니다.
- 분산 트랜잭션/2PC: 브로커·DB 지원과 운영 복잡성이 큽니다.
- CDC: 지연은 줄일 수 있지만 초기 인프라 비용이 큽니다.

## Consequences

커밋된 이벤트 의도를 유실하지 않습니다. 폴링 지연, 테이블 정리와 중복 발행을 운영해야 합니다.

## Validation

커밋 후 발행 전 프로세스 종료, ACK 유실과 발행기 다중 인스턴스 테스트로 검증합니다.

## Outcome — 2026-09-06

구현과 장애 테스트로 확인했습니다.

- 업무 상태·원장·잔액·Outbox가 한 트랜잭션에 커밋됩니다.
- 업무가 롤백되면 이벤트도 함께 사라집니다(T-003 테스트).
- 커밋 후 발행 전에 멈춰도 재시작한 발행기가 이어서 발행합니다(F-003 테스트).
- 발행 실패 시 이벤트가 유실되지 않고 백오프 후 재시도하며, 최대 시도를 넘기면 `FAILED`로
  전환되어 운영자 조회 대상이 됩니다.
- 적체는 `paritypay.outbox.pending`, `.failed`, `.oldest_pending_age_seconds`로 관측합니다.

**아직 하지 않은 것**: 발행기 다중 인스턴스 동시 실행 테스트. 구현은 `FOR UPDATE SKIP LOCKED`로
준비되어 있지만 실제 다중 인스턴스 실험은 하지 않았습니다.

### 발행 처리량 — 2026-09-07

폴링 방식의 대가로 예상했던 지연이 처리량 문제로 먼저 나타났습니다. 건별 동기 전송이 병목이었고
(P-003), 배치 전송과 적체 시 연속 배치로 같은 조건에서 56.9 → 536.7건/초를 측정했습니다(P-005).

확인 시점은 바꾸지 않았습니다. 브로커가 받았다고 답한 이벤트만 `PUBLISHED`가 됩니다. 이 결정을
뒤집어 전송 직후 표시하면 처리량은 더 오르지만 유실 창이 생기므로, 그 교환은 하지 않았습니다.

배치로 보내도 실패는 이벤트 단위로 기록합니다. 전송 호출이 그 자리에서 던지는 경우(브로커 부재로
메타데이터를 못 받는 상황)까지 포함합니다. 이것을 빠뜨려 배치 전체가 롤백되던 결함을 크래시
실험에서 찾았습니다(reports/11 결함 C).
