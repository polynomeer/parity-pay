# ADR-007 외부 결과 불명확 상태 UNKNOWN 도입

- Status: Accepted
- Decided: 2026-09-06
- Date: 2026-09-03

> **에이전트 영향**: 외부 호출 타임아웃을 `catch` 해서 실패로 확정하는 코드를 쓰지 않습니다. `UNKNOWN`으로 전이하고 복구 작업에 맡기며, 사용자에게는 `202 RESULT_PENDING`을 응답합니다.

## Context

외부기관이 승인 또는 취소를 처리한 뒤 응답이 유실되면 내부 시스템은 성공·실패를 알 수 없습니다. 즉시 실패로 처리하면 중복 승인·환불 위험이 생깁니다.

## Decision

충전, 결제, 취소와 지급에 `UNKNOWN` 상태를 두고 외부 조회, 웹훅과 대사로 최종 상태를 확정합니다.

## Alternatives

- 타임아웃을 실패로 처리: 구현은 단순하지만 실제 외부 성공과 불일치할 수 있습니다.
- 즉시 같은 요청 재전송: 외부 멱등성이 불완전하면 중복 금융 효과가 발생합니다.

## Consequences

정확성을 높이지만 사용자에게 처리 중 UX가 필요하고 복구 작업·알림·운영 절차가 추가됩니다.

## Validation

승인·취소·지급 성공 후 응답 유실 시나리오에서 최종 수렴과 중복 금액 효과 0건을 확인합니다.

## Outcome — 2026-09-06

구현과 장애 테스트로 확인했습니다.

- 외부 승인 후 응답이 유실되면 `UNKNOWN`으로 보존하고 202로 응답합니다(F-006).
- 복구 작업이 조회로 최종 상태에 수렴시키며, 반복 실행해도 금액은 한 번만 움직입니다.
- 외부에 기록이 "없음"으로 반복 확인되어야 실패로 확정합니다(단발 조회로 단정하지 않음).
- 조회 API가 죽어 있으면 아무것도 확정하지 않고 백오프하며, 제한을 넘기면 수동 검토로 넘깁니다(F-009).
- 정산 지급에도 같은 규칙을 적용했습니다(F-010).

추가로, 재시작 때문에 `PROCESSING`에 갇힌 거래도 복구 대상에 포함했습니다. 설계 당시 명시되지
않았지만 실제로 열려 있던 구멍이었습니다.

**적용 범위 제한**: 결제(Payment)와 취소(Cancellation)의 `UNKNOWN`은 상태 전이표와 DB 제약까지만
준비되어 있고 도달 경로가 없습니다. 페이머니 결제는 외부 호출이 없기 때문이며, 외부 PG를
도입할 때 활성화됩니다.
