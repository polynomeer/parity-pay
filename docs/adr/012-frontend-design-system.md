# ADR-012 순수 CSS 토큰 패키지로 두 앱의 디자인을 만듦

- Status: Accepted
- Decided: 2026-09-14
- Date: 2026-09-14

> **에이전트 영향**: 화면을 꾸밀 때 Tailwind·CSS-in-JS·컴포넌트 라이브러리를 들이지 않습니다.
> 색·간격·상태 색은 `packages/ui/src/tokens.css`의 변수만 씁니다 — 화면 CSS에 16진수 색을 직접
> 적지 않습니다. **UNKNOWN·PROCESSING·"확인 중"은 보라(`--unknown`)이지 빨강이 아닙니다.**
> 메뉴는 링크만 씁니다(버튼 금지). 테스트·E2E가 잡는 제목 문구·버튼 텍스트·`data-testid`·
> `role`은 스타일 작업으로 바꾸지 않습니다.

## Context

2026-09-14 기준 두 프론트엔드 앱에는 **CSS 파일이 하나도 없었습니다.** 화면 20여 개가 마크업만
있고 브라우저 기본 스타일로 렌더링됐습니다. 고객 앱에는 메뉴도 없어서 `/pay`·`/shop`·`/orders`를
URL로 직접 쳐야 했고, 정산 화면(`Settlements.tsx`)은 만들어져 있지만 어느 경로에도 연결되어 있지
않았습니다.

[DOC-14 §6](../14-frontend-design.md)은 스타일을 "Tailwind CSS — 두 앱이 공유하는 토큰만
정의합니다"라고 적어 두었지만, Tailwind는 설치된 적이 없었습니다. 문서가 계획을 적었고 코드는
거기 닿지 않은 상태였습니다.

디자인을 넣을 때 지켜야 하는 제약이 이미 여럿 있었습니다.

| 출처 | 제약 |
|---|---|
| [DOC-15 §4.1](../15-ui-screen-plan.md) | 상태 색 기준 — 정상 초록, 확인 필요 주황, 즉시 대응 빨강, **상태 미확정 보라 또는 파랑** |
| [DOC-14 FE-002](../14-frontend-design.md) | 202와 `UNKNOWN`은 실패가 아닙니다. 화면이 실패로 표현하면 사용자가 다시 시도해 이중 출금이 됩니다 |
| [DOC-14 FE-005](../14-frontend-design.md) | 잔액은 스냅샷이므로 기준 시각을 함께 보여 줍니다. 디자인이 그것을 숨기면 안 됩니다 |
| [DOC-14 §2](../14-frontend-design.md) | 고객 앱과 운영 콘솔은 다른 오리진·다른 성격입니다. 하나로 뭉개지 않습니다 |
| [ADR-011](011-deployment-shape.md) | 배포는 nginx가 정적 파일을 서비스합니다. 런타임에 외부로 나가는 요청(웹폰트 등)을 만들 이유가 없습니다 |
| 단위 테스트 56건·E2E 7건 | `getByRole("heading", { name })`, `getByRole("button", { name })`, `data-testid`, `document.querySelector("form")`, `document.querySelectorAll("button")[0]`에 의존합니다 |

마지막 줄이 가장 구체적인 제약입니다. E2E는 상품 화면에서 **문서의 첫 번째 `<button>`**을 구매
버튼으로 집고, 충전 화면에서 **첫 번째 `<form>`**을 제출합니다. 메뉴에 버튼을 두거나 검색 폼을
앞에 놓으면 스타일만 바꿨는데 시험이 깨집니다.

## Decision

### 1. 순수 CSS. 토큰과 프리미티브는 `packages/ui`, 레이아웃은 앱별 `app.css`

```text
packages/ui/src/tokens.css    색·간격·반경·그림자·글꼴 변수. 라이트/다크 두 벌
packages/ui/src/base.css      리셋 + 요소 기본값(button·input·table·dl·form) + 프리미티브 클래스
apps/web-customer/src/app.css 상단 바·하단 탭·잔액 카드·상품 격자·인증 카드
apps/web-ops/src/app.css      사이드바·검색·타임라인·불변조건 카드·원장 배너
```

두 앱은 `@paritypay/ui` 워크스페이스 패키지를 의존성으로 갖고 `@import "@paritypay/ui/base.css"`로
들여옵니다. DOC-14 §6이 예정해 둔 `packages/ui/` 자리를 그대로 씁니다.

**Tailwind를 쓰지 않는 이유.** 세 가지가 겹칩니다.

- 화면이 20여 개이고 앞으로도 크게 늘지 않습니다. 유틸리티 클래스가 갚아 주는 비용(수백 개
  컴포넌트에서 스타일 파일과 마크업을 오가는 비용)이 여기에는 없습니다.
- 이 앱의 TSX는 시험이 구조를 읽는 대상입니다. `className="flex items-center gap-2 rounded-lg
  border px-4 ..."`가 줄마다 붙으면 시험이 보는 마크업이 스타일에 묻힙니다. 클래스 하나
  (`className="card"`)가 낫습니다.
- 빌드 단계가 하나 늘고(PostCSS 또는 Vite 플러그인), 설정 파일이 둘 더 생기고, 프로덕션 CSS
  퍼지가 동적 클래스 이름을 놓치는 함정이 생깁니다. 지금 CSS는 앱당 12~14 kB(gzip 3~4 kB)라
  줄일 것도 없습니다.

Tailwind가 주는 것 중 실제로 필요했던 것은 **토큰 하나로 두 앱을 맞추는 것**뿐이고, 그것은 CSS
변수로 됩니다.

**CSS-in-JS·컴포넌트 라이브러리를 쓰지 않는 이유.** 런타임 의존성이 늘고, 라이브러리의 색 체계를
DOC-15 §4.1에 맞추려면 어차피 토큰을 덮어써야 합니다. 이 앱에 필요한 컴포넌트는 버튼·입력·표·
배지·알림 다섯 가지 정도이고, 그것을 위해 라이브러리를 배우는 비용이 직접 쓰는 비용보다 큽니다.

### 2. `role` 속성을 그대로 스타일링합니다

```css
[role="alert"]  { background: var(--danger-soft); color: var(--danger); }
[role="status"] { background: var(--unknown-soft); color: var(--unknown); }
```

화면 코드는 이미 오류에 `role="alert"`, "확인 중"에 `role="status"`를 붙여 두었습니다. 시험이
`getByRole("alert")`로 그것을 찾고, 보조기기가 그것을 읽습니다. 즉 **그 속성은 이미 계약**입니다.
같은 뜻의 클래스를 하나 더 붙이면 두 곳이 어긋날 수 있고(클래스는 붙였는데 역할을 빼먹는 식),
어긋난 쪽이 눈에 보이지 않습니다. 속성 자체를 꾸미면 어긋날 수가 없습니다.

`role="status"`가 보라인 것은 우연이 아닙니다. 이 앱에서 `status`는 거의 전부 "결과를 확인하고
있습니다"이고, 그것은 FE-002가 실패로 보이면 안 된다고 못 박은 상태입니다.

### 3. 요소 기본값을 먼저, 클래스는 구조가 필요한 곳에만

`button`·`input`·`select`·`table`·`dl`·`form`·`label`은 태그 자체에 기본 모양을 줍니다.
`button[type="submit"]`은 주 동작 색입니다. 그 위에 `.card`·`.badge`·`.table-wrap`·`.page` 같은
클래스 열 개 남짓을 둡니다.

이렇게 한 이유는 **마크업을 최소한으로 건드리기 위해서**입니다. 폼 하나를 꾸미려고 `label`마다
클래스를 붙이면 20개 화면의 diff가 스타일과 무관한 줄로 채워지고, 그 사이에서 시험이 의존하는
문구나 testid를 실수로 바꾸기 쉽습니다. 실제로 이번 작업에서 화면 파일의 변경은 대부분
"감싸는 `div` 하나와 클래스 한두 개"였고, 제목·버튼 문구·testid는 하나도 바뀌지 않았습니다.

### 4. 상태 색은 DOC-15 §4.1을 토큰 이름으로 고정합니다

| 토큰 | 뜻 | 쓰이는 상태 |
|---|---|---|
| `--ok` 초록 | 정상 | SUCCEEDED·APPROVED·COMPLETED·POSTED·PAID·불변조건 정상 |
| `--warn` 주황 | 확인 필요 | 부분 취소·전액 취소·HELD·OPEN·수동 검토 필요·갱신이 멈춘 캐시 |
| `--danger` 빨강 | 즉시 대응 | FAILED·REJECTED·불변조건 위반·차변≠대변 |
| `--unknown` 보라 | 상태 미확정 | UNKNOWN·PROCESSING·PAYING·"확인 중"·"반영 중" |

운영 콘솔은 `StatusBadge`가 서버 열거형 문자열을 그대로 두고 색만 입힙니다 — 운영자는
`PAYMENT_UNKNOWN`을 읽어야 하는 사람입니다. 고객 앱은 `paymentStatusLabel`이 이미 만들어 둔
사용자 문구("결과 확인 중")에 같은 색을 입힙니다.

색이 문구보다 먼저 읽힙니다. 문구가 "확인 중"인데 색이 빨강이면 사용자는 빨강을 믿고 다시
시도합니다. 그래서 색 매핑은 화면마다 정하지 않고 토큰 이름에 뜻을 박아 두었습니다.

### 5. 레이아웃: 고객 앱은 상단 바(폰에서 하단 탭), 운영 콘솔은 사이드바

두 앱의 성격이 다릅니다. 고객 앱은 항목이 다섯 개이고 한 손으로 씁니다 — 640px 아래에서는 상단
메뉴가 `position: fixed` 하단 탭이 됩니다. 운영 콘솔은 표와 숫자를 훑는 도구라 항목이 늘어도 되는
사이드바를 두고 글자 크기를 한 단계 줄였습니다.

React Router의 중첩 라우트(`<Route element={<Shell/>}>` + `<Outlet/>`)로 틀을 씌웁니다. 인증
화면(로그인·가입·비밀번호)은 별도 틀(`AuthShell`)에 있어 메뉴가 없습니다. 이전에는 운영 콘솔의
`<nav>`가 로그인 화면에도 그려졌습니다.

**메뉴는 링크만 씁니다.** E2E가 상품 화면의 첫 `<button>`을 구매 버튼으로 집기 때문입니다. 로그아웃
버튼을 두지 않은 것도 같은 이유이고, 그 전에 로그아웃 API 자체가 클라이언트에 없습니다 — 이
ADR의 범위가 아닙니다.

### 6. 다크 모드는 토큰 두 벌로, 시스템 설정을 따릅니다

`@media (prefers-color-scheme: dark)`에서 변수만 바꿉니다. 화면 CSS에는 다크 분기가 없습니다.
토글 UI는 두지 않았습니다 — 저장할 곳(로컬 저장소)과 동기화할 대상(두 앱)이 생기고, 지금은 그
가치가 없습니다.

### 7. 웹폰트를 쓰지 않습니다

`"Pretendard Variable", Pretendard, -apple-system, "Apple SD Gothic Neo", "Noto Sans KR", ...`
시스템 글꼴 스택입니다. ADR-011의 배포 형태에서 앱은 정적 파일이고 브라우저는 자기 오리진만
부릅니다. 폰트 CDN을 부르면 그 원칙에 예외가 하나 생기고, 오프라인 개발·E2E에서 글꼴 로딩이
시험 시간에 섞입니다. 한글 시스템 글꼴은 macOS·Windows·Android 모두 충분합니다.

### 8. 정산 화면을 라우팅하고 MERCHANT에만 메뉴를 보입니다

`/settlements`가 없어서 화면이 죽어 있었습니다. 서버가 `/api/v1/merchant/**`를 `MERCHANT` 역할로
막으므로, 토큰에 그 역할이 있을 때만 메뉴에 나타납니다. 들어갈 수 없는 메뉴를 보여 주지
않습니다.

## Alternatives

| 대안 | 뺀 이유 |
|---|---|
| Tailwind CSS (DOC-14 원안) | §1. 화면 수에 비해 비용이 크고, 시험이 읽는 마크업을 유틸리티 클래스로 덮습니다 |
| CSS Modules | 파일이 화면마다 하나씩 늘고, 두 앱이 공유하는 토큰은 결국 전역 CSS에 둬야 합니다. 이름 충돌을 막아 주는 것이 장점인데 클래스가 열 개 남짓이라 충돌할 것이 없습니다 |
| styled-components / Emotion | 런타임 의존성·SSR 없음·색 체계를 덮어써야 함 |
| MUI·Chakra 같은 컴포넌트 라이브러리 | 필요한 컴포넌트가 다섯 가지뿐이고, 상태 색 규칙이 라이브러리 기본과 다릅니다 |
| 각 앱에 CSS를 따로 복사 | 토큰이 두 벌이 되어 색이 어긋납니다. DOC-14가 공유 패키지를 예정해 둔 이유입니다 |
| 클래스로만 스타일링, 요소 기본값 없음 | 20개 화면의 모든 `label`·`button`에 클래스를 붙여야 하고, 그 diff에서 문구·testid를 건드릴 위험이 큽니다 |
| 로그아웃·다크 모드 토글 추가 | 디자인이 아니라 기능이고, 로그아웃은 API가 없습니다. 이 ADR 밖입니다 |

## Consequences

**긍정**

- 두 앱의 색·간격·상태 표현이 한 파일에서 나옵니다. DOC-15 §4.1을 바꾸면 `tokens.css` 한 곳만
  바꿉니다.
- 화면 코드의 시험 계약(문구·testid·역할)이 그대로입니다. 단위 테스트 56건이 수정 없이 통과했고,
  유일한 시험 변경은 `Home.test.tsx`에 `MemoryRouter`를 씌운 것입니다(홈에 링크가 생겼으므로).
- 빌드 단계가 늘지 않았습니다. `pnpm build`가 전과 같은 도구로 돕니다.
- 다크 모드가 공짜로 따라옵니다.

**부정 · 주의**

- 유틸리티 클래스가 없으므로 새 화면을 만드는 사람은 `base.css`의 프리미티브 목록을 알아야
  합니다. 목록은 파일 상단 주석에 있고, 없는 것이 필요하면 화면 CSS에 임시로 적지 말고 `base.css`에
  추가합니다.
- `button[type="submit"]`이 전역으로 주 동작 색입니다. 부 동작이 제출 버튼이면 `.btn--ghost`
  등으로 덮어야 합니다. 지금은 그런 화면이 없습니다.
- `form > button { align-self: flex-start }`가 기본이라 꽉 찬 버튼은 `.btn--block`을 명시해야
  합니다. 인증 카드는 CSS가 대신 넓힙니다.
- 충전·결제 화면의 카드 안에 `<h1>`이 하나 더 있습니다(페이지 제목과 별개로). 시험과 E2E가
  `heading "충전"`·`heading "결제"`를 찾으므로 태그를 내리지 않고 `.card h1` 크기만 줄였습니다.
  의미상 `h2`가 맞고, 시험을 같이 고칠 때 바꿉니다.
- 상품 그림은 이모지입니다. 카탈로그가 고정 데이터라 그림도 고정입니다 — 실제 상품이 생기면 같이
  바꿉니다.
- CSS에 린터·포매터가 없습니다. TS는 `tsc`가 잡지만 CSS 오타는 브라우저에서만 드러납니다.
- **`backdrop-filter`는 `position: fixed` 자손의 기준 상자가 됩니다.** 상단 바에 그것을 두었더니
  폰에서 하단 탭이 상단 바 안에 갇혔습니다. 640px 아래에서는 끄도록 했고, 같은 함정이 `transform`·
  `filter`에도 있습니다.

## Validation

- 단위 테스트 56건과 `pnpm typecheck`가 통과한다
- 두 앱이 프로덕션 빌드된다 (`pnpm build`)
- 고객: 가입 → 계좌 연결 → 충전 → 상품 구매 → 부분 취소 → 구매확정 → 거래내역이 실제 스택에서
  화면으로 된다
- 운영: 로그인 → 주문번호 검색 → 후보 선택 → 타임라인 → 원장 상세(차변=대변)가 화면으로 된다
- 라이트·다크·375px 폭에서 깨지는 화면이 없다
- `UNKNOWN`·"확인 중"이 어디에서도 빨강으로 그려지지 않는다
