# ADR-008 원장과 잔액 스냅샷 분리

- Status: Accepted
- Decided: 2026-09-06
- Date: 2026-09-03

> **에이전트 영향**: 조회는 `wallet_balance`, 진실은 원장입니다. 스냅샷 갱신은 원장 전기와 같은 트랜잭션에서만 합니다. 스냅샷을 별도 경로로 수정하는 코드를 만들지 않습니다.

## Context

매 조회마다 원장 전체를 집계하면 비용이 크지만 잔액 컬럼만 신뢰하면 오류를 검증하거나 재구축하기 어렵습니다.

## Decision

원장을 진실의 원천으로 두고 `wallet_balance`를 트랜잭션 내에서 함께 갱신하는 조회 스냅샷으로 사용합니다. 주기적으로 원장 계산값과 비교합니다.

## Alternatives

- 원장 실시간 합산: 단순한 진실 모델이지만 데이터 증가에 따라 조회 비용이 큽니다.
- 잔액만 저장: 빠르지만 감사와 재구축이 약합니다.
- 비동기 투영: 쓰기 지연은 줄지만 결제 직후 잔액 일관성이 복잡합니다.

## Consequences

빠른 조회와 재구축을 함께 얻지만 원장·스냅샷 이중 표현을 검증해야 합니다.

## Validation

임의 거래 재생, 스냅샷 손상 후 재구축과 대량 원장 집계 성능을 테스트합니다.

## Outcome — 2026-09-06

구현과 테스트로 확인했습니다. `wallet_balance`는 원장 전기와 같은 트랜잭션에서만 갱신되고,
`GET /api/v1/wallets/{walletId}/ledger-verification`으로 스냅샷과 원장 재생값을 비교합니다.
충전·결제·취소·정산 시나리오마다 두 값이 일치하는지 확인했고, 차이가 생기면
`paritypay.invariant.balance_snapshot_drift` 지표가 0이 아니게 되어 즉시 경보 대상이 됩니다.

이 검증 API는 **운영자 전용입니다**(`OPS_VIEWER` 이상). 경로가 회원 영역 아래 있지만 본인 지갑도
열지 않습니다. INV-010 불일치는 회원이 할 수 있는 일이 없는 문제이고, 확인도 재구축도 운영자
절차이기 때문입니다. 처음에는 인증만 걸린 채 누구에게나 열려 있었고, 남의 지갑 잔액까지 보였습니다.
근거: docs/09-consistency-recovery.md §13

### 재구축 — 2026-09-07

스냅샷을 의도적으로 손상시킨 뒤 원장으로 재구축하는 절차를 만들고 실행했습니다(F-010).

- 운영자 API `POST /api/v1/admin/wallets/{walletId}/balance-rebuild`. 요청자와 다른
  `OPS_APPROVER`의 승인이 필요하고, 전후 값이 감사 로그에 남습니다.
- 쓸 수 있는 값은 원장 계산값 하나뿐입니다. 임의 금액을 넣는 파라미터가 없습니다.
- 자동으로 돌지 않습니다. 조용히 맞춰버리면 원인을 조사할 증거가 사라집니다.
- 원장 항목 44,970건 규모에서 재구축 왕복 104 ms(중앙값), 전 지갑 탐지 쿼리 54 ms(중앙값).
  원장은 전후로 동일했습니다. 자세한 결과는 reports/11 F-010에 있습니다.

**아직 하지 않은 것**: 전 지갑 일괄 재구축 절차와, 지갑당 원장 항목이 훨씬 많을 때(수십만 건)의
집계 비용 측정. 지금 측정한 규모는 지갑당 1,170건입니다.
