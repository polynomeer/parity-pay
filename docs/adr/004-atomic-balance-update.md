# ADR-004 지갑 잔액 조건부 원자 업데이트

- Status: Accepted
- Decided: 2026-09-06
- Date: 2026-09-03

> **에이전트 영향**: 잔액 차감은 "조회 후 계산 후 저장"이 아니라 WHERE에 잔액 조건과 버전을 넣은 단일 UPDATE로 구현합니다. 0행 갱신은 충돌과 잔액 부족을 구분해 처리합니다.

## Context

잔액 조회 후 차감하면 동시 결제가 모두 승인될 수 있습니다. 지갑별 경합과 단순성을 함께 고려해야 합니다.

## Decision

`available_amount >= amount`와 버전을 조건으로 한 단일 UPDATE를 기본안으로 사용합니다. 버전 충돌은 제한적으로 재시도하고 잔액 부족은 확정 실패로 처리합니다.

## Alternatives

- `SELECT FOR UPDATE`: 이해하기 쉽지만 락 대기와 트랜잭션 길이가 늘 수 있습니다.
- 분산 락: DB 업데이트와 원자성이 자동 보장되지 않고 운영 실패 모드가 추가됩니다.
- 지갑 단위 메시지 직렬화: 높은 처리량에 유용하지만 비동기 UX와 복잡성이 증가합니다.

## Consequences

단일 SQL로 잔액 조건과 경쟁을 제어할 수 있습니다. 높은 경합에서 재시도가 증가할 수 있습니다.

## Validation

동일 지갑과 서로 다른 지갑 부하에서 비관적 잠금과 비교해 처리량, p99, 충돌률과 DB 락 대기를 측정한 뒤 Accepted 여부를 결정합니다. 결과는 [성능·장애 보고서](../../reports/11-performance-failure-report.md) P-002에 기록합니다.

## Outcome — 2026-09-06

두 구현을 모두 만들어 같은 환경에서 비교했습니다(`BalanceStrategyBenchmarkTest`). 전략은
`paritypay.wallet.balance-strategy` 설정으로 전환합니다.

### 측정 조건

- 부하: 8 스레드 × 5 결제 = 40 요청, 하나의 지갑에 집중. 초기 잔액은 절반만 승인 가능한 금액.
- 라운드: warm-up 1회(버림) + 측정 3회, 전략을 번갈아 실행해 순서 편차를 상쇄.
- 환경: Java 21.0.7, macOS aarch64, 10 cores, PostgreSQL 17(Testcontainers).
- 원본 결과: `apps/pay-api/build/reports/adr-004-balance-strategy.txt`

### 결과

| 구현 | median | min | max |
|---|---:|---:|---:|
| 조건부 원자 UPDATE (JDBC) | 1,463 ms | 969 ms | 1,975 ms |
| 비관적 잠금 `SELECT FOR UPDATE` | 2,133 ms | 1,998 ms | 2,311 ms |
| 조건부 UPDATE (JPA `@Modifying`) | 1,569 ms | 1,048 ms | 3,242 ms |

**정확성은 세 구현이 동일했습니다.** 매 라운드 승인 20/40건, 최종 잔액 0원으로 잔액을 넘겨
승인된 경우가 없었습니다. 이것이 1차 판단 기준입니다.

### 결정

조건부 원자 UPDATE를 유지합니다. 정확성이 같은 상태에서 이 환경 측정으로는 조건부 갱신이 더
빠르며, 비관적 잠금을 택할 근거가 없습니다.

### 이 측정의 한계

- 개발 노트북 + Docker Desktop 환경이며, 전체 라운드의 최대/최소 비율이 3.3배로 편차가 큽니다.
  median 차이(약 1.46배)는 신호로 보이지만 강한 결론은 아닙니다.
- HTTP 계층을 거치지 않은 유스케이스 직접 호출이며, DB 락 대기는 측정하지 않았습니다.
- 서로 다른 지갑 워크로드(P-001)에서 두 전략을 비교하지는 않았습니다. 경합이 없을 때는 차이가
  더 작을 것으로 예상하지만 확인하지 않았습니다.

### 이후 측정 (2026-09-07, HTTP 부하)

k6로 HTTP 경로 전체를 거쳐 다시 측정했습니다. 이번에는 전략 비교가 아니라 **경합 자체의 비용**을
쟀습니다.

| 조건 | 처리량(중앙값) | p50 | p95 |
|---|---:|---:|---:|
| 서로 다른 지갑 (20 VU) | 65.9 req/s | 186 ms | 421 ms |
| 동일 지갑 (20 VU) | 11.3 req/s | 662 ms | 3,676 ms |

조건부 원자 갱신을 쓰더라도 하나의 지갑에 트래픽이 몰리면 처리량이 5.8배 떨어지고 꼬리 지연이
8.7배가 됩니다. **잔액 행이 직렬화 지점이라는 사실은 잠금 전략을 바꿔도 사라지지 않습니다.**
이 구간을 넘어서야 한다면 다음 선택지는 지갑 단위 직렬화나 잔액 분할이며, 그것은 이 ADR이 아니라
새 결정입니다.

정확성은 이 부하에서도 유지됐습니다. 결제 21,930건 이후 불변조건 지표가 모두 0이었습니다.
근거: [reports/11](../../reports/11-performance-failure-report.md) P-001·P-002

### 부수적으로 발견한 것

첫 측정에서 조건부 갱신이 비관적 잠금보다 3.7배 느리게 나왔습니다. 원인은 잠금 전략이 아니라
배관이었습니다. 조건부 갱신만 JPA `@Modifying(flushAutomatically, clearAutomatically)` 경로였고,
매 호출마다 영속성 컨텍스트를 flush·clear하고 있었습니다. 두 구현을 모두 JDBC로 맞추자 순서가
뒤집혔습니다. 기본 구현을 JDBC로 바꿨고, JPA 경로는 이 사실을 남기기 위해 비교 대상으로
보존했습니다(꼬리 지연이 가장 깁니다: max 3,242 ms).


### 이후 측정 (2026-09-09, DB 안쪽) — M-007

위 두 측정은 모두 애플리케이션 바깥에서 시간을 쟀습니다. "이 측정의 한계"에 적어 둔 **DB 락 대기
미측정**을 `pg_stat_statements`와 대기 이벤트 샘플링으로 닫았습니다.

- 동일 지갑에서 대기 표본의 약 84%가 잔액 행의 `Lock`(`transactionid` 75.4~76.9%, `tuple`
  7.6~8.5%)이고, 서로 다른 지갑에서는 Lock 대기가 0.0%입니다. **잔액 행이 직렬화 지점이라는 판단은
  측정으로 확인됐습니다.**
- 커넥션 풀 대기(`hikaricp_connections_pending`)는 어느 조건에서도 최대 3입니다. 병목은 풀이
  아닙니다.
- 잔액 UPDATE의 평균 실행 시간은 서로 다른 지갑 0.3 ms, 동일 지갑 97.4 ms입니다.

**이 ADR의 결정은 바뀌지 않습니다.** 다만 M-007은 잠금 전략과 무관한 것을 하나 찾았습니다.
차감이 트랜잭션 앞쪽에 있어 **행 잠금을 COMMIT까지 필요 이상으로 오래 쥐고 있었습니다**(31 ms
트랜잭션 중 17 ms, 그 안의 실제 DB 실행 2.31 ms). 차감을 트랜잭션 마지막으로 옮겨 동일 지갑
처리량이 1.75배가 되었습니다.

이것은 "어떤 잠금을 쓰는가"가 아니라 **"잠금을 얼마나 오래 쥐는가"**의 문제였고, 조건부 원자
UPDATE든 비관적 잠금이든 똑같이 겪었을 문제입니다. 잠금 전략 비교만으로는 보이지 않았습니다.
근거: [reports/11](../../reports/11-performance-failure-report.md) M-007·결함 I

### 이후 측정 (2026-09-16) — 뺀 대안을 실제로 만들어 재봄: 분산락 (M-024~M-028)

Alternatives에 "분산 락: DB 업데이트와 원자성이 자동 보장되지 않고 운영 실패 모드가 추가됩니다"라고 한 줄로
적어 두었습니다. 그 한 줄을 실측으로 바꿨습니다. **실험 경로이며 채택하지 않습니다** — `experiment-lock`
프로필(`apps/pay-api/.../experiment/lock/`)에서만 지갑 모듈의 `WalletBalanceRepository`를 감싸고, 기본 경로는 한
줄도 바뀌지 않았습니다. Redis 락 안에서 "조회 → 300~500 ms 멈춤 → 계산 → 조건 없는 UPDATE"를 하는, 락이
정합성을 지켜 준다고 믿는 구현을 일부러 만들어 같은 부하(스레드 16, 지갑 4, 60초, 각 3회)로 기본 경로와
대조했습니다. 근거: [reports/11](../../reports/11-performance-failure-report.md) M-024~M-028

| 조건 (같은 부하, 같은 멈춤) | 소유 겹침 쌍 | drift (INV-010) | 초과 승인 (INV-003) | 처리량 |
|---|---:|---:|---:|---:|
| SETNX+TTL 200 ms 락, 조회→계산→저장 (M-024) | 1,697~1,714 | 340,000~350,000원 | 340~350 | 19.2/s |
| + Watchdog 자동 연장 (M-025) | 0 | 0 | 0 | 9.7/s |
| + Watchdog + 프로세스 정지 SIGSTOP 400 ms × 35 (M-025) | 131~132 | 81,000~83,000원 | 81~83 | 8.7/s |
| + 쓰기 시점 fencing token (M-026 c-1) | 1,713~1,732 | 350,000~353,000원 | 350~353 | 19.1/s |
| + 읽는 순간 fencing token (M-026 c-2) | 1,722~1,770 | **0** | **0** | 승인 4~6건, 나머지 전부 거부 |
| Redis 단절 20초, fail-open (M-028) | 단절 중 2,210~2,245 | 486,000~491,000원 | 486~491 | — |
| Redis 단절 20초, fail-closed (M-028) | — | (락 자체의 것) | (락 자체의 것) | 단절 중 결제 0 |
| **이 ADR: 조건부 원자 UPDATE, 락 없음 (M-027)** | (락 없음) | **0** | **0** | **36.8~38.5/s** |

- lease가 트랜잭션보다 먼저 만료되면 **정말 깨집니다.** 지갑마다 60건만 승인 가능한데 141~149건이 승인됐고
  원장은 −81,000~−89,000원인데 스냅샷은 0에서 멈춰 "다 썼다"로 보입니다 — 어긋남은 원장과 대조해야만 보입니다.
- Watchdog은 "느린 작업"의 만료는 없애지만 "멈춘 프로세스"의 만료는 못 막습니다. 연장 스레드도 같은
  프로세스의 스레드이기 때문입니다.
- fencing token은 **읽는 순간부터** 걸려 있어야 정합성을 지키고(쓰기 시점 비교만으로는 (a)와 구별되지
  않음), 지키는 순간 lease가 짧은 시스템의 결제는 거의 전부 거부됩니다. 안전은 주지만 실행은 보장하지 않습니다.
  락 서버가 비워진 채 돌아오면 카운터가 되감겨 DB에 남은 토큰보다 작아지고, 그동안(지갑당 96건) 전부 거부됐습니다.
- lease를 작업의 두 배(1 s)로 잡아도 락 서버가 수백 ms 멈추면 만료가 났습니다(TTL 1 s 보충 실험, 3회 중 2회).
  lease의 시계는 락 서버의 것이고, 소유자는 응답을 받은 뒤에야 자기 lease가 언제 시작됐는지 압니다.
- 조건부 원자 UPDATE는 "언제 읽었는가"를 묻지 않습니다. 조건은 쓰는 순간 DB가 행 잠금 아래에서 검사하고,
  그 앞의 멈춤은 지연일 뿐입니다. 여섯 번 전부 승인 정확히 240건·drift 0이었고, Redis를 죽이고 살려도
  아무것도 달라지지 않았습니다.

**결정은 바뀌지 않습니다.** "분산 락은 운영 실패 모드가 추가된다"는 문장은 이제 숫자입니다: lease 만료(3/3),
프로세스 정지 뒤 만료(3/3), 락 서버 단절(fail-open이면 정합성 사고, fail-closed면 가용성 사고), 락 서버
재시작 뒤 토큰 되감김. 실험 경로는 이 수치를 같은 코드로 다시 재기 위해 남겨 두며 `EXPERIMENT_LOCK_MODE`
없이는 빈이 만들어지지 않습니다. 회귀 시험 `RedisLeaseLockTest` 3건(락 원시 연산의 의미 — 실험이 잰 것이 락의
버그가 아니라 lease 모델의 성질임을 고정).
