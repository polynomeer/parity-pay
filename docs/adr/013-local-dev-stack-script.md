# ADR-013 로컬 스택을 한 스크립트로 띄우고, 잡힌 포트는 우회함

- Status: Accepted
- Decided: 2026-09-14
- Date: 2026-09-14

> **에이전트 영향**: 로컬에서 전체를 띄울 때는 `scripts/dev.sh`를 씁니다. 다른 프로젝트가 기본
> 포트를 잡고 있어도 스크립트가 빈 포트로 옮기므로 **호스트의 다른 컨테이너를 내리지 않습니다.**
> 포트를 아는 곳(compose 매핑·Redpanda 광고 주소·pay-api 환경변수·Vite 프록시·재설정 메일 링크)
> 을 손으로 맞추지 않습니다 — 스크립트가 한 번에 넣습니다. `scripts/dev.sh down`은
> `docker compose down`이므로, 다른 세션이 같은 컨테이너를 쓰고 있으면 치지 않습니다.

## Context

로컬에서 화면까지 보려면 README가 여섯 단계를 요구했습니다 — 기관 DB 초기화, 기관 jar 빌드,
`docker compose up`, 기관 컨테이너 기동, `pay-api` 기동, Vite 둘. 순서가 있습니다: 기관 DB가
없으면 기관이 뜨지 않고, 기관이 없으면 충전·결제가 안 되고, `pay-api`가 없으면 Vite 프록시가
502를 돌려줍니다. `load-tests/run-e2e.sh`가 이 순서를 이미 셸로 갖고 있었지만, Playwright를
돌리고 바로 내리는 스크립트라 사람이 쓸 수는 없었습니다.

두 번째 문제는 포트였습니다. 이 개발 호스트에는 다른 프로젝트의 컨테이너가 상시 떠 있습니다
(2026-09-14 기준 `sys-drill`이 5433·6379·4317·4318·16686, `monticker`가 5xxxx 대역, `code-drill`이
5436·6381). `docker-compose.yml`은 `${PARITYPAY_DB_PORT:-5432}`처럼 호스트 포트를 환경변수로
바꿀 수 있게 되어 있었지만, 바꾸면 그 포트를 알아야 하는 곳이 **다섯 군데**였습니다.

| 포트를 아는 곳 | 안 맞추면 |
|---|---|
| compose 호스트 매핑 | 컨테이너가 뜨지 않음 (포트 충돌) |
| Redpanda `--advertise-kafka-addr` | **첫 연결만 되고 끊김** — 클라이언트가 부트스트랩 뒤 광고된 주소로 다시 붙습니다 |
| `pay-api`의 `PARITYPAY_DB_URL`·`PARITYPAY_KAFKA_SERVERS`·기관 URL·메일 포트 | 앱이 뜨지 않거나 충전이 실패 |
| Vite `server.proxy` 대상 (`vite.config.ts`에 8080 고정) | 502 |
| `PARITYPAY_PASSWORD_RESET_LINK` (`app.localhost:5173` 고정) | 재설정 메일의 링크가 열리지 않음 |

Redpanda 줄이 특히 나쁩니다. 호스트 포트만 9093으로 옮기면 `docker compose up`은 성공하고
`pay-api`도 뜨는데, 첫 메타데이터 응답이 `localhost:9092`를 광고해서 그다음 연결이 조용히
실패합니다. 어디가 틀렸는지 로그로 알아내기 어렵습니다.

## Decision

**`scripts/dev.sh [up|down|status|logs]` 하나로 전부 띄웁니다.** 순서는 E2E 스크립트와 같습니다:
의존 컨테이너 → 기관 DB 보장 → 기관 대역 → `pay-api` → Vite 둘.

### 포트 우회 규칙

1. 서비스마다 시작 포트가 있습니다(`PARITYPAY_*_PORT`로 바꿀 수 있음). 그 포트가 listen 중이면
   `+1`씩 올려 빈 포트를 잡고, 우회했다는 사실을 stderr에 씁니다.
2. **이미 실행 중인 우리 컨테이너**(`paritypay-postgres` 등)가 잡은 포트는 `docker port`로 읽어
   그대로 씁니다. 그러면 compose가 "설정이 바뀌었다"고 컨테이너를 다시 만들지 않습니다.
3. 이번 실행에서 이미 배정한 포트는 파일에 적어 두고 다시 배정하지 않습니다. 아직 아무것도
   listen하지 않는 Vite 두 개가 `lsof`만으로는 같은 포트를 받을 수 있기 때문입니다 (실제로
   5173이 잡힌 상태에서 고객 앱과 운영 콘솔이 둘 다 5174를 받았습니다). 같은 포트면 하나가 못
   뜨는 것을 떠나, 같은 오리진이면 운영 콘솔 쿠키가 고객 앱으로 넘어갑니다(ADR-011).
4. 결정한 포트를 위 표의 다섯 곳 **전부**에 넣습니다. 그러기 위해 두 군데를 바꿨습니다.
   - `docker-compose.yml`: `--advertise-kafka-addr=...OUTSIDE://localhost:${PARITYPAY_KAFKA_PORT:-9092}`.
     기본값은 그대로라 E2E·CI는 영향이 없습니다. 관측 스택 포트 셋도 같은 방식으로 변수화했습니다.
   - `vite.config.ts` 둘: 프록시 대상을 `process.env.PARITYPAY_API_URL ?? "http://localhost:8080"`.
5. Vite는 `--strictPort`로 띄웁니다. Vite는 포트가 잡혀 있으면 스스로 다음 포트로 가는데, 그러면
   스크립트가 정한 값과 재설정 메일 링크가 어긋납니다. 우회는 한 곳에서만 합니다.

### 이전 실행 정리

`up`은 먼저 이전 실행의 호스트 프로세스(pid 파일)를 죽입니다. 남아 있으면 `pay-api` 두 개가
같은 DB에 스케줄러·Outbox 릴레이를 두 벌 돌립니다. `load-tests/run-p004.sh`가 같은 이유로
`pkill`을 먼저 합니다.

### 관측 스택은 선택

`--observability`를 주지 않으면 prometheus·grafana·jaeger를 띄우지 않고
`PARITYPAY_TRACE_SAMPLING=0`으로 `pay-api`를 띄웁니다. 트레이스 백엔드가 없는데 샘플링이 1.0이면
내보내기 실패 로그만 쌓입니다.

## Alternatives

| 대안 | 뺀 이유 |
|---|---|
| `pay-api`·Vite까지 compose에 넣기 | 코드를 고칠 때마다 이미지 빌드입니다. 그 형태는 `deploy/run.sh`(ADR-011)가 이미 있고, 개발용은 호스트에서 돌려야 HMR과 디버거가 붙습니다 |
| 기본 포트를 아예 다른 대역(15432 등)으로 고정 | 오늘 비어 있는 포트가 내일 비어 있다는 보장이 없고, README·문서·E2E의 5432·8080을 전부 바꿔야 합니다 |
| `.env` 파일에 포트를 적어 두기 | 사람이 다섯 곳을 맞추는 문제가 그대로입니다. 스크립트가 값을 **만들어** 넣는 것이 핵심입니다 |
| Vite의 자동 포트 이동에 맡기기 | 재설정 메일 링크와 어긋납니다(§5) |
| 충돌 시 그냥 실패하고 사용자에게 맡기기 | 이 호스트에서는 거의 매번 실패합니다. 실패 메시지를 읽고 환경변수 다섯 개를 맞추는 것이 원래 문제입니다 |
| 다른 프로젝트 컨테이너를 내리기 | 남의 작업입니다. 내리지 않습니다 |

## Consequences

**긍정**

- `scripts/dev.sh` 한 줄로 화면까지 뜨고, 뜬 주소가 출력됩니다.
- 포트 충돌이 오류가 아니라 정보가 됩니다. 어디로 우회했는지 보이고, 모든 소비자가 같은 값을
  받습니다.
- Redpanda 광고 주소 함정이 스크립트 안에 갇혔습니다.

**부정 · 주의**

- **`down`은 `docker compose down`입니다.** `paritypay-*` 컨테이너를 전부 내립니다. 다른 세션이나
  실험(`load-tests/*.py`)이 같은 postgres를 쓰고 있으면 그것도 죽습니다. 볼륨은 남기지만
  실행 중인 실험은 깨집니다. 같은 호스트에서 두 세션이 돌 때는 `down`을 치기 전에 `status`와
  `docker ps`로 확인해야 합니다. 이 ADR을 쓰는 동안 실제로 한 번 그럴 뻔했습니다.
- prometheus의 스크레이프 대상은 `deploy/observability/prometheus.yml`에 `host.docker.internal:8080`
  으로 고정되어 있습니다. `pay-api`가 우회하면 지표가 끊기고, 스크립트는 그 사실을 출력만 합니다.
  파일을 마운트하므로 스크립트가 고쳐 쓸 수 없습니다.
- 우회는 `+1` 선형 탐색입니다. 5174가 잡혀 있으면 5175, 5175도 잡혀 있으면 5176 — 실제로
  운영 콘솔이 5176을 받은 적이 있습니다. 예측 가능하지만 "예쁜" 번호는 아닙니다.
- `lsof`에 의존합니다. macOS와 Linux에 있지만 컨테이너 안 같은 최소 환경에는 없을 수 있습니다.
- 첫 실행은 jar 셋을 빌드하느라 1~2분 조용합니다(`-q`). `--no-build`로 건너뛸 수 있습니다.

## Validation

- 기본 포트가 비어 있으면 5432·9092·8080·5173·5174로 뜨고 두 앱의 `/api`가 `pay-api`에 닿는다
- 시작 포트가 잡혀 있으면 빈 포트로 우회하고, 그 상태에서 충전이 `SUCCEEDED`가 되며 이벤트가
  Redpanda 토픽에 도착한다 (광고 주소가 맞다는 뜻)
- 고객 앱과 운영 콘솔이 같은 포트를 받지 않는다
- 이미 떠 있는 `paritypay-postgres`가 다시 만들어지지 않는다
- 인자 없이 실행해도 된다

## Outcome

2026-09-14에 구현하고 확인했습니다. 커밋 `fe80d12`, `3ec6eec`.

| 항목 | 결과 |
|---|---|
| 기본 포트 실행 | `/actuator/health` UP, 두 앱의 `/api/v1/auth/tokens` 프록시가 400(502가 아님 — API에 닿음) |
| 우회 실행 (`DB_PORT=5433 KAFKA_PORT=19092 PORT=16686 CUSTOMER_PORT=5174`) | 5434 · 19093 · 16687 · 고객 5174 · 운영 5176으로 우회. 고객 앱 프록시로 가입→계좌 연결→100,000원 충전 `SUCCEEDED`, `paritypay.events` 토픽 offset 214에 이벤트 도착 |
| 컨테이너 재사용 | 실행 중인 `paritypay-postgres`는 `Running`으로 남고 재생성되지 않음 |
| 백엔드 테스트 | 317/317 통과 (`--rerun-tasks --no-build-cache`) — compose 기본값이 바뀌지 않았음을 확인 |
| 프론트엔드 테스트·타입 검사 | 56/56, 통과 — `vite.config.ts`의 `process.env` 참조가 타입 검사를 지남 |
| 인자 없이 실행 | 처음에는 **아무 출력 없이 exit 1**로 죽었습니다. 빈 인자 목록에서 `shift`가 실패하고 `set -e`가 첫 `echo` 전에 끝냈기 때문입니다. 테스트를 전부 `up --no-build`처럼 인자를 넣고 해서 놓쳤습니다. `3ec6eec`로 고쳤습니다 |

인자 없는 실행이 깨진 것은 "스크립트를 사용자가 쓰는 방식 그대로 한 번은 돌려 본다"를 빠뜨린
결과입니다. 이후 스크립트는 기본 호출 형태로도 한 번 확인합니다.
